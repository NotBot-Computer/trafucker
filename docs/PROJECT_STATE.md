## 1. What this project is

**Traffic Tower** is a local party game built in **Godot 4.7** (GL Compatibility renderer), structured as a set of "many small competitive modes" (inspired by *Tricky Towers*). **Two modes exist:**

- **Don't Crash** (sessions A-R) — split-screen. Each player gets their own vertically-scrolling lane board side by side on one screen; you steer left/right to dodge oncoming traffic, and the road speeds up over time. Whoever survives longest (covers the most distance) wins the round.
- **Pile Up** (session S) — one shared tower. Players take turns steering car-shaped tetromino bricks down onto a single narrow platform under real rigid-body physics; when everything stops moving, anything that fell off costs the player who dropped it a life. Last of 2-4 builders with a life left wins.

The two share `GameSettings`, the menu flow, the key bindings and the round-start countdown, and nothing else — see §2. **The mode is chosen on the main menu and carried in `GameSettings.mode`.**

Full player-facing description, controls, and art notes are in [README.md](../README.md) — that file is accurate and up to date; don't duplicate it here, read it for the "how to play" side.

## 2. Architecture / structure

Scene tree flow: `MainMenu.tscn` (**pick a mode**) → `PlayerSelect.tscn` (pick 2–4 players) → `SkinSelect.tscn` (each player cycles/locks a color) → **either** `Main.tscn` (Don't Crash) **or** `TowerMode.tscn` (Pile Up).

The first three screens are shared and branch on `GameSettings.mode`: `PlayerSelect` hides the race-only "1 PLAYER vs BOT" option, and `SkinSelect` drops the bot hotkeys and picks which scene to hand off to. `SkinSelect` stays in the flow for both modes because both need a colour per player — in Pile Up it identifies whose brick is in the air and whose lives are whose, since every brick already on the pile looks identical.

**One node is shared between the two modes and it is worth knowing why it is the only one.** `Countdown` (`scripts/Countdown.gd`) sits in each mode's own `HUD` CanvasLayer and plays the "3 — 2 — 1 — GO!" that opens a round. It could be shared because it holds no game state and drives no game loop: it draws, and it emits `finished`. Freezing the game is the caller's job (Main leaves its boards' `active` false, TowerMode sits in a `countdown` state), and even the *clock* is the caller's — the two modes run on different ones, so `advance(delta)` is called from Main's `_process` and from TowerMode's `_physics_process`. See §5 session U for the measurement that forced that last part.

**Pile Up is a separate scene and script tree, not a variant of `Main`/`PlayerBoard`.** They have no geometry, camera model or update loop in common: Don't Crash is N independent scrolling boards moving `Area2D` obstacles by hand with no rigid bodies anywhere in the project, while Pile Up is one world of real `RigidBody2D` bricks on a `StaticBody2D` platform. `TowerMode.tscn` owns a `Camera2D`, the `Platform`, a `PiecesContainer` of live bricks, and a `HUD` CanvasLayer holding `TowerHUD`.

`Main.tscn` instantiates one `PlayerBoard.tscn` per player side by side inside `BoardsContainer`, and one `LaneDivider.tscn` between each adjacent pair inside `DividersContainer`. Each `PlayerBoard` owns its own `Road` (background), `PlayerCar`, and `ObstacleContainer` (spawned traffic). `LaneDivider` is a decorative strip that is **not** a child of `PlayerBoard`, but as of session O it is no longer independently timed: it *follows* a flanking board's `distance` odometer (see §5 session O, and the §7 invariant). The independent timer was the fragile design §7 used to warn about, and it did eventually ship a visible bug.

Global/shared state lives in the `GameSettings` autoload (`scripts/GameSettings.gd`, registered in `project.godot` under `[autoload]`): player count, chosen skins, the `PLAYER_SKINS` and `TRAFFIC_KINDS` tables (textures + spawn weights + per-kind speed ranges), and the 4-way keyboard binding table (`PLAYER_CONFIGS`).

## 4. What's already implemented

### Both modes

- **A round opens with a "3 — 2 — 1 — GO!" countdown** (`Countdown.gd`, ~2.7s), over a frozen playfield with a wash over it that clears on GO!. Each step opens with a 0.2s burst — a spark blooming outward from the centre — and the glyph then slams down into it, so the count arrives rather than appearing. It plays on a replay (Enter after a game over) as well as on the first round, since both go through the same entry point. It is the only node the two modes share — see §2.

### Pile Up (the tower mode)

- **The whole mode, end to end, unplayed.** Mode picker on the main menu → shared player-count/colour screens → a full match: turn order round-robin over living players, a brick the active player steers down onto the tower, a landing, a settle wait, a life lost for whatever fell, elimination at zero lives, a winner, Enter to replay, Esc to the menu.
- **A brick descends on its own and there is no drop button.** It falls slowly from the moment it appears; the player steers and rotates it on the way down and holds `down` to speed it up. The turn ends when it touches something.
- **Sideways movement is discrete.** A press moves the brick exactly half a cell, the dash button exactly one, and holding a direction repeats the half-cell step. Because every command is a multiple of half a cell and the aim clamp also lands on that lattice, a brick stays on an exact half-cell grid for its whole descent. **The dash is a chord of the dash key and a direction key, and either one may be the one you hold**: hold a direction and press dash, or hold dash and press a direction. Both spell the same thing, so a player picks whichever order suits the hand they already have on the keyboard. Half a chord — the dash key on its own — deliberately does nothing, because it is not a dash yet, it is the first half of one.
- **Contact is resolved by shape query, not by the solver.** A brick under the player's control is frozen *and* out of the collision world, so it can never shove the tower; every move is instead tested with `intersect_shape` and refused if that space is occupied. A refused downward move is what "landed" means. This is what makes exact discrete movement possible at all — see `TowerMode`'s header.
- **Bricks are real rigid bodies once they land.** Merged-rectangle collision (not one box per cell — internal edges catch neighbouring bricks), friction 0.94, zero bounce, mass proportional to cell count, shape-cast CCD, and a terminal-velocity cap that now governs collapses rather than landings.
- **A turn ends when the world stops, not when the brick lands**, so a brick that settles innocently and topples the tower five seconds later is still scored against whoever placed it. Debris is *counted* the moment it passes below the platform but *freed* much later, so the turn never waits for it to finish falling (see §5).
- **The camera follows the tower up**, holding the top of the stack at a fixed fraction of screen height, computed from the real rotated silhouette of every settled brick rather than from body origins. A parallax backdrop (`TowerBackground`) sells the climb.
- **HUD in the side columns**, not across the top — the playfield is a tall narrow shaft on a 1500x800 screen, so the columns were dead space and the top strip was stealing drop headroom.
- **Lives are the same heart pip Don't Crash trails behind a car**, in the same per-player colour, swelling out of its slot and fading the same way when one is spent. A spent slot keeps a ghost of the pip rather than going blank, which is the one place the two modes differ on purpose — see §5 session X.
- Headless validation harness (`TowerProbe`) covering match termination, settle behaviour and brick-through-platform tunnelling.

### Don't Crash (the racing mode)

- Full menu flow: main menu → 2/3/4 player select → per-player skin select (duplicate-skin avoidance, ready-up gating) → round start.
- Momentum-based steering (not lane-snapping) with configurable top speed and grip response.
- **Dash**: double-tap a direction within a short window → fast eased snap exactly one lane over, with a fading afterimage trail, on a per-player cooldown.
- **Drift**: triggered by a genuine velocity reversal (pressing the opposite direction while still carrying real speed the other way) — not a separate button/gesture. Nose points where you steer, actual momentum lags behind at reduced grip, leaves a twin continuous skid-mark trail (`Line2D`, not stamped marks). The drift *session* (trail + nose lead, `is_drifting`) persists across direction switches and only ends after a short release-grace window with both keys up; *grip* (`drift_sliding`) is a separate sub-state that resolves once momentum catches up to the held direction, and instantly re-engages on a fresh reversal. See §5/§6/§8 for why this is split this way — it was not obvious up front.
- Traffic: **10 vehicle kinds** (sedan, SUV, pickup, van, sports car, semi truck, towed trailer, transit bus, coach, motorcycle) with weighted random spawn selection, real cropped sprite art, per-kind size ratios matched to each sprite's real aspect ratio. Weights total 100 so each reads as a percentage. Six of them had their art replaced or introduced in session Q; `coach` was split out of `bus` in session R because the two sprites' proportions genuinely differ (§5 session R).
- **Chaotic lane-changing traffic**: a random slice of spawned obstacles blink a turn signal, then smoothly merge one lane over mid-transit, instead of every vehicle holding a perfectly straight line for its whole lifetime. See §5 session D for the fairness constraints that keep this from feeling cheap.
- Speed ramp: `SpeedRamp.speed_at(elapsed)`, an eased curve (160 base, easing along `progress ^ 1.45` to a 560 top speed at 100s, then creeping at +1.2/s so a round still always ends). Traffic density tightens on the same curve over a shorter window (0.85s → 0.35s between spawns, complete at 70s). `PlayerBoard` and `LaneDivider` both call into it — it is one implementation now, not a shared convention. See §5 session K for why the old straight line was replaced.
- **Three lives per player, shown as hearts trailing behind the car.** A crash costs one life instead of ending the round: the vehicle that landed it is destroyed on the spot (the existing explosion), the board drops to `INVULN_SLOW_MULT` of road speed and eases back up over ~1s, and the car blinks for `INVULN_DURATION` (2.2s) during which traffic passes straight through it. At zero lives the board goes `alive = false` exactly as it always did, so `Main`'s round-end path is unchanged. The pips are the user's own pixel-art heart re-hued into each player's car colour at runtime (one PNG, six colours), laid out on fixed slots one line below the car's rear bumper and anchored to the *road* rather than to the car's drawn position — which is what keeps them out of Nitro's comet. See §5 session W.
- Round scoring by distance traveled; game-over overlay declares the winner; Enter restarts, Esc returns to menu.
- Road and median rendered as tiled real-texture scrolling strips (not procedurally drawn shapes) — both cropped from the same source art so grass/guardrail styling matches exactly (`Road.SHOULDER_RATIO` is tuned to the texture's actual asphalt width).
- **Player-count-aware camera framing**: camera zoom adapts to fit every board's full width on screen at any player count (2-4), only ever zooming out from the preferred `1.15`, never in — see §5 session E. Road/median tile rendering and obstacle spawn/despawn extend to match whatever extra vertical area that zoom-out reveals, and a screen-space vignette (`ScreenMask.gd`) masks the top/bottom edge.
- **Skill pickup + choice system**: a rare glowing collectible (`SkillPickup.gd/.tscn`) spawns in a free lane every 9-15s, scrolling at the road's own rate (not a vehicle's own pace). Driving over one doesn't crash the player — it shows two glowing choice icons flanking the car (left = a skill that affects opponents, right = a skill that benefits the player) that the player picks with two new dedicated per-player keys, independent of steering, so the round never pauses and the choice never expires (it only ever changes if the player drives over another pickup before picking). `PlayerBoard._resolve_skill_choice()` routes "self" picks to a random entry of `SELF_SKILLS` (just `["tank"]` today) and "opponent" picks to a random entry of `OPPONENT_SKILLS` (just `["taxi"]` today) — the latter emitted as a signal for `Main` to relay to every *other* board rather than applied locally. See §5 session F for the choice-system design history, session G for the first self skill, and session I for the first opponent skill; §11 for next steps.
- **The Taxi (the first opponent skill)**: picking "opponent" sends a reckless cab onto every *other* player's board (relayed by `Main`, since boards have no reference to each other — see §5 session I). It arrives from behind and runs riot through the traffic for `TAXI_CHAOS_DURATION` (11s) — cutting across up to three lanes at a time, hunting gaps, surging up the road and braking hard — then floors it off the top. It **roams the whole board rather than chasing the player** (see §5 session L); being dangerous to them is a consequence of where it happens to be. Critically it is a **real traffic vehicle** — moved by the same line as every other car, with car-following and lane-clearance limits that make overlapping traffic geometrically impossible; all of its aggression lives in how tightly it plays inside those rules (barely signals, sometimes signals the wrong way, squeezes into gaps ordinary traffic won't). See §5 session I and §6/§7/§8 for the design history and the rules that must not be relaxed.
- **Tank Mode (the first self skill)**: picking "self" transforms the player into an invincible tank for 6s — cropped/rotated tank sprite, steering top speed cut to ~72% (heavier handling), any traffic it touches is crushed instead of crashing the round, and `key_confirm` is repurposed from boost to firing a cannon shot (muzzle flash/smoke overlay + a real traveling shell sprite + a brief recoil kick/speed-dip) at the nearest vehicle ahead in roughly the same lane. See §5 session G for the full build/tuning/bugfix history and §7/§12 for the non-obvious parts (overlay-anchoring trick, the tween-kill leak, asset-alpha gotchas).
- **Boost**: a per-player charge bar (drawn above the car via `PlayerBoard._draw()`) fills while `is_drifting` is true. Spent by holding the player's `confirm` key (bound per-player in `PLAYER_CONFIGS`, previously unused during a round) — a hold-to-drain resource, not an instant full-bar burn, so a player can spend part of the bar and bank the rest. Speed multiplier is re-read from the *current* charge every frame across three tiers (1.3x/1.5x/1.8x), so a long burn from a full bar visibly weakens as it drains through them. Multiplies `current_speed()` only (not `elapsed`), so it doesn't touch the permanent difficulty ramp. Exhaust is small procedural flame polygons (same technique as the dash-ghost trail, no particle system/new art) tinted from the player's own car color, which required adding a real `Color` per skin (`GameSettings.PLAYER_SKINS[i]["color"]`) since skins were texture-only before — threaded through `SkinSelect` lock-in → `Main._build_boards()` → `PlayerBoard.body_color`. See §5 session C and §12 for details.

- **Nitro (the second self skill)**: the car lifts off the road inside a gathering ball of energy, rockets up it at 2.85x for ~3.8s trailing a comet, then settles back down — 5.3s of flight in all. Airborne, it flies **over** traffic rather than through it, which is what makes it a benefit rather than a faster way to crash and what keeps it distinct from Tank Mode's ground-level invincibility (that one crushes what it touches; this one never touches anything). Rounds are scored by distance, so the surge banks a real chunk of score. Its arrival is what makes the skill choice an actual choice: with one entry per pool, `randi() % 1` was always the same pick. See §5 session P.

- **Six more skills, three a side, each in its own file under `scripts/skills/`** (session Y, unplayed). Chosen so that no two skills — old or new — are the same mechanic in a different coat: Tank is a timed invincible transform, Nitro is timed flight, Taxi is a rogue AI vehicle; the new ones are **Make Way** (traffic ahead pulls out of your lane, via the existing lane-change machine), **Pit Stop** (instant: a spent life back, or a full boost bar at full lives), **Compact** (the car shrinks to 66% width for 7s — the geometry changes, not the player), **Detour** (lines of roadworks barriers, spawned as ordinary `Car`s so collision, culling and the bot's senses all come free, with one gap to find), **Oil Slick** (grip ×0.34 for 5s plus a slow two-sine fishtail — control, not the road), and **Smoke Screen** (a rolling smoke band over the upper board for 5s — information, and no physics at all). They ride a small module layer (`SkillEffect`/`SkillCatalog`/`SkillOverlay`) that `PlayerBoard` consults before its three inline skills; every icon is still a placeholder. Session Z then reworked three of them without touching any mechanism: Oil Slick draws the user's own puddle art at full opacity (`sprites/skills/oil_1..8.png`), Make Way's reach went 400 → 720px and it re-skins the player's car as a police cruiser (`sprites/cars/police.png`, via the new `SkillEffect.car_texture()` hook), and Smoke Screen was made much thicker and now covers the road from the top edge down. See §5 sessions Y and Z, and `docs/SKILL_ART_BRIEF.md`.
- **A bot that plays a board (`BotDriver.gd`)**, switchable on or off per player at any moment — the **1-4** keys during skin select or mid-round, plus a **1 PLAYER vs BOT** button on the player-count screen; **5** cycles EASY/NORMAL/HARD live. It exists first as a testing tool (this project's only validation is manual playtesting, so being able to hand a board to the AI and watch a change play out hands-free is the point) and second as the single-player opponent. It drives through the same `_steer_held()`/`_press_steer()`/`_press_confirm()` entry points the keyboard uses rather than faking input events — see §5 session J for the design and the four scoring bugs it took to make it play respectably, and §7 for the invariants.

## 5. Session history

### 2026-09-03, session Z (second pass): the police car, and the smoke that was a slab

Session Z's first pass was played and came back with three things and one new ask. In order:

**"The smoke looks like a block, it doesn't look natural, and there's a gap between where the smoke ends and the top of the road."** Those two are one bug. The band started at `_hud_bottom + HUD_CLEAR_RESERVE` (79px) to keep the HUD clear — but the camera sees above y = 0 by `vertical_margin`, which is **125px at the 4-player zoom** (measured, not estimated: the old comments said ~107). So the bank had clear road above it, clear road below it and the board edges either side: four straight edges, i.e. a slab parked on the road. Nothing about density was going to fix that.

The fix is that the HUD strip is now **veiled instead of skipped**. The band starts above the top of the visible road (`-(vertical_margin + BAND_TOP_OVERSHOOT)`, with the whole top feather finishing off-screen, so there is no top edge at all) and its density is multiplied down to `HUD_VEIL_ALPHA` over the bars. Two details earn their keep. The veil is a **window, not a stripe** — a full-width thin band was tried first and is worse than the hole it replaced, because traffic scrolling down through it lights up in every lane for ~50px and then vanishes, which reads as the smoke flickering; the bars only occupy the middle `BOOST_BAR_WIDTH_FRAC` (0.5) of the board, so the window is that wide plus a pad, and the outer lanes stay at full density. And its alpha was walked up twice against screenshots — 0.26, then 0.40, then 0.52 — because at anything thinner a car crossing the window was plainly readable. At 0.52 the smoke over the boost bar is ~0.42 alpha: the bar keeps well over half its contrast, a grey car does not.

**The floor stopped being a rectangle.** The base was five full-width gradient slices, so at any given height it was one value across all 360px — the definition of a slab, and no amount of puffs on top hides that the thing underneath them is rectangular. It is now a 16x5 grid of quads whose every corner samples the vertical profile times a drifting two-sine wobble (`BASE_VARIATION` 0.20), so the floor is never the same twice across a row and the whole field creeps. Corners are sampled once per grid line and shared by the quads either side, so the grid itself is invisible. The veil is also a shape the five fixed slices could not have expressed.

**"Make it even harder to see."** `BASE_ALPHA` 0.72 → 0.80 and the puffs 0.30/0.34 → 0.32/0.38, which with the wobble puts a typical spot at ~0.86 and the knots at ~0.98. `PUFF_COUNT` 22 → 34, which is not taste: the band is now ~186,000px² on screen against ~119,000, and 22 puffs over it would have been ~1.3x coverage — *thinning* the smoke in the change meant to thicken it. 34 is ~2.0x. **This is the second time the file's own written caution (that past ~0.85 "the road is simply gone") has been overruled by the person playing it**, and the note now says so; if it ever needs pulling back, `BASE_ALPHA` is the honest lever because it sets what the thinnest spot costs.

**And the player now drives an actual police cruiser during Make Way.** `scripts/dev/extract_police.py` cuts `sprites/cars/police.png` out of the user's `polis.png` — flat grey background, soft drop shadow, ~5.7x upscaled pixel art. The shadow is excluded by threshold rather than by geometry: the car's own dark parts sit ~80-95 from the background grey and the shadow never gets past ~40, so a 55 threshold takes one and leaves the other; the antialiased outline is then grown back by dilating the solid body 3px and keeping only what is still clearly not background.

Wiring it needed one new hook. `SkillEffect` gained `car_texture()`, `PlayerBoard` gained `_effect_car_texture()`, `_current_player_texture()` and `refresh_car_texture()` — the exact shape `car_kind()`/`refresh_car_size()` already had, and for the identical reason: with two systems able to re-skin the car, neither end of either one can hardcode "put it back to `player_texture`" without being wrong whenever the other is still live. `_deactivate_tank_mode` did exactly that, and would now drop a player out of a police car they were still driving; both ends of Tank Mode go through the new function instead. `SkillProbe`'s snapshot gained the car's texture, because a skin left behind is the session-G class of bug in a form the child-node count cannot see — nothing leaks, the player is just permanently in someone else's car.

**The art was fitted to the footprint, not the other way round.** `Car._rebuild()` scales a texture to `width x height` on each axis independently, so a texture at any aspect but `PLAYER_KIND`'s is visibly distorted. The cruiser is more slender than the stock sedans (h/w 2.15 against 1.81), so it is scaled to the same 121px length they use and centred in the same 78x132 canvas, ending up ~56px wide against their 67. **Make Way deliberately does not claim `car_kind()`**: a cruiser that was also a different size would be a second, unasked-for mechanic riding along with a costume, and the hitbox, steering bounds, dash clamp and what the bot thinks fits in a gap all stay exactly what they were.

The strobe was kept, as asked, and moved onto the car it now sits on. The lamp positions are measured off `police.png` rather than guessed — its painted light bar is at 0.504 down the car's own content box with the blue lens 0.137 of the width left of centre — so the drawn lamps land on the painted ones and light them up instead of floating over the bonnet in front of them. The fake dark "housing" rectangle under them is gone: it existed to make the glows read as mounted hardware, and the car now has real mounted hardware that it was doing nothing but covering. The beams are thrown from the car's **nose** rather than from the lens, because lamps at the car's middle threw red and blue over the bonnet the player is trying to look past.

Validation: `godot --headless --import`, `--quit` on the boot scene and on `Main.tscn` (both clean), `SkillProbe` (OK, including the new skin check). Drawing was again checked with a throwaway screenshot scene, deleted afterwards — and it earned its keep twice, first catching the disc-edged puffs and then measuring that the "invisible" bus at the top of the band was in fact under the smoke correctly and only looked visible in an upscaled crop.


### 2026-09-03, session Z (first pass): real oil, a siren that reaches, and smoke you cannot see through

Four asks against session Y's skills, all of them feel/art rather than mechanism: give Oil Slick the user's own art (`~/Documents/yag.png`), make it opaque and make traffic visibly drive over it; make Make Way reach further up the road; make Smoke Screen much thicker. **Nothing about any skill's physics changed** — the grip is still 0.34, the hurry is still 0.7, Smoke Screen still has no physics hook at all. This session moved three numbers and one drawing routine.

**Oil Slick's spills are now sprites.** `scripts/dev/extract_oil.py` cuts eight puddles out of the 1536x1024 sheet into `sprites/skills/oil_1..8.png`. It is a segmentation job rather than the grid-measuring the other `extract_*.py` do: threshold at alpha > 100 (bodies sit at 200-255), dilate 14px so each puddle adopts its own ring of splash droplets instead of contributing a dozen extra components, label, crop, cap at 256px. Two things in it are load-bearing. The sheet's "transparent" background is not blank — it carries a dark smoke gradient at alpha 1-8 that is invisible in any preview over black and would have been a grey film over the asphalt; `ALPHA_FLOOR` drops it, set well under the antialiased edge values so no outline is eaten. And the downscale is done **premultiplied**: straight-alpha RGBA through Lanczos drags the transparent pixels' near-black into every edge, which on art whose entire subject is a bright rim would have ringed each puddle with a dark halo.

**Opaque, and the traffic is what makes it read as being on the road.** The file previously argued the opposite — `SPILL_BODY` was alpha 0.58 so the road texture would survive underneath, on the theory that a solid spill reads as a hole in the asphalt. With real art that inverts: the sheet's puddles carry their own dark rim, rainbow film and wet highlights, which *is* the "liquid on a surface" information, and thinning them to 58% destroys all three and leaves a smudge. What keeps them from reading as holes is that `draw_board()` runs inside `PlayerBoard._draw()`, which a CanvasItem draws before its own children — so every vehicle in `ObstacleContainer`, and the player's own car, is drawn over the oil. That layering was already there for a different reason (a spill must never hide an oncoming vehicle; vision is Smoke Screen's job) and now carries the whole illusion. Verified by screenshot, not by argument: a truck passing a spill occludes it.

The procedural sheen, the hue crawl and the upper-edge glint are gone with the polygons — the art has all three. `SPILL_STRETCH_Y` dropped 1.5 → 1.15, because a ring of random radii is round by default and needed the streak; these puddles are already streaked (one is nearly 3:1) and stretching further smears the film. Rotation (±0.30 rad) and a horizontal flip give the eight textures enough variety for a nine-spill field, and the textures are dealt from a shuffled bag rather than picked independently — nine independent `randi()`s over eight textures produce a visible triple more than half the time. `draw_texture_rect` cannot rotate, so the tilt goes through `board.draw_set_transform()`; **that is canvas state and `draw_board()` runs partway through `PlayerBoard._draw()`**, so the reset after the loop is unconditional or the boost bar, the life pips and the bot tag all draw rotated.

**Make Way: `SIREN_REACH` 400 → 720.** 400 reached about two thirds of the way up a 620px board from a player sitting at ~560, which left the top third of the lane full of cars that began moving only once they were close. 720 covers the player's y plus the largest `vertical_margin` the 3/4-player camera zoom adds (~107), i.e. the whole visible road and a little of the strip above it, so a car is pulled aside at or just before the moment it enters the board. The timing argument for the old number gets *better*, not worse: at the ramp's top speed a car 400px out had ~0.8s before it arrived against a 0.29s hurried slide, and at 720 it is ~1.5s — the reach was never limited by the physics, only by a first guess at how strong the skill should be. The drawn corridor's top clamp moved from `0.0` to `-board.vertical_margin` to match: the board draws past `[0, board_height]` by that margin (session E) and traffic is visible up there, so a corridor stopping at `y = 0` would have left cars being shoved aside above the end of the thing shoving them. What did **not** change is the honest limit in the file's header — a car with nowhere safe to merge still stays put, so a longer reach finds more cars, not more room.

**Smoke Screen: thicker in both axes, and the puffs stopped being discs.** Density went 0.44/0.12/0.20 → 0.72/0.30/0.34 and the band's bottom edges 0.38/0.52 → 0.50/0.66 of board height. That cuts the clear approach from ~218px to ~131px (~0.33s at mid-round speed) and takes a typical spot from ~0.51 to ~0.80 alpha. Session Y's file had written that above ~0.85 "the road is simply gone and the victim stops steering and starts praying"; played, the reality was that 0.76-in-the-rare-knots left traffic perfectly readable, and these numbers deliberately sit past that old ceiling. **The one hard ceiling that was respected is the player's own car**: Nitro lifts it 105px to a roof at ~435px and `BAND_BOTTOM_FRAC * 620 = 409` clears that by 26px — any further and a boosting victim is inside their own smoke, which reads as a bug.

`PUFF_COUNT` 14 → 22 is not a taste change but the same coverage arithmetic re-run against the taller band: 14 puffs over the old 87,000px² band was ~1.6x coverage, and 14 over the new 119,000px² band would be ~1.3x — i.e. *thinning* the smoke in the change meant to thicken it. 22 is ~2.1x, which is what puts a typical point under two puffs.

**And the failure that only a screenshot could have caught.** At 0.12/0.20 `draw_circle`'s hard rim was faint enough not to matter. At 0.30/0.34 it is not: the first render of the thicker smoke was twenty-two legible circles, a raft of soap bubbles, which is a worse look than the thin smoke the change existed to replace. Each puff is now one `GradientTexture2D` (radial, near-full alpha out to 45% of the radius and then falling to nothing) drawn as a rect — the same one draw call `draw_circle` was, and no edge at all. A pure linear falloff was rejected: it averages a third of its peak and turns the bank into haze with nothing solid enough to hide a car behind. `SkillProbe` passes a broken visual cleanly by construction (headless has no renderer), so this was found with a throwaway scene that booted `Main.tscn`, applied all three skills to different boards and saved a viewport PNG. It is not in the repo; if the next visual change to a skill is bigger than this one, it is worth writing properly.

**One rejected micro-optimisation, recorded because the reasoning is not obvious.** The puff texture depends on nothing about the board or the effect, so it wants to be a `static var` shared across all four boards. Written that way, `godot --headless --quit res://scenes/Main.tscn` began reporting "9 ObjectDB instances were leaked at exit" — with the static holding `null` and nothing ever assigned to it. Measured both ways: the same file with the two `static` keywords removed exits clean. The storage for a script's statics evidently outlives the leak check in 4.7.1. That headless run is this project's only automated validation and its entire value is that clean means clean, so the texture is per-effect. It is a `Resource`, not a `Node`: it is refcounted away with the effect and there is nothing for `deactivate()` to free.

Validation: `godot --headless --import` (the eight new PNGs), `godot --headless --quit` and `--quit res://scenes/Main.tscn` (both clean, no leaks), `SkillProbe` (OK — 18 lifecycle cases, 6 no-stack cases, Pit Stop's refund), and the throwaway screenshot above for the three skills' drawing.


### 2026-09-02, session Y: six skills at once, and the layer that made that possible

Asked as: assign agents to generate skills for Don't Crash, both categories, **diverse — "not just the copies of the current ones"** — and use ChatGPT to generate the animation frames and skins in pixel-art style, or, failing that, "create a temporary skin and let me generate it later".

**ChatGPT was not reachable, and the fallback was taken deliberately rather than by accident.** No `codex`/`openai` CLI on the machine, no API key in the environment. The one remaining route — driving chatgpt.com through the user's logged-in Chrome — was rejected on three counts: every generated image is a download needing a separate permission, the web UI's raster output is nowhere near pixel-perfect and would need the same background-removal pass that cost sessions G/H/P each a chunk of their time, and it would have put the whole session's throughput behind a browser loop. So: `scripts/dev/make_placeholder_skill_icons.py` draws every glyph and Detour's barrier from hand-typed 16x16 pixel maps (nearest-neighbour doubled, so they are honest pixel art, just blunt), and `docs/SKILL_ART_BRIEF.md` is the brief for the real thing — canvas, frame count, what each frame shows, where each sheet plugs into which script. Replacing an icon is a file swap at the same path; nothing in the code names a placeholder as such.

**The structural decision came first, and it is the one worth defending.** `PlayerBoard.gd` was 2559 lines with three skills written straight into it. Six more, written the same way, would have been ~1200 lines more of the same file — and, decisively, six agents editing one file in one checkout is the exact failure §12 already records from session Q (two processes read-modify-writing `GameSettings.gd`, one edit lost, nothing flagged). So before any skill existed, a module layer went in: `SkillEffect` (a `RefCounted` with lifecycle hooks, physics multipliers, a crash-absorb veto, a `car_kind()` claim and two draw hooks), `SkillCatalog` (one table: id → category/title/script/glyph) and `SkillOverlay` (a z-6 child node, because a CanvasItem draws under its own children and `PlayerBoard._draw()` therefore cannot get above the traffic — the boost bar has been behind passing cars this whole time for that reason). `PlayerBoard` gained ~90 lines of plumbing: dispatch in `_resolve_skill_choice`/`receive_opponent_skill` that checks the catalog first and falls through to the tank/nitro/taxi branches, `_effect_*_mult()` folded into `current_speed()`/`steer_top_speed()`/the grip line, `_effect_car_kind()` inside `_current_kind()` (Tank still outranks it), an absorb check ahead of `_take_hit`, `refresh_car_size()` (which `_deactivate_tank_mode` now uses instead of hardcoding `PLAYER_KIND`, or a tank ending mid-Compact would snap the car to the wrong size), stacked timer bars, and `_clear_skill_effects()` from both `start_round()` and the elimination branch. **Tank, Nitro and the Taxi were left inline on purpose.** Porting them would have been a refactor of three playtested skills with no playtest behind it; the layer is additive and the three old branches are untouched.

**Then six agents, one file each, forbidden from running Godot.** Each got the full contract, a design brief, the house style, the §12 trap list, and two hard rules: touch exactly one file, and never run `godot` — concurrent headless runs race on `.godot/`, and validation was the parent's job. Stubs for all six were in the catalog and compiling clean *before* dispatch, so at no point did the project fail to load. All six were then killed by a rate limit mid-flight; three (Make Way, Compact, Oil Slick) had already written complete files, three (Pit Stop, Detour, Smoke Screen) had not and were relaunched. The three that died after writing never delivered their reports, so their §5 notes below are reconstructed from the files, which are heavily commented enough for that to be reliable.

**Two contract bugs, both found by the agents reading the base class against the engine, both fixed at the source.** (1) The `SkillEffect` doc said to draw on `board` from both hooks; Godot refuses `draw_*` on any CanvasItem but the one currently inside its own `_draw()`, so `board.draw_*()` inside `draw_overlay()` — which runs from `SkillOverlay._draw()` — would have painted nothing. Make Way and Compact both spotted it and drew on `board.skill_overlay`; the doc now says so and the three later agents were told directly. (2) `_apply_skill_effect` called `activate()` *before* appending the effect to `active_effects`, so a skill claiming a `car_kind()` and calling `refresh_car_size()` in `activate()` was answered as if it did not exist — Compact's first version had to defer its shrink to its first `tick()` to get around it. The order is now flipped both ways: listed before `activate()`, removed before `deactivate()`, which also means a `deactivate()` that asks the board to recompute the car's size is not answered by the very effect being retired. Compact was simplified to match.

**The six, and why each is not a copy of something** (every number is a first guess, none has been felt):

- **Make Way** (`siren`, self, 5s). Traffic ahead in the player's lane is handed to the *existing* lane-change state machine with its metas pre-filled — starting in `moving`, indicator lit, `lc_timer` at 0 so the first frame is exactly where the car already is — and then hurried by feeding that same machine extra delta (`HURRY_TIME_BONUS` 0.7 → a 0.29s slide). Pre-loading the timer was rejected because the machine lerps from `lc_from_x` by the eased fraction, so a timer starting at 0.2 teleports the car 35% of a lane on its first frame. A car with nowhere safe to go stays put — the skill opens the lane it can, not a clear road, and the corridor is drawn under the traffic so a car still standing in it is visibly the limit rather than a bug. Skips taxis (their AI owns their x) and pickups. Merge room is measured bumper-to-bumper against real vehicle lengths, since `LANE_CHANGE_SAFE_GAP`'s 200px centre-to-centre means 20px of daylight for a truck and a parking space for two sedans.
- **Pit Stop** (`pitstop`, self, instant). One spent life back; at full lives, a *full* boost bar instead (not a top-up — the tiers only mean anything from full), so a roll is never wasted. The only skill with a permanent consequence and no timer, which is the point of it. The refund rebuilds exactly one pip: it kills `heart_loss_tween` if one is mid-pop (a loss tween can only ever be popping this same slot), frees whatever is in the slot, builds a fresh `Sprite2D` the way `_build_hearts()` does and writes it into that one index — so the invariant `_spend_heart()` relies on (exactly `lives` valid pips in the first `lives` slots) holds and the *next* crash spends the right one. Rebuilding the whole row was rejected (flickers all three, kills an unrelated tween). The pip plays the loss gesture backwards off `HeartPips`' own numbers, ease-out rather than the exact reverse curve (which would slam into the slot), then a landing flash via `modulate > 1.0` — body flares, black outline stays black. `refresh()` re-grants, so two picks inside the 0.8s window both count. Its 0.8s duration is cosmetic — frames to draw in — and `bar_color()` is transparent so it never shows a countdown for work already done. **It shipped with a real bug the probe caught on its first refund** — see §12's freed-instance entry.
- **Compact** (`compact`, self, 7s). `car_kind()` returns `PLAYER_KIND` at 66% width — width only, because `height_frac` multiplies the computed width and touching it would distort the sprite. Every consumer of `car_size()` re-reads it (dash clamp, `steer_bounds`, trail spacing, icon offset, the bot). The dangerous half is the grow-back: a wider car has narrower bounds, the steering block re-clamps but a dash in flight writes `car_x` straight from `dash_from`/`dash_to` computed against the old bounds, so `deactivate()` re-clamps both endpoints rather than cancelling the dash. `STEER_MULT` 1.08 as a handling nod. Tank outranks it and the visuals stand down while any other footprint is in force rather than draw a slack readout that is not true.
- **Detour** (`roadblock`, opponent, 7s). Lines of barriers, each an ordinary `Car` in `obstacle_container` with `speed_mult` 1.0 (bolted to the road, like a pickup) — so movement, culling, the crash path and the bot's senses all come free and nothing bespoke moves anything; `_lanes_used_near_top()` even keeps traffic out of a fresh barrier's lane, which is what leaves a pocket behind each one to slide into, and a taxi driving up into one queues behind it via `_taxi_follow_limit`. First line at 0.4s, then every 1.9s from the *actual* spawn, and a line is only laid if it will reach the victim before the bar runs out — so it is 3 lines from ~27s into a round and 2 before, decided by road speed rather than a dice roll. Footprint `width_frac` 1.0 × `height_frac` 0.4167 (20/48, the art's own ratio): edge to edge, and adjacent hit boxes leave an 11px seam against the player's 27px box, so straddling is not a way through. **Gap walk:** the first line anchors on the victim's current lane (excluded — a gap where you already are is a free pass), later lines within `GAP_WALK_MAX` 2 of the previous gap; two adjacent gaps only at 7+ lanes, so never today. **Crowding is judged at arrival, not at spawn** — a barrier closes at 1.0, faster than everything, so `_lanes_used_near_top()`'s "top 190px now" is the wrong question: every car in the candidate gap lane is played forward by the line's travel time and the gap refused if the car would be within a lead window of the victim (0.6s if the line overtakes it, 0.8s if it passes first); that is never relaxed. A second, cosmetic score counts cars the barrier would visibly drive through in closed lanes; if the best candidate still has those the line waits, retried every frame, and after 1.2s is laid through them anyway (the same overlap fast-behind-slow traffic already produces, and that lane was closed by the car regardless). If no gap ever passes, the line is lost rather than laid unfairly. While a line is above the victim, traffic ahead of it in the two lanes flanking the gap with a still-`pending` lane change is set `idle` — exactly what the machine does itself when no safe lane exists — so a late merge cannot close the gap. ### 2026-09-01, session W: three lives, and the two places a life pip must not be

The user asked for three hearts each in Don't Crash, drawn from their own `kalp.png`, sitting *behind* the car, coloured to match it, with a life lost on contact and the usual slow-down-and-blink recovery that these games use. Four of those five are mechanics; the interesting one is "behind the car", because in this game there are two different things that phrase can mean and the effects already living back there decide which.

**"Behind" is a z-order question before it is a position question.** Everything the player's car emits comes out of its back end: the boost exhaust and Nitro's ground shadow at z -1, Nitro's two energy layers at z 2 and the airborne car itself at z 3. Drawing the pips the way this board draws everything else — in `PlayerBoard._draw()` — would have put them at the board's own z 0, which is *in front of* the boost flames. A row of hearts covering the exhaust is the exact failure the user named, just with the wrong effect. So the pips are three `Sprite2D`s at `HEART_Z` (-2) instead: above the road (-10), below every tail-pipe effect there is. Nothing that comes out of the back of the car can be occluded by them, which makes the requirement structural rather than something to re-check each time a skill is added.

**The row is anchored to the road, not to the car, and that is what leaves Nitro room.** Nitro lifts the car `NITRO_LIFT_PX` (105) up the board and streams a comet ~194px out behind it. Pips parented to the car's drawn position would ride up with it and spend the whole flight inside that comet; anchored to the road at a fixed line, the lift *opens* the gap and the effect plays out in it. `_layout_hearts()` therefore reads `car_x` and never `player_car.position` — the latter also carries Nitro's per-frame shudder, and a readout that vibrates is a readout you stop reading.

**That fixed line exists because the car's rear bumper never moves.** `ground_y` subtracts half the car's own height from `board_height - CAR_BOTTOM_MARGIN`, so the bumper lands on the same y whatever is being driven — Tank Mode's taller footprint included. The 24.0 that used to be spelled out twice in the file is now `CAR_BOTTOM_MARGIN` for exactly this reason: the heart row hangs off it, and a hardcoded copy in a third place would be a third thing to keep in sync. The row ends up spanning 58.5px against a 33px car, centred on it, and still clears the board's side bounds at full lock.

**One PNG, six colours, done per pixel rather than by `modulate`.** Modulating the sprite by the car's colour multiplies the *whole* image, which turns the red body muddy and the white highlight into a flat wash of the player's own hue — the outline survives (black times anything is black) and nothing else does. `_tint_heart_texture()` instead walks the image once at round start and re-hues only the pixels whose saturation is at or above `HEART_BODY_SAT`: the black outline and the white highlight are hue-less and are left exactly as they are, which is what keeps a yellow or a green pip readable against grey asphalt. Each body pixel keeps its own brightness so the art's shading survives, and `extract_heart.py` normalises the brightest body pixel to 1.0 so that multiply needs no constant on the game side describing this particular PNG. `HEART_MIN_VALUE` floors the brightness the tint is scaled by, because green (v 0.68) is the one skin dark enough to smudge at 17px.

**The recovery is three separate things and they are deliberately not on one timer.** `INVULN_DURATION` (2.2s) is how long traffic passes through, and it has to outlast the wall of cars the player was already buried in when they hit — otherwise the second life goes to the car immediately behind the first. `INVULN_SLOW_DURATION` (0.95s) is the shorter knocked-down-to-a-crawl window, applied in `current_speed()` next to boost and tank recoil rather than to `elapsed`, so a crash costs distance without rewinding the difficulty ramp. And the blink's *trough* climbs from `INVULN_ALPHA_LOW` to `INVULN_ALPHA_LOW_END` across the window, so it fades out rather than stopping dead — possibly on the transparent half of a cycle, which would leave a ghost car for a frame.

**The vehicle that lands a hit is destroyed.** Without it, a player who is now untouchable has a car driving straight through them for the next second, which reads as the invulnerability being a bug. It goes through the existing `_destroy_vehicle()` — same burst as a crushed or shelled car — so the collision keeps looking like a collision. On the *last* life both fire: the vehicle's burst and the player's own, which is the one crash that should look bigger than the others.

**Verified headlessly, in the one way that was worth doing.** A throwaway probe drove real collisions into a live board and read back the state: lives 3→2→1→0, hits inside the window ignored (three of seven), `current_speed()` at 0.32x on the frame of impact and back to 1.00x by the next hit, `alive`/`active` false only at zero, pips built at z -2 with a blue car producing a blue pip. Geometry was checked separately by compositing the real road tile, the real car sprite and the real pip at their true world sizes. Neither of those judges feel, which is the whole of what is left.

### 2026-08-30, session U: the dash that was fine one press in six, and the chord that removed the question

"fix the dash system in the pile up game mode", with no symptom attached. The dash's own probe passed — `DashProbe` has reported `OK: a dash covers DASH_CELLS at 2x the follow speed, with a trail` since session S — so the first job was to find out what a passing probe was not looking at.

**`DashProbe` measures the dash's intent, not the dash.** It calls `_press_dash()` and samples `dash_active`, `dash_ghost_timer` and the constant that *would* be used, all on the same frame, and never lets `_update_piloting()` run. Everything that happens to a dash after the button goes down — the follow that actually moves the brick, the hold-repeat that runs before it in the same frame, the collision refusal — is structurally invisible to it. That is the third time in this mode a probe has been reporting a clean bill of health on a code path it does not exercise (§5 session S sixth pass, §5 session T), and it is the same lesson each time.

`DashFeelProbe` was written to close it: real `InputEventKey`s through `Input.parse_input_event()`, so `_unhandled_input`, `Input.is_physical_key_pressed` and the whole physics step run exactly as they do under hands, with the brick's per-frame lateral displacement recorded. Three defects came out, none of which is visible in the source.

**1. The hold-repeat cancelled dashes in flight, and one press in six had no dash in it at all.** `_update_hold_repeat()` cleared `dash_active` on every repeat tick, so that a repeat step would not inherit the dash's speed — reasonable in isolation. But the repeat runs *before* the follow in the same frame, a dash needs about two frames at 60Hz, and a tick lands every five. Where in that tick the button happens to fall is not something a player controls. Measured across the six phases of one tick, on the old code:

```
  dash, held, repeat phase 0    1.50 cells   peak 1400 px/s   0.61 cells above the ordinary follow
  dash, held, repeat phase 1    1.50 cells   peak  620 px/s   0.00 cells above the ordinary follow
  dash, held, repeat phase 5    1.00 cells   peak  620 px/s   0.61 cells above the ordinary follow
```

Phase 1 is the whole mechanic gone: peak speed identical to simply holding the key, distance identical to simply holding the key. §7's invariant says it plainly — the dash's distance is *deliberately* the same as ordinary steering, so **speed and trail are the entire difference** — and here the speed was intermittently absent. Half the phases were degraded, one completely. From the player's side that is a button that works, then doesn't, then does, for no reason they can see, which is a worse experience than one that never works: an input you cannot form a model of is one you stop using.

The fix gives the dash its own destination. `dash_target_x` is set to the commanded position at the moment of the press, and the fast follow chases *that* rather than `aim_x`, ending when the brick arrives. A repeat tick can now pile another half cell onto `aim_x` without either cancelling the dash or being dragged along at dash speed — which is the thing the cancel was there to prevent, achieved without costing the dash its fast frames. `_update_hold_repeat()` no longer touches `dash_active` at all.

**2. A dash with no direction held did nothing whatsoever, and the first fix for it was the wrong shape.** The direction was remembered for `DASH_DIR_GRACE` (0.45s) after a steer press. Past that the button was inert: 0.00 cells, no trail, no feedback of any kind. Steer, look at the tower for a second, press dash — nothing. §9 had this listed as an open question ("untested against real hands"); it is not a close call. **A dash that produces nothing is exactly how this mechanic's first version was reported** — "i cant dash" (§5 session S), when it was in fact moving the brick correctly the whole time.

The first attempt was to make `last_dir` last the whole turn, so the button always had *some* direction to go on. That trades silence for guessing — better, but still bad — and the user named the right answer instead: *"make it so that i can choose the direction, when i hold down w and press d i should dash to the right"*.

**The dash is now a chord, and either key may be the one held.** Hold a direction and press dash, or hold dash and press a direction; both dash exactly one cell that way. This is strictly better than either previous answer because it removes the question rather than answering it: the dash key alone has no direction because **it is not a dash yet** — it is the first half of a gesture, and the direction key that follows completes it. Nothing is guessed and nothing is swallowed. `last_dir` and `DASH_DIR_GRACE` are both gone.

The general point is worth keeping, because this one input has now produced it twice: **when an input genuinely has no good answer, the fix is usually to stop asking the question rather than to pick the least-bad answer.** "Guess from the last key pressed" and "do nothing at all" are both attempts to resolve an ambiguity that the chord simply does not have.

Which order a player reaches for is not predictable — it depends on where the brick already is and which way the hand was going — so `DashFeelProbe` asserts the two orders are worth the same and fails if they come apart. With the chord's branch stubbed out it reports `the chord is worth 1.00 cells one way round and 0.00 the other`.

**The HUD line for it had to be measured rather than written.** Spelled out, "W + A / D   dash a whole block" is 215px for P1 and "Up + Left / Right   dash a whole block" is 266px for P2, against a 196px column at font 15 — `draw_string` does not trim, so both would have run out of the panel and over the playfield. `_controls_text()` reads `%s + a direction   a block` instead, whose widest player measures 178px and which pairs with `half a block` on the line above.

**3. A dash hard against the aim bound armed the effect for a move that never happened.** `_press_dash()` set the ghost and `dash_active` before `_command_move()` clamped, so a dash at the edge left the fast follow armed with nowhere to go. The afterimage self-healed (`_draw_dash_ghost()` returns when the brick has not travelled a pixel), which is why nothing showed — but the state was wrong, and a state that is wrong and invisible is the shape of every bug in this file. It now checks whether the command actually changed and returns if it did not.

Also: a steer press in the opposite direction now ends a dash in flight rather than letting it finish first, and a dead `limit` local in `_command_move()` — computed, never used, duplicated correctly in `_command_to()` a few lines below — is gone.

**The probe was shown to fail before it was trusted**, three separate ways: against the pre-fix code it names the cancelled dash and the inert button, and against a build with the chord's new branch stubbed out it names the two orders disagreeing. Against the shipped code every dash case carries a full cell above the ordinary follow in every repeat phase, and each half of the chord pressed alone moves nothing. That order matters here more than usual, because the thing being asserted is a *comparison* between behaviours, and the previous probe on this exact mechanic passed throughout both defects.

**Nothing else moved.** `StallProbe` 0 mid-air stalls over 61 turns, `LandingProbe` 0.27px mean / 0.75px worst against a 1.75px descent step with 0 wedged, `TowerProbe` 12/12 matches at both spreads with 20.8 and 18.3 turns per match and zero tunnelling, `PaceProbe` 4.97s per turn — every one identical to session T's numbers, as expected, since none of those probes press a key.

**Second pass: a round-start countdown, in both modes, and the frame it moved.**

The user supplied `sayım.png` — 3, 2, 1 and GO! as pixel art — and asked for a countdown at the start of both modes.

**The sheet needed almost none of what the last one did.** `extract_blocks.py` exists mostly to remove a baked-in checkerboard by flood fill, because a threshold cannot tell a block's black outline from the dark it sits on. This sheet ships a **real alpha channel**: measured, alpha is bimodal at ~0 and ~255, and the glyphs' black outlines are opaque (254) while the black behind them is 0. So every cut is made on alpha alone. Two things still had to be got right, and both were found by looking rather than by reasoning:

- **Each crop is masked to its own connected components.** A box centred on a numeral and wide enough for the widest digit's burst marks also reaches ~20px into the *next* digit's leftmost spark — the digits are 36px apart and their bursts are not. The first extraction shipped a sliver of the 2 inside the 1.
- **The digits are centred on the numeral, not on their own bounding box.** The burst marks are not symmetric about the numeral (the 1's bounding box centre sits 22px left of the 1), so a bounding-box crop makes the number jump sideways as the count ticks.

`extract_countdown.py` now asserts that no art touches a crop's border, which is how the first, too-tight padding was caught rather than shipped.

**The countdown node holds no game state, and that is the whole reason one node can serve two modes that share nothing else.** It draws and emits `finished`. Freezing is the caller's job, and each mode already had the means: Don't Crash leaves its boards' `active` false (`PlayerBoard._process` and `_unhandled_input` both gate on it, so the board does not scroll, spawn, steer or read a key — and a bot driving that board is inside the same gate, so it stops too), and Pile Up sits in a new `countdown` state that `_physics_process`'s match simply has no branch for. Neither mode learned a new word for "paused".

**The clock had to be the caller's too, and the probes are what said so.** With the node ticking itself in `_process`, Pile Up's first brick was created from an idle frame rather than the physics step every other part of a turn happens on. Nothing looks wrong, and the assertions all still passed — but `TowerProbe` moved from 20.8 turns per match to 22.9, and `PaceProbe` from 4.97s per turn to 5.53s, deterministically. **A one-frame shift at turn one diverges every tower after it**, which is ordinary chaos in a rigid-body stack and not a regression, but it makes every historical number in this document unreproducible for no benefit. `advance(delta)` is now called from Main's `_process` and from TowerMode's `_physics_process` — each mode's countdown on each mode's own clock, which is also just the correct answer.

**The residual shift is sample variation, and that was checked rather than asserted.** Re-running `TowerProbe` across four different seed bases gives 20.3 / 20.7 / 20.9 / 22.9 turns per match, and `PaceProbe` across four seeds gives 4.95 / 5.06 / 5.07 / 5.53s per turn. The old and new figures both sit inside those spreads, and the per-phase numbers barely moved — what changed is which towers get built, not how long anything takes. **A deterministic metric is not automatically a precise one**, and this is the first time in this project that distinction has mattered.

**Seen, not just measured.** Both modes were screenshotted with the real renderer at the 3, the 1, GO! and after the release. At its widest — GO! at the peak of its pop — the overlay spans x[282, 1218] against Pile Up's HUD columns, which end at 252 and start at 1248, so it clears them by 30px on each side without the layout having to be moved.

### 2026-08-28, session T: the brick that stops in mid-air, and the pixel that stopped it

First report from actual play of Pile Up: "bricks stops sometimes when they cross a line and i need to move right or left to contunie". A brick descends, halts in clear air part way down, and only starts falling again when the player steers sideways.

**The cause is one number, and it is zero.** Godot's `intersect_shape` counts two *exactly touching* rectangles as a hit — measured directly: a 0.00px gap intersects, a 0.05px gap does not. And exact touching is not a freak case in this mode, it is the ordinary one: every command is a multiple of half a cell from x=0, so a descending brick's faces line up precisely with the faces of the bricks already stacked. Settling makes it worse rather than better — a landed brick picks up a thousandth of a radian of lean, which pokes a corner a fraction of a pixel across the line into the column beside it. The case that was caught:

```
active O brick   box x[19.00, 95.00]   bottom y = -379.82
landed T brick   box x[-94.87, 19.23]  top    y = -379.99
```

A **0.23px** corner overlap refused the brick its next step down. `_supported()` was right that nothing was holding it up (its feet are inset 6px precisely so a flank cannot count as a floor), so the brick kept its steering and hung there — for the full six seconds of `WEDGE_GRACE` when the player did not touch anything, which is the "session S sixth pass" backstop doing exactly what it was designed to do to a situation that should never have arisen.

**Why every existing probe passed it.** `TowerProbe` and `LandingProbe` set the aim with `randf()`. A continuous random position essentially never reproduces an exact face-to-face alignment; a player on a half-cell lattice reproduces it constantly. So the probes were exercising a geometry the game does not actually produce. `LandingProbe` had a second blind spot on top of that: it only looks at the frame control *ends*, and a brick that hangs half way down and then carries on makes a perfectly good landing afterwards. The bug was invisible to it by construction.

**The fix: a move is refused only if it would put the brick *meaningfully* inside something, never for merely grazing it.** `TowerMode.QUERY_SKIN` trims the query boxes by 3px, and — this is the part that matters — trims them **across the direction of travel and never along it**. Descending, the brick ignores what it grazes to its sides but nothing it is coming down on, so a landing is still detected at the exact pixel of contact: `LandingProbe`'s mean gap under a brick when control ends is unchanged at 0.29px, worst 0.78px, exactly as before the change.

`QUERY_SKIN` is half `TowerPiece.FOOT_INSET` **on purpose, and the two must stay in step**. The feet that decide support are inset by half of FOOT_INSET per side, so an overlap deep enough to refuse a descent is also deep enough for the feet to find. That identity is what makes "blocked on the way down" and "something is underneath" the same event, rather than two events with a band of geometry in between for a brick to hang in — which is the general shape of this bug, and it would come back if either number moved alone.

What the tolerance costs, measured with the solver's own narrow phase rather than with bounding boxes (an AABB reports tens of pixels of overlap for a brick part way through a quarter turn, all of it imaginary): a worst case of **1.4px** of brick-into-brick overlap at landing and 2.7px while stepping sideways along the stack's surface, against a 38px cell. Both are inside the skin by construction and the solver clears them on release. The sideways figure is the more useful one to know about: it is what lets a brick slide along the top of the tower when its underside is level with the surface, which used to be refused by the same zero-depth contact.

**`StallProbe`** (`scripts/dev/StallProbe.gd`) was written to catch this and kept to stop it coming back. Two things make it different from the probes that missed it, and both were necessary:

- It **steers through `_press_steer()`**, so the commanded position is only ever a multiple of half a cell — the lattice is the precondition for the bug, so a probe that aims at real numbers is testing a different game.
- It measures the **descent**, not the landing: any frame where the brick's y does not advance, with clear air under it, counted from the brick's own geometry rather than by asking `_supported()`.

Shown to fail before it was trusted (§8's rule): with the tolerance removed it reports 2 of 61 turns hanging in mid-air, worst 6.00s over 5 cells of air. With it, zero. It also tops up `lives` each turn — the descent is what it measures, and a 2-player match eliminates everyone at about thirteen turns, well before the tower has flanks worth falling past.

**One more thing this repaired for free.** `WEDGE_GRACE` should now be genuinely unreachable rather than merely rare: after the fix, a downward move can only be refused by something overlapping deeply enough for the feet to find it, so "blocked but unsupported" has no geometry left to live in. It stays as the backstop.

**Second pass, same day: new brick art (`yenib.png`), and rotating the arrangement instead of the art.**

The user replaced the sheet — the seven pieces are now clusters of *self-contained square blocks* (a wheel, a battery, a radiator, a spoiler) rather than one continuous drawing of a car spread across the cells, which is what `bloklar.png` was. Instruction was explicit: keep the current brick sizes, change only the skin. So `GameSettings.TETROMINOES`' `cols`/`rows`/`boxes` are untouched and the art is fitted to them.

Three of the sheet's clusters are drawn in a different orientation than the game's own shapes: the T's stem points up where the game's points down, the J's lone block sits over the left end rather than the right, and the L is drawn 3 wide by 2 tall against the game's 2 by 3. **The obvious fix — rotate or flip the extracted image — is wrong, because these blocks have an up.** A quarter turn to make the L fit puts a wheel on its side, hangs a headlight sideways and stands a spoiler on end. What the new sheet's modularity buys is the alternative: cut the cells apart and place them into the footprint the game already defines, each one still upright. The arrangement rotates; the art does not. The rule the mapping follows is that **the run of three stays a run of three and the lone block stays the lone block**, so an L's horizontal bar becomes its vertical bar in the same reading order.

The extraction itself was easier than the old sheet's: the background is a flattened alpha checkerboard (~248/~241 neutral greys) with no drop shadow at all, so the same border-flood-fill by reachability clears it in one pass over the whole image, and the piece labels printed under each cluster never come into it because every cut is made inside a piece's own bounding box. The threshold takes the antialiased edge pixels with the background (`hi > 150`, not `> 200`) so no pale fringe survives around a block. Cell size is inconsistent across clusters exactly as before — 146px wide for the I against 127 for the S, and every block drawn 10-30% wider than tall — and is normalised away per cell.

Two HUD accent colours were nudged to match the art they now sit directly under in the NEXT BRICK panel: I from `Color(0.30, 0.66, 0.80)` to `(0.30, 0.79, 0.80)` (the new art is teal, not cyan-blue) and T from `(0.62, 0.40, 0.80)` to `(0.70, 0.40, 0.80)`. Measured rather than eyeballed — every other piece's table colour was already within 8° of hue of its new art and was left alone.

**What checks this.** A script comparison of each sprite's occupied cells against `GameSettings.TETROMINOES`' own `boxes`, parsed out of the source file rather than copied: all seven match, at exactly `cols*100 x rows*100` px. That is worth keeping in mind as the failure mode here — a mis-laid cell would put art where there is no collision and collision where there is no art, which no compile check and none of the probes can see, because the physics does not read the texture at all. `TowerProbe` at spread 0.3 returns byte-identical numbers to before the reskin (23.5 turns per match, 4 settle timeouts over 282 turns), which is the confirmation that nothing but pixels changed.

**Third pass: "the time it takes for the other brick to fall and change the player is too long".**

`PaceProbe` was written before anything was changed, because "the hand-off is too long" is a complaint about a *total*, and a total cannot be tuned. The split:

```
descent (piloting)   : 3.84 s   of which 2.51 s before the brick is within two cells of anything
settling             : 2.62 s
pause before next    : 1.20 s
whole turn           : 7.66 s   hand-off (landing -> next brick in reach): 6.33 s
```

So about 1.3 seconds of a 7.7-second turn had the brick anywhere near the tower. Three separate costs wearing one symptom, and they needed three different answers.

**The descent was the easy one and the doc had already called it** (§9 said `DESCEND_SPEED` was "the knob before anything else" if turns dragged). `DESCEND_SPEED` 58 → 105, and — wrongly — `SPAWN_CLEARANCE` 7 → 5.5 cells with it, on the reasoning that height and speed are the same second approached from two directions.

**They are not, and that is the lesson of this pass.** The user played it and reported it in one line: bricks start too low. **Speed is the pace knob; height is a readability one.** The distance above the stack is how much of the fall a player can see coming and plan against — where the brick sits relative to the tower, whether the rotation is right, how far across it still has to travel — so cutting it does not make the turn feel faster, it makes the brick feel like it appears already half way down. The height went back to 7 cells and the speed stayed at 105. The descent still costs 2.39s against the original 3.84s, and **every second of that saving came from the half of the change that was actually about time** — which is the tell that the other half was never a pace fix at all.

**The pause split in two.** `RESOLVE_PAUSE` was one number doing two jobs: giving a "P2 DROPPED 2 BRICKS" message time to be read, and padding turns where nothing happened at all and there was nothing to read. Now `RESOLVE_PAUSE_EVENT` (1.1) and `RESOLVE_PAUSE_QUIET` (0.35), chosen by whether anything actually fell — most turns are the quiet kind.

**The settle was the interesting one, and most of it is not padding.** Two measurements decided this:

- The tower drops below `SETTLE_LINEAR` within 0.36s of a landing, but 72% of settling frames fail the rest test, with tumbles up to 5.3 rad/s. So the tower really is still moving — loosening `SETTLE_LINEAR`/`SETTLE_ANGULAR` would resolve turns on towers that are still falling and bill the collapse to the next player, which is the one thing the whole turn structure exists to prevent. They were left alone. `SETTLE_HOLD` is a different quantity — the quiet required *after* motion stops — and half a second of it was padding on a test the tower passes in a third of that. 0.5 → 0.25.
- Splitting settle time by outcome found where it actually goes: **1.25s when nothing fell, 3.74s when something did.** The difference is a brick tumbling the full height of the tower to reach `LOST_Y`.

**The tempting fix for that, and the measurement that killed it.** Session S's own lesson (score a brick when it is lost, free it later) suggests going further: a brick that has slid off the tower and is falling clear of the platform's footprint is already decided, so why wait for it to cross a plane below the platform? A throwaway probe asked whether such a brick ever touches the tower again. **579 of 689 did**, and dooming them early would have saved only 0.72s on average. Debris does not fall away from a tower, it tumbles down alongside it and keeps hitting it — which is exactly why the turn has to wait. Recorded in §8: this is the second time in this mode that "the brick is obviously gone" turned out to be a claim about a trajectory nobody had measured.

Result, same probe, with the spawn height restored:

```
descent              : 2.39 s   of which 1.45 s before the brick is near anything
settling             : 1.85 s   (3.01 s when a brick fell, 0.70 s when none did)
pause before next    : 0.72 s   (0.35 quiet / 1.10 after a life lost)
whole turn           : 4.97 s   hand-off: 4.03 s
quiet turn end to end: 3.44 s   (was ~6.3 s)
```

**And one change that is about seam rather than speed.** The turn banner read `settling...` through every hand-off — a word the player cannot act on, captioning something already visible on screen, and making each gap read as the game stopping. It now names the player the baton is passing to (`P3 — GET READY`, in their own colour), so the same seconds read as a hand-off instead of a pause. `TowerHUD` gained `next_slot` for it.

Balance is intact: `TowerProbe` still terminates 12/12 at both spreads with zero tunnelling, and settle timeouts went from 4 in 282 turns to **0 in 279** (a shorter hold is easier to satisfy before the 9s backstop). Careful play still outbuilds sloppy, 23.2 turns per match against 20.4, though the margin over twelve seeded matches is narrower than the 23.5-vs-18.8 measured before this pass and that gap is inside the run-to-run spread rather than a demonstrated effect. `LandingProbe`'s gap under a brick when control ends scaled exactly with the bigger descent step, as it should — 0.65px mean and 1.50px worst against a 1.75px step, still within one step of contact.

**Fourth pass: a little more room to the sides.** `AIM_BOUND_CELLS` 2.0 → 2.5 — half a cell further out each way, with `PLATFORM_CELLS` deliberately untouched, so the platform is exactly the same size and there is simply more air either side of it that a brick may be steered over. The shaded play column and the height guides widen with it for free, since both are drawn from that constant rather than from their own numbers.

Two things made this a measurement rather than a one-character edit. The constant has to stay a multiple of 0.5 or the aim clamp stops landing on the half-cell lattice (the limit is `2.5 + AIM_BOUND_CELLS − the brick's half-width in cells`, and half-widths are whole numbers of half cells). And §9 lists it as one of the mode's two *difficulty* knobs, so widening it is a balance change: `TowerProbe` aims as a fraction of the legal range, which conveniently models a player who spends all of the new reach, and it puts the cost at 23.3 → 20.8 turns per match at spread 0.3 and 19.7 → 18.3 at spread 1.0. A full cell (3.0) was measured too and costs about the same at careful aim but noticeably more when blind (19.7 → 16.8), so if the extra room turns out to be too little, that is the next notch and it is not free.

### 2026-08-25, session S: Pile Up — a second mode, and the number that made it work

The user asked for a Tricky-Towers-style survival mode using car models as bricks, with one difference from the original: **everyone builds the same tower**, and whoever drops a brick loses a life. Art supplied as `bloklar.png`, the seven tetrominoes drawn as clusters of top-down cars.

**Turn-based, and that is a design consequence rather than a simplification.** The fault rule only has an answer if exactly one player can be responsible for the tower's state at a time; with everyone dropping onto one shared stack at once, a collapse has no author. So turns are what make "the one who drops a brick loses a life" well-defined at all. `TURN_TIME_LIMIT` (14s, auto-drops) keeps them from dragging. Fault is always the active player's, including for bricks *other* people placed that this drop knocked off — that is the tension the shared tower exists to create.

**Extracting the sheet.** Two problems, both instructive:

- The sheet sits on flat gray (~73,73,74) with a drop shadow (~42,42,42) offset down-right. Neither can be separated from the cars' own near-black outlines by brightness, because the cars' windows and tyres live in the same value band as the shadow. What *does* separate them is reachability: background and shadow form one region touching the image border, while every dark pixel inside a car is walled in by its own outline. Border flood fill — the same technique §7 already records for the tank art's baked-in checkerboard.
- The sheet is not internally consistent about cell size: every piece is drawn 4-14% taller than it is wide, and the I piece's cars are 113px tall against the L piece's 105. Same class of problem as the tank sheet in session G. Rather than carry a per-piece fudge factor in the game, `extract_blocks.py` normalises each piece to an exact `cols x rows` grid of square cells at export time, so `TowerPiece` scales any brick by one number (`cell / 100`) and cell-unit collision rectangles are simply correct.

**The finding that mattered, and the harness that found it.** `TowerProbe` plays whole matches headlessly at seeded random aim positions. Its first useful result was a *comparison*: dropping bricks dead centre on the platform knocked the tower apart at the same rate as dropping them deliberately terribly (14.7 bricks lost per match vs 13.1), and no tower ever got past 10 bricks. That is not a hard mode, that is a mode that does not work — careful play has to be rewarded or there is no game.

The cause was drop speed. A brick released a fixed distance above the stack arrives at whatever speed that height dictates — about 670px/s, fifteen cell-widths a second. At that speed a brick does not stack, it demolishes. Capping terminal velocity (`TowerPiece.MAX_FALL_SPEED`, 340) took towers from a ceiling of 10 bricks to 11-15, and dropped falls-off-a-1-brick-tower to zero. It is also honest physics rather than a fudge — it is air resistance. **Treat it as a feel constant: raising it makes every landing more violent no matter how well aimed, which is not the same axis as making the mode harder.**

**A false positive worth remembering.** The probe's first tunnelling check was "is the brick below the slab while horizontally inside its footprint", which reported 1 brick in 189 turns passing through the platform. It was wrong: a brick that legitimately falls off the edge can be knocked back inward by the next one on its way down and land in exactly that state. The sound test is *how far out the brick ever got* — the slab is solid edge to edge, so reaching the void below it requires taking the centre past the edge first. With that test, tunnelling is zero across every run. Noted in §8 because the failure mode is general: a "was it ever here" test and a "how did it get here" test are not interchangeable, and the first one quietly manufactures bugs.

**Two layout problems fixed by arithmetic before anything was rendered.** With the HUD as a strip across the top, a vertical I piece's top edge landed at screen y=74, underneath the player cards. And a 230px-wide tower on a 1500px screen left ~600px of dead background down each side. Both were fixed at once by moving the HUD into the side columns the tower was never going to use: the dead space carries something worth reading, and the entire top of the screen went back to being drop headroom (`SPAWN_CLEARANCE` 3.6 → 4.5 cells). `CELL` was also raised 46 → 58, chosen off the *vertical* budget — width is never the constraint here — which also lands the 100px sheet cells at a 1.7x downscale instead of 2.2x.

**Second pass, same day, after the user compared it to a Tricky Towers screenshot.** Five changes, three of them structural:

- **Smaller bricks, wider view.** `CELL` 58 → 38. Chosen off the vertical budget as before, but with the right target this time: at 58 only five and a half cells of tower were visible below the brick in play, so the tower kept scrolling out from under itself and never read as tall. At 38 about eleven cells of tower sit below the brick and twenty-one fit on screen.
- **The brick descends by itself; there is no drop button.** It falls slowly from the moment it appears and the turn ends when it touches something; `down` (a new per-player binding, see below) speeds it up. This deleted `TURN_TIME_LIMIT` and its countdown outright — the descent bounds the turn on its own, so there is nothing left to stall.
- **Sideways movement became discrete**: half a cell per press, a whole cell on a double-tap, with hold-to-repeat. Worth noting the lattice survives the clamp: the aim bound works out to (2.5 + `AIM_BOUND_CELLS` − half the brick's width in cells) cells, and a brick's half-width is always a whole number of half cells, so clamping lands *on* the lattice rather than between two steps.
- **Contact moved from the solver to shape queries.** The brick was already frozen and outside the collision world while held; now every move it makes — sideways, rotational, downward — is tested with `intersect_shape` before it is applied, and a refused downward move is the landing. This is what makes an exact half-cell step safe: a brick that was genuinely falling could not be stepped sideways without risking ending up inside the tower, but a brick whose every move is permission-checked can be put anywhere that is empty. It also made landings gentle for free — the brick is handed to physics at the instant of contact with no velocity — which retired `MAX_FALL_SPEED`'s original job (see below).
- **`sprites/bg/tower_backdrop.png`** (the user's `arka.png`) behind everything, on its own CanvasLayer, scrolling at 0.28 of the camera. Screen-space rather than world-space deliberately: the camera pans up without limit, so world-space art would be left behind within a few bricks. Above the art's own top edge the sky continues in the image's own sampled sky colour.

**What the second pass broke, and what it taught.** The gentle landings did what they were meant to — towers got much taller — and that immediately exposed a bug the short towers had been hiding: **the settle timeout started firing on 6.5% of turns, twelve times in a single measured match.** It was not jitter. A brick shrugged off a twenty-cell tower has to fall about 900px to reach the kill plane, roughly six seconds, and a turn ends when *everything* is at rest — so every collapse sat there burning the 9-second timeout with the player watching "settling...".

The fix was to notice that **losing a brick and removing a brick are two different moments**, and that conflating them is what cost the six seconds. A brick is now scored as fallen the instant it passes below the underside of the slab (`LOST_Y` — there is nothing under the slab, so it can never rejoin the tower) and freed much later, off screen (`DESPAWN_Y`). Debris is excluded from the at-rest test from the moment it is counted. Settle timeouts went from 16 in 247 turns to **0 in 255**. The general lesson is the one this project keeps relearning: *when did this become true* and *when may we stop tracking it* are separate questions, and answering the first with the second is what makes a turn wait on something nobody is watching.

The same change also fixed a bug nothing had reported yet: a brick steered clean past the platform edge had nothing to land on, so under the descent model it would have descended forever and hung the turn. `_update_piloting` now treats passing `LOST_Y` as a landing.

**A new binding.** Soft drop needed a key every player has, and `confirm` is the wrong shape for "down" (P2's is the Up arrow). `PLAYER_CONFIGS` gained `down`: S, Down, G, K — each the key physically below that player's confirm and between their two steering keys, so "down" means down on the keyboard as well as in the game. Don't Crash does not read it.

**Third pass, after the user's first screenshot.** Two complaints, one cause: the tower stood on a dark slab on two thin legs running off the bottom of the screen, and it sat too high. Both are the same mistake — the platform was designed as an abstract game object against a flat dark background, and once real scenery went behind it, it read as scaffolding parked in front of a painting.

- **The platform became a rock outcrop growing out of the ground.** Grass-capped, flaring as it descends, with its base buried in a near-ground band that `TowerGround` draws across the frame. The first attempt painted it in flat colours sampled from the art's cliffs, and that was still wrong for a reason worth recording: *everything else on screen is textured pixel art, so a smooth trapezoid is the one object with no detail, and flatness is what reads as "prop"*. The fix was to cut the outcrop's body out of the backdrop's own earth band — the stone layer under its near grass — drawn as horizontal slices that narrow with the taper (a texture can only be drawn into a rect, so the taper has to be made of rects). It is now literally the same stone as the retaining wall at the bottom of the picture. This is §7's "derive new art from the existing art" rule applied to something drawn rather than to a sprite.

- **`TowerGround`, a foreground layer.** It sits after `PiecesContainer` in the scene, so it draws *over* the bricks: one knocked off the tower slides down behind the grass and is gone, which is both how it should read and how the despawn gets hidden (`DESPAWN_Y` came down from 950 to 600 as a result). Unlike the backdrop it moves at the world's exact rate — it is where the tower actually stands, so any parallax on it would slide the outcrop out of its own ground. The two are cut from one image and aligned at the start of a match, then separate as the tower climbs, which is the parallax doing its job: near ground dropping away faster than far. `TowerBackground` is therefore anchored by its *ground line* (`TowerGround.GROUND_LINE_PX`, a measured row, not a guess) rather than by its bottom edge.

- **The camera got a second framing.** One fraction cannot both sit the platform low on the ground and leave the descending brick room to fall — that conflict is why the platform floated mid-screen. So there are now two shots and the camera takes whichever sits lower: `CAM_GROUND_FRAC` (0.70) is the resting shot, held while the tower is short, and `CAM_STACK_TOP_FRAC` (0.48) is the climbing shot, which takes over automatically at about five bricks.

**Fourth pass: "i cant dash", and the most instructive bug of the session.**

The dash worked. Measured through `TowerMode._press_steer()` directly, a double-tap moved the brick **1.00 cells** and two slow taps moved **1.00 cells** — the detection fired every time, the arithmetic was exactly as designed, and there was nothing whatsoever to feel.

The cause was a decision that looked like care. The dash was specified as "lands exactly one cell from where the gesture started", so the dash tap added the *remaining* half cell on top of the half the first tap had already committed — at the ordinary follow speed. Correct to the letter, and it made the dash produce the same distance at the same pace as simply pressing twice. **A feature whose output is identical to something the player can already do has not been added.**

Worth being precise about why reading the code could never have caught this: both paths were right. There was no wrong branch, no missed reset, no off-by-one. The defect only exists in the *comparison* between two behaviours, and comparisons are exactly what a single code path cannot show you. It is the same shape as the drop-speed bug earlier in this session — there too, the finding was a comparison (careful play scoring the same as terrible play) rather than an observation.

The fix keeps the distance the user asked for and attacks the sameness instead: the dash now commands `dash_origin_x + dir * CELL` (the same place, but said in a way that cannot silently decay into "another half cell"), travels at `DASH_FOLLOW_SPEED` (1400 against 620, so about 27ms for the cell), and draws an afterimage — four fading silhouette copies back along the path, speed lines, and a white rim flash at the landing position. All of it is drawn by `TowerMode._draw()`, which paints before its own children, so the rim flash shows only the half of its stroke that falls outside the brick and reads as an edge light rather than a box on top of the art. `DASH_WINDOW` also went 0.26 → 0.32, because a double-tap nobody can confirm landed is a double-tap people give up on.

`DashProbe` was written to find this and kept to stop it coming back. Its assertion is deliberately not "the dash moves one cell" — that was always true — but "the dash is distinguishable from not dashing".

**Fifth pass: "player looses control of the brick before it touches other bricks", and the dash moved to a button.**

The control complaint was real and had a one-line cause with a three-step diagnosis, all of which is worth keeping.

**Blocked and landed are not the same event.** Descent was decided by a single question — "can the brick be in the space one step lower?" — and that is also answered "no" when the brick has come up against the *flank* of a taller stack. So a brick sliding down beside a tower went limp in mid-air with a visible void beneath it. `TowerPiece.foot_shapes` now asks the second question separately ("is anything holding this brick up?"), and a blocked-but-unsupported brick keeps its steering; `WEDGE_GRACE` (1.5s) only exists so a brick held against a wall forever still resolves.

**Two false measurements came first, and both looked authoritative.** The first probe measured the gap *after* `release()`, by which point physics has moved the brick and it is back in the collision world — so the landing query reported the brick colliding with itself, and blamed the tower for a 42px mean gap that was entirely the probe's own artifact. The second measured the gap under the brick's *lowest point*, which is wrong because J, T, S and Z all decompose into boxes a cell apart in depth: a brick resting on its shallower box legitimately has a cell of air under the deeper one, and the metric called that a failure. **A measurement that disagrees with the code is not automatically evidence about the code.**

**Then the fix's own bug, which the fix hid.** With feet added, 8 of 11 landings still timed out wedged — but their gap was 0.8px, i.e. they were *at* the surface and simply not detecting it. The feet were stored as offsets in the brick's own frame, so a rotated brick probed sideways, and a half-turned one probed the sky. "Underneath" is a question about the world, not about the brick; `_supported()` now sizes and places the feet against the world axes at query time. The tell was in the numbers all along — roughly three quarters failing, against a probe that randomises rotation over four quarter-turns.

**Probe reproducibility.** `TowerMode` picks its bricks with the *global* `randi()`, so seeding a probe's own `RandomNumberGenerator` left the piece sequence free-running. Two runs of the same "seed" reported a 0.45px mean and a 7.52px mean, and there was no way to tell a regression from variance. All three probes now seed the global RNG too.

**The dash is a button.** `confirm` (W / Up / T / I — the one key per player that Pile Up was not using) dashes a whole cell in the direction held, or the last one pressed within `DASH_DIR_GRACE`. The double-tap is gone: a double-tap and two deliberate half-steps are the same keypresses, so the game had to infer intent from timing, and a separate key cannot be misread.

Settle timeouts went back to **0 over 507 turns** across both spreads once the feet worked — the broken version had been parking most bricks in a 1.5s wedge, which distorted the towers it built.

**Sixth pass: the rule stated plainly — "player should have the control until bricks touches another brick, not before".**

The fifth pass fixed the flank case but left a clock on it: a wedged brick kept its steering for `WEDGE_GRACE`, then had it taken away regardless. 1.5s was short enough to fire during ordinary placement, which is the same complaint wearing a different hat. The grace is now **6 seconds and reframed as an anti-deadlock backstop rather than a gameplay rule** — every wedged position has an exit (the brick got there by descending, so it can move back the way it came), so reaching six seconds means someone is leaning on a direction into a wall on purpose.

**The probe could not see any of this, and that was its own bug.** It set the aim once per brick and never touched it again, so it never pressed a brick against a flank and never reached the wedge path at all — it had been reporting a clean bill of health on a code path it did not exercise. Half its turns are now "pushers" that pin the command hard to one side for the whole descent.

That immediately produced three turns ending with the brick touching nothing — which turned out to be **correct** behaviour the assertion had no category for: a brick shoved clean off the platform edge falls into open sky, and there is nothing left for it ever to touch. So the probe now classifies four distinct endings (supported / flank-before-backstop / backstop / steered-off-the-platform) and fails only on the second. Two rounds of "the measurement disagrees with the code, and the measurement is wrong" in one session is worth noticing: **a probe that has never been shown to fail is not evidence of anything.**

**Not played.** Everything above is headless measurement and arithmetic. See §9 for what that cannot tell us.

### 2026-08-24, session R: the coach was never a bus

Reported in full: `bus_coach.png` renders ~15% too short, found by `FleetProbe` and written up as a known bug at the end of session Q. ### 2026-08-24, session Q: six new sheets, and what the fleet gained from them

Asked for, in full: **"change the models accordingly. i uploaded new pngs to documents. suv.png pickup.png kamyon.png spor.png eşyalı.png motorlu.png"**.

Four of the six sheets map onto kinds that already existed (`suv` → suv, `pickup` → pickup, `kamyon` → truck, `motorlu` → motorcycle). **Two had no counterpart, and adding kinds was the only reading that used them**: `spor.png` is five sports cars and `eşyalı.png` is five pickups towing something (boat / camper / ATV flatbed / cargo box / jet-ski). Folding either into an existing kind was not possible even in principle — `height_frac` is per-kind and `Car._rebuild()` scales each axis independently, so a 3.74-aspect trailer inside the 2.23-aspect `pickup` entry would be squashed by 40%. `TRAFFIC_KINDS` went from 7 kinds / 38 textures to **9 kinds / 57 textures**.

Its alpha turned out to be sharply bimodal (977k pixels at 0, 441k at ≥250, only ~154k in between), so one threshold separates bike from glow cleanly. **Check the mode, then look at the histogram — "has alpha" is not the same as "alpha means what you want".**

**Flood-filling from the border is necessary but not sufficient.** §7's rule protects white bodywork, and it did — `pickup_white` and `truck_white` came through intact. What it does *not* reach is background enclosed by the subject: the X-brace over a pickup bed, a trailer's A-frame hitch, the gap between a semi's cab and its trailer. Those stayed opaque as leftover checkerboard until a second flood fill was run per-vehicle from its own crop border. Verified by compositing every sprite over magenta, which is the only way this shows up — over the road texture, leftover light-gray reads as a highlight.

**The style check §7 demands was run before anything was installed, and it passed.** Measured against the kept fleet (sedans/vans/buses, value 0.21-0.67, dark 11-58%), the new sprites land at value 0.13-0.63 — the same range, with the low end being black SUVs and a black cargo trailer, i.e. palette rather than technique. Rendered side by side at true in-game scale on the actual road tile (the §8 rule), they sit with the existing fleet rather than on top of it. This is the taxi lesson from session I applied *before* shipping instead of after being told.

**Pixel density was matched deliberately, not incidentally.** The fleet runs 78-115px wide for a ~33px on-road car; the new sprites were resized to 84-100px (44px for motorcycles) so nothing carries detail the rest of the fleet doesn't. This is the other half of the session-I taxi failure.

**Three things worth keeping:**

- **`height_frac` was measured, not guessed, and it moved a lot for pickups.** The new pickups are 2.23-aspect crew cabs against the old entry's 1.52 — so a pickup went from 50px to 74px of road, and is now a real obstacle rather than a slightly-long sedan. SUVs went 1.79 → 1.98. Both are the art's own proportions; the alternative was stretching it.
- **The two new kinds were given opposite ends of the speed band on purpose.** Trailers sit at `0.78-0.95` (the slowest-driving kind in the table, a rolling roadblock you must commit to going around); sports cars at `0.35-0.60`, down with the motorcycles, so they nearly keep pace and hang alongside you instead of sweeping past. Both stay clear of the §7 `< 1.0` invariant.
- **Weights were rebalanced to total exactly 100** (sedan 30, suv 16, pickup 12, van 11, sports 9, truck 7, trailer 5, bus 5, moto 5), so every weight reads directly as a percentage of traffic and adding a kind forces an explicit decision about what it displaces instead of quietly diluting everything.

**The harness caught nothing this time, and was still worth writing** — session P's `NITRO_STAGE_FRAMES` compiled perfectly clean against both scenes and then threw on every frame at runtime, and a clean `godot --headless --quit` would have said exactly as little here. `FleetProbe` force-spawns 4000 vehicles through `PlayerBoard._spawn_obstacle()` itself: all 9 kinds appear, the observed distribution matches the weights (30.1/16.6/11.9/10.7/7.9/6.6/5.0/5.6/5.7% against 30/16/12/11/9/7/5/5/5), **all 57 textures are reached**, nothing spawns without art or with the placeholder polygon still visible, and every `speed_mult` is below 1.0.

**It force-spawns rather than watching a live round for a measured reason.** The first version instantiated `Main.tscn` and watched a board for 100 simulated seconds, and saw **10 cars** — an unattended board crashes within seconds and `_process` early-returns on `not alive`, so spawning stops. Anything that wants a traffic sample from this game has to drive `_spawn_obstacle()` directly or hand the board to a bot; watching a live board silently measures the first four seconds of a round.

Unlike session P's throwaway, this one is **committed**: art gets swapped in this project often (sessions G, I, P, Q), and the probe encodes §7's `speed_mult`/meta/aspect invariants as executable checks rather than prose. It is also what found the pre-existing bus defect, fixed in session R below.

**Then the semis shipped facing the wrong way, and nothing in the pipeline could have known.** Reported as *"semi trucklar ters"*. `kamyon.png` draws its trucks cab-at-the-**bottom**, so one kind silently inverted the convention every other sheet follows — the trailer led and the tractor pushed it up the road. Fixed by rotating the five sprites 180°, which is lossless (`Image.transpose(ROTATE_180)` is a pixel reindex, not a resample; the rotation was verified reversible byte-for-byte before saving).

**The obvious automated check for facing does not work, and that was measured rather than assumed.** "Saturated red pixels cluster at the rear" sounds reliable and isn't: scored over the whole fleet it flags **21 of 59 sprites**, because red/orange/yellow bodywork drowns out its own tail lamps (`suv_red` -0.74, `pickup_red` -0.39) and a correctly-oriented pickup towing a pale trailer scores a perfect **-1.00** (`trailer_boat` — the red is the truck, at the front, exactly where it belongs). A check that noisy trains you to ignore it, so `FleetProbe` deliberately does **not** test orientation. Facing is a look-at-it property; render new art beside a known-good sprite before installing, which is the same contact-sheet step §8 already requires for style.

**Then: *"containers of the semi trucks are too small make them bigger"*, and *"make it also longer"*.** The source art draws the trailer **narrower than the tractor** (142px against a 159px cab body) — backwards from a real semi, where the box is the widest thing on the vehicle below the mirrors. Both fixes were made **at source resolution (192x803) with a single downsample at the end**; widening or stretching the finished 92px sprite would have resampled it twice.

- **Width 142 → 167px**, scaled about the trailer's own centre. The sprite's overall width is set by the mirrors (192px) and is unchanged, so `width_frac` still describes the same footprint — **this part is purely visual and changes no gameplay.**
- **Length +40%, added as nine whole 19-px rib periods spliced into the box's uniform middle, not by stretching.** The trailer is a ribbed container: stretching it coarsens the rib pitch and immediately reads as a scaled-up sprite, while repeating whole periods leaves the pitch, the front face and the rear doors exactly as drawn. The period was measured per sprite by autocorrelation (19px on four of the five, 20 on `truck_green`) rather than eyeballed.
- **`height_frac` 4.18 → 5.07** to match, which is a real difficulty change: a semi is now **179px of a 620px board**, up from 148. That is the one part of this that wants a playtest — see §9.

**Finally, the motorcycles went back.** Played and reported as *"motors are facing wrong direction"* — the one risk §9 had flagged at import, landing exactly as written. `motorlu.png` is a **front elevation**, not a top-down view: you are looking at the rider's face, with the headlight and front wheel at the bottom of the frame, so in a game where all traffic drives away from the player the bikes ride straight at them.

**Nothing could be transformed into a fix, and it is worth being precise about why.** A 180° rotation puts the rider upside down (helmet toward the player, front wheel at the top). A vertical flip is the same thing. **A flipped front view is not a rear view** — the two differ in content (visor and headlight versus the rider's back and a tail lamp), not in orientation, so no rigid transform of this sheet produces a usable sprite. Converting one to the other means repainting the face and the lamp, which is new art, not extraction.

Reverted to the three original top-down bikes and the ten new ones deleted rather than left in the tree as dead assets (the session-P `guclu.png` precedent). `motorcycle` went back to `width_frac` 0.30 / `height_frac` 2.07, and in doing so went from the fleet's **worst**-fitting kind at 7.0% stretch to its **best** at 0.1%. Five of the six supplied sheets shipped; this one could not.

**The transferable rule: check a sheet's *view*, not just its facing, before extracting from it.** Facing is which way a correctly-projected sprite points and is fixable with a rotation (the semis, above). View is the projection itself — front elevation versus top-down — and is not fixable at all. Both were wrong in this session's art, they look similar in a bug report, and only one of them has a cheap fix.

### 2026-08-23, session P: Nitro, and what "the animation looks static" actually meant

Asked for **"a skill benefiting player itself ... it will lift the player a little and in a energy it will really go fast forward"**, with a supplied 6-panel effect sheet (`enerji.png`). Then, across two follow-ups: **"make the energy bigger ... make it go a little bit longer"** with a second, denser sheet (`guclu.png`), and finally **"use them otherwise the animation looks static"** with a third sheet (`more_steps.png`).

This is §11's old step 3 done. It also forced the fix that step had flagged: `_resolve_skill_choice()` rolled the skill **when the pick was made**, so the choice icons could not show what they were offering and simply hardcoded the tank and taxi art. That was only ever correct because both pools held exactly one entry. The roll now happens in `_roll_pending_skills()` when the choice *appears*, and the glyph is a table lookup — so what the player is looking at is what they get.

**The lift is the mechanic, not decoration.** Making the player invulnerable at ground level would have been Tank Mode again. Flying over the traffic is the same fiction the user described, it needs no new collision concept (`_nitro_airborne()` just returns early in `_on_player_area_entered`), and it explains the speed. The lift also turned out to be **structurally** necessary: the car sits ~50px above the board's bottom edge, and the trail is most of the effect's length, so at the original 78px most of the expensive art hung off-screen. 105px is what makes the beam read as long rather than clipped.

**Three decisions worth keeping:**

- **Landing on traffic has to resolve somehow, and both defaults are bad.** The player either dies to a skill meant to help them, or silently drives through a car that never fired `area_entered` because it was *already* overlapping at touchdown. So the landing destroys what it lands on. The sweep runs for a short grace window rather than once, because `get_overlapping_areas()` reports the **last physics tick** and cannot see an overlap created by a position written from `_process` on the same frame — a one-shot sweep at touchdown is guaranteed to look at the wrong place.
- **Boost is suppressed while airborne, not capped.** Stacked, boost (1.8x) and nitro (2.85x) reach ~4.7x, which is faster than a 620px board can be read. Suppressed because "you are not touching the road" is a *reason*; a cap is just a number. The bar does not drain either, and `boost_active` is deliberately left set, so a held key simply resumes working at touchdown.
- **No `Tween` owns the sequence.** The overlay has to be repositioned against a car that is still steering every frame, and a tween that owns an animation is also the thing that leaks an overlay sprite when something kills it mid-flight — the §7 `fire_anim_tween` invariant, which exists because of exactly that leak in session G. The whole skill is one countdown with every phase derived from it.

**"Bigger and more powerful" was a layering problem, not a scale problem.** Simply enlarging one sheet made it blurry, not massive. Two additive layers of the *same storyboard* — the dense sheet at the core, the softer one drawn larger and dimmer behind it — give a footprint neither carries alone. Additive blending is what makes that stack legal: the art is a glow on near-black, so the dark ground contributes nothing and neither layer occludes the other. Both layers run off **one phase index, not two animations**, so they cannot drift apart.

**"The animation looks static" was literally true, and the reason is worth recording.** The six panels of the first two sheets are six *stages*, and the surge is by far the longest phase — so maximum power held a single still frame for 3.8 seconds while the car shook underneath it. `more_steps.png` resolves each stage into its own sub-frames (its own note: *"her bir aşama soldakinden sağdakine doğru zaman içinde gerçekleşir"* — each stage happens over time, left to right), 23 in all. Each stage now walks its frames across its slice of the clock, and **maximum power ping-pongs** over its three rather than parking on the last one. Measured: **55 frame changes per flight, all 23 sub-frames visited**, against 6 before.

`guclu.png`'s six frames were deleted rather than kept: `more_steps.png` is the same art style with strictly more detail, so keeping them would have meant shipping six dead assets. `enerji.png` stays as the halo for a specific measured reason — its comet is proportionally the longest of the three sheets (length-to-cross-section **1.74**, against `more_steps`' **0.65**), so it supplies the effect's reach while the core supplies detail and motion.

**Three extraction findings that a re-run would otherwise rediscover the hard way:**

- **None of the three sheets had a real alpha channel** — all three reported plain `RGB`, the §7 raw-PNG trap for the third time in this project. Alpha is derived from luminance at crop time, which also happens to be exactly right for additive blending.
- **Every frame group is cropped to one common size, and the comets to a common head slot.** This is not tidiness. A per-frame bbox crop would have destroyed the size progression that *is* the animation (stage 1 grows from sparks to a full ring), and a head that moved between frames would make the whole effect jitter against the car as they advance. One crop size per group is also why one scale constant covers a sheet.
- **The little violet "over time" arrows between sub-frames cannot be removed by colour or brightness.** The art's own lightning is violet too, and some arrows are as bright as a bolt; a loosened colour rule punched visible holes straight through the beam. They were removed by **position** instead — all 17 x-values read off an annotated grid render of the sheet, each refined to its local violet cluster before clearing.

**The bug the compile check could not see.** `NITRO_STAGE_FRAMES` was generated flat (23 textures in one array) instead of nested (6 groups). It compiled perfectly clean against both scenes and then threw on every single frame at runtime. This is §8/§12's warning landing again, and it is why the throwaway harness was worth writing: it caught it in one run.

**Verified by harness rather than by reasoning**, in the spirit of sessions L/M/O — lift returns to **exactly 0.0** and scale/`z_index` to their defaults, `elapsed` is **never touched** (so the permanent ramp stays independent of the surge, the §7 invariant), **zero leaked nodes**, the comet head sits at **(0,0)** on the car on every frame, and a car pinned onto the player gives `alive=true` with the skill against `alive=false` without it — same collision, opposite outcomes, which is what proves both that the fly-over works and that ordinary crashes still kill. The harness was thrown away rather than committed (unlike `TaxiProbe`/`ScrollSyncProbe`): nothing here is a behaviour that will be re-tuned by eye over many sessions, it was a one-off correctness check.

### 2026-08-23, session O: the median was never actually in sync with the road

Reported as **"there is a disconnect between the road and where the trees are ... it makes the game look like it's getting stuck or buggy."**

`LaneDivider` kept its own `elapsed` and re-integrated `SpeedRamp.speed_at(elapsed)` every frame. **Session K had already "fixed" this**, by deleting the copy-pasted ramp constants so that the board and the divider could no longer disagree about the curve, and §9/§11 both recorded the leftover risk as a *start-time* problem — "a divider that is reset or created at a different moment than its neighbouring board would still drift". That framing is why this survived three more sessions: it is true, it is also irrelevant, and both boards and dividers are in fact reset in the same `_start_round()` call. **Identical ramps are not identical distances.** Two things break the equality and neither has anything to do with when the timers started:

1. **Boost and tank recoil.** `PlayerBoard.current_speed()` multiplies the ramp by per-board state the ramp knows nothing about — boost alone is up to **1.8x**. The road surges, the median doesn't, and because distance gained is never given back the offset is **permanent**: one boost, then the trees are out of phase with the road for the rest of the round. Measured at **-567px, or -1.69 median tiles.**
2. **A crashed or inactive board.** `PlayerBoard._process` early-returns on `not active or not alive`, freezing its road. Nothing froze the median, so it scrolled on beside a dead board with drift growing every second **without bound** (+297px one second after the crash, +837px five seconds later). This is the one that reads as the game having glitched rather than merely looking off, and it is almost certainly what prompted the report.

The fix is §11's old step 7, finally done: the divider owns no scroll state and **follows a flanking board's odometer**. It integrates the *delta* rather than copying the value, so switching source when the followed board crashes carries no jump. Drift measured at **exactly 0.0px** through both a boost and a crash, and constant (not growing) after a source switch.

**Two details that were both found by measuring, not reasoning**, and that a re-implementation would get wrong:

- **`process_priority = 10` on the divider.** `DividersContainer` sits *above* `BoardsContainer` in `Main.tscn`, so tree order alone left the median reading a one-frame-stale odometer. Priority makes the ordering explicit instead of a property of scene-file layout.
- **`reset()` primes its source instead of nulling it.** With a null source, frame one establishes its baseline from an odometer that has *already* advanced, silently dropping one frame of distance — 2.7px, permanent, for the whole round. This is the difference between the -2.7px the first version measured and the 0.0px the final one does, and it is invisible to anything but a probe.

**The unavoidable residue, stated so nobody "fixes" it later:** one strip of scenery sits between two boards that can legitimately scroll at different rates (one player boosting, the other not), and it cannot match both. It matches `neighbors[0]`, its left board, and falls back to the right one only when the left stops scrolling — so it is always locked to *some* live road rather than to none. The only complete fix is splitting the strip so each half follows its own board, which would tear the trees down the middle whenever the two differ. That is worse than the problem.

`scripts/dev/ScrollSyncProbe.gd` is committed for the same reason `TaxiProbe` was: the reasoning about this bug was confidently wrong twice (session K's fix, and §9's start-time framing), and the numbers are the only thing that settled it.

### 2026-08-23, session N: easing the taxi off a notch

Reported as simply **"the taxi is a little bit too aggressive, make it a little bit less aggressive."** No bug, no failure mode — the taxi did exactly what sessions I/L/M built it to do, and it turned out to be slightly too much of it. Worth recording anyway, because the *shape* of the fix is the reusable part and because a future session reading §5 could easily mistake these smaller numbers for timidity being introduced by accident.

Every dial is a **loosened tolerance, never an exemption** — the §7 invariant. The one time the taxi was given its own private code path it phased through traffic (session I), so "less aggressive" had to mean playing less tight inside the same rules, not being handed a new rule.

The biggest single offender was the **decision interval**, and it is the one that would not have been found by staring at the constant list: at 0.45-1.0s it re-rolled *faster than a lane change completes*, so the taxi spent its whole life re-deciding mid-move and the weave never resolved into manoeuvres a player could read. It read as frantic rather than reckless. 0.65-1.4s now; the `tx_blocked` timer collapse still short-circuits it, so nothing is lost when the taxi genuinely needs a gap immediately.

Alongside it: `TAXI_LANE_SWEEP_MAX` 3 → 2 (a full three-lane slash was the most alarming thing it did), the signal split 35/30/35 → **55/25/20** honest/none/fakeout, `TAXI_SIGNAL_WARNING` 0.35 → 0.55s (0.35 is shorter than a lane change itself, so even an *honest* signal gave nothing to react to), `TAXI_SIDE_GAP` 18 → 28px, `TAXI_MAX_STEER_SPEED` 520 → 470, and `TAXI_URGENCY_MAX` 1.0 → 0.85.

**Why urgency and not the speed bounds.** The obvious way to soften the surges and the hard braking is to narrow `TAXI_SPEED_MULT_MIN`/`MAX`. That is the trap: those bounds are what let the taxi cross the board end to end inside its window, and narrowing them walks straight back into session L's complaint. `TAXI_URGENCY_MAX` is the scalar that decides how often `_roam_speed_mult` gets *pinned* to those bounds, so trimming it takes the edge off without touching the taxi's reach.

**Measured over 20 seeds per version** with `TaxiProbe` (2 players, 1 taxi), because the whole change is behaviour no compile check can see:

| | old | new |
|---|---|---|
| lane changes per taxi | 18.2 | **13.1** |
| onboard | 79.7% | 79.1% |
| coverage | 91.8% | 90.5% |
| lanes visited | 4.6 | 4.3 |
| blocked | 19.9% | 21.6% |

The −28% on lane changes is the change landing; **the flatness of the other four rows is the actual result.** Those are precisely the metrics that collapsed in the pre-session-L taxi (onboard 58%, 42% of its life below the board), so holding them steady is what distinguishes "calmer" from "back to loitering". A future dial-back should re-run this and check the same four rows, not just the one it is aiming at.

Also corrected a doc error found on the way — see §9: the 4.3px worst-case overlap recorded by session M was measured over 5 seeds and understates it. Over 20 seeds *both* versions reach 20-25px.

### 2026-08-22, session M: why the taxi was clipping cars, and a harness that can answer that

Follow-up to session L, which left a measured but undiagnosed residual: taxis still overlapped other vehicles by up to 15.7px. §9 had recorded a *guess* at the cause — traffic merging into the taxi mid-sweep. **The guess was wrong**, and the way it was shown to be wrong is the reusable part of this session.

The measurement harness became a committed tool (`scripts/dev/TaxiProbe.gd`) instead of a throwaway, and learned to classify *why* each overlap starts rather than just counting frames. Two details made it work, both of which had produced misleading numbers first:

- **Classify at the onset of an overlap episode, not every frame.** An overlap persists for many frames after whatever caused it has stopped moving, so per-frame sampling reported "neither party was moving" for every single overlap — which was true, and useless.
- **Dump the raw geometry, not just a verdict.** The `taxi_y` field is what actually cracked it: the overlaps were at y≈716 and y≈760 on a 620px board. Those are *below the bottom edge* — the spawn strip.

Two real causes, neither of them the guess:

1. **Taxis were spawning inside cars.** The spawn strip below the board is exactly where traffic waiting to cross the despawn line sits. `_spawn_taxi` picked a lane avoiding the player and other taxis, and never looked at ordinary traffic. Fixed with `_spawn_slot_clear()` and a scored lane pick — clearance deliberately outranks avoiding another taxi's registered lane, since that lane may be nowhere near the spawn point while a car in the spawn slot is a visible overlap on frame one.
2. **`_taxi_follow_limit` had a lateral blind band.** It only considered vehicles within `(w1 + w2) * 0.45`, while actual sprite overlap begins at `* 0.5`. Cars sitting in that ~2.5px band were invisible to car-following while genuinely overlapping on screen, so the taxi closed straight through them longitudinally. Now `0.5`, matching the geometry it is supposed to enforce.

Worst-case overlap 15.7px → **4.3px**, most seeds completely clean. Fix 2 also improved the taxi's driving as a side effect — seeing cars it had been ignoring dropped `blocked` from 56% to 19% and pushed lanes visited to 5/5 — which is a fair warning that the 0.45 was costing behaviour, not just tidiness.

The one remaining known cause is written up in §9 and deliberately left alone: traffic never re-checks a merge it has committed to. Fixing it means touching lane-change behaviour signed off in session D, for about one episode in five seeds.

### 2026-08-22, session L: the taxi actually causes chaos

Reported as: **"it sticks to the side of the road or doesn't do much"**, it should **"not just focus or aim at the player"**, and its goal is to **bring chaos** — go up, down, left, right, in the traffic. Three separate causes, not one behaviour needing a tuning pass:

1. **It steered to arbitrary x, not to lanes.** Targets were `current_x ± one lane width`, clamped to `board_width * 0.06` — but the road's painted shoulder is `SHOULDER_RATIO` 0.1287, so the taxi's own targets could park it *on the shoulder*, in no lane at all. That is the reported "sticks to the side" literally. Targets are lane centres now; measured shoulder time is 0%.
2. **One blocked frame cancelled the whole lane change.** The per-frame clearance re-check wrote the taxi's current x back into `tx_target_x`. Traffic streams past a taxi doing -0.5 constantly, so nearly every lane change got aborted part-way, leaving it stranded between lanes with no intent. See the §7 invariant this became.
3. **It picked lanes at random while being unable to overtake within one.** It spawns behind all the traffic and `_taxi_follow_limit` rightly forbids driving through the car in front, so its only route up the road is through gaps — and a random lane is usually just a different car to sit behind. `_taxi_lane_headroom` now scores lanes by open road ahead, ignored 30% of the time so the weaving doesn't read as a solver.

The player-chasing went with them. Every speed roll used to be biased to keep the taxi near the player's y, which is what made it a tailgater with a small range. `_roam_speed_mult` replaces it: a destination anywhere on the board (`tx_roam_y`), converted to a `speed_mult` **every frame** rather than at decision time — that continuous evaluation is what eases it in on arrival instead of sailing past the top between two decisions.

**Measured, not eyeballed.** The complaint was about behaviour no compile check can see, so this was validated with a throwaway `--fixed-fps` harness (see CLAUDE.md) that reported where taxis actually went, run over 5 identical seeds against both the old and new code:

| | old | new |
|---|---|---|
| time actually on screen | 42% | 76% |
| board height covered | 57% | 90% |
| lanes visited (of 5) | 2.7 | 4.3 |
| lane changes per run | 3.7 | 18.3 |

That 42% *is* the complaint: the old taxi spent most of its life off-screen below the board, fighting exit traffic it was not allowed to overtake.

**Two bugs the harness caught that reasoning had missed**, both worth remembering because both looked fine in code review:

- Spacing a simultaneous wave by 130px pushed the second taxi **past the shared despawn line at spawn**, so it was culled on its first frame — one rival's skill silently doing nothing. The window between the taxi's spawn y and that line is only ~50px. The stagger is now small and clamped against it, and distinct spawn lanes do the real work of keeping a wave apart. `OBSTACLE_DESPAWN_MARGIN` was extracted as a named constant so the spawn can reason about it instead of re-deriving `140.0`.
- The **leaving** state only set a speed, so it got pinned behind traffic exactly like the entry did and the taxi never actually left — the "and then it screams off up the road" beat simply never happened. It keeps gap-hunting on the way out now.

### 2026-08-22, session K: easing the difficulty ramp (and centralizing it)

The user's report was flat: **"game gets too fast too soon."** It turned out to be true on both of the ramp's axes, and both bottomed out inside the first half-minute:

- **Road speed** was `160 + 6 * elapsed` — dead linear and unbounded. A board was at double its starting speed 30 seconds in, and it never stopped climbing, so a long round became unreadable rather than hard (t=240 was 1600px/s).
- **Traffic density** reached its floor (0.35s between spawns) at **33 seconds**. Maximum traffic arrived before the player had settled in at all. This is the half of the complaint that isn't about raw pace, and it would have been easy to miss by only looking at the speed formula.

Speed now eases along `progress ^ 1.45` toward a real top speed, so the opening stays close to the starting feel that was already signed off and the pressure arrives as the round matures. Density tightens on the same curve but over a **shorter** window (70s vs 100s), deliberately leading speed: thicker traffic makes a board harder to *read* without making it a blur, so the mid-round difficulty is about picking a line through real traffic and only the late round is about pace.

| t | new speed | old speed | new interval | old interval |
|---|---|---|---|---|
| 15s | 186 | 250 | 0.80 | 0.63 |
| 30s | 230 | 340 | 0.70 | 0.40 |
| 60s | 351 | 520 | 0.45 | 0.35 |
| 100s | 560 | 760 | 0.35 | 0.35 |
| 240s | 728 | 1600 | 0.35 | 0.35 |

Past the ramp, speed keeps creeping at `OVERTIME_SPEED_PER_SECOND` (1.2, a fifth of the old slope) rather than flattening off. **Don't Crash is a last-one-driving mode, so a round has to stay guaranteed to end** — a hard cap would let two good players stalemate indefinitely. It just no longer resolves that by running away to 1600px/s.

The constants moved into a new `scripts/SpeedRamp.gd` rather than being tuned in place, which is §11's old step 5 finally being done — and it was a precondition, not a bonus. `BASE_SPEED`/`SPEED_PER_SECOND` were copy-pasted between `PlayerBoard.gd` and `LaneDivider.gd` and had to be kept numerically identical by hand or the road and the tree median scroll at different rates. Two numbers you can eyeball for equality is one thing; duplicating a five-constant eased curve is asking for that desync back. `SpeedRamp` is a `RefCounted` with `class_name` and only static functions — no autoload entry, no state — because `elapsed` still belongs to each board and each divider separately.

**Gotcha this cost a validation cycle:** a new `class_name` is not visible to a headless run until the project has been reimported. The first `godot --headless --quit res://scenes/Main.tscn` after adding `SpeedRamp.gd` failed with `Identifier "SpeedRamp" not declared in the current scope` and `Failed to load script "res://scripts/PlayerBoard.gd"` — nothing to do with the code being wrong. Run `godot --headless --import` first (`.godot/global_script_class_cache.cfg` is what gets rebuilt). See §12.

Validated by the numbers table above being printed from the real `SpeedRamp` (a throwaway `SceneTree` script run with `godot --headless --script`, then deleted) rather than from arithmetic done by hand, plus the user's own playtest — "okey push it".

### 2026-08-22, session J: BotDriver — an AI that plays a board, for testing and single player

Asked for by the user as a way to **playtest changes without having to hold the keys** (this project's only validation is manual play — see CLAUDE.md) and, as a side effect, to make **single player** possible in a mode that is structurally a race between boards.

**How it is wired in (the part worth preserving).** The bot does *not* synthesise `InputEvent`s or touch the `Input` singleton. Those are global — a fake "A pressed" would be seen by every board bound to A and would fight a real player's fingers. Instead `PlayerBoard`'s own input reads were funnelled through three functions that the keyboard path and the bot both call: `_steer_held(dir)` (replaces the two `Input.is_physical_key_pressed` calls in the steering block), `_press_steer(dir, register_tap)` and `_press_confirm()`/`_release_confirm()` (the bodies lifted out of `_unhandled_input`'s key branches). `bot.tick(delta)` runs at the top of `_process`, exactly where a human's key events would already have landed. Consequence: a board can be handed between a bot and a human **mid-round** with no other machinery, which is what the 1-4 keys do.

**What it senses.** Only `obstacle_container`'s children and the `lane`/`speed_mult`/`lc_*` meta keys the traffic systems already maintain, so taxis and lane-changers are handled for free rather than as special cases. It reads turn signals (`lc_state` + `lc_to_x`) and plans against where a blinking car is *going*, which is most of what makes it look like it saw a merge coming. A vehicle's `speed_mult` sign is kept, so a taxi closing from behind is as dangerous to it as traffic closing from the front.

**Four rounds of correction before it played respectably.** All four were found by running headless (`--fixed-fps 120`, which runs far faster than real time) with all four boards botted and tracing per-lane numbers. Survival at the hardest profile went 7-40s → a steady 16-55s across the fixes:

1. **Greedy one-step scoring parked it in a lane until it died there.** Scoring a lane purely by its own time-to-impact meant the bot sat in the roomiest lane while the lanes either side filled in, then had nowhere to go — traced it watching a car close from 2.4s to 0.0s without moving. Fix: `_survival()`, a small depth-limited lookahead that asks "and when that car reaches me, is there anywhere left to be?", exploring single-lane hops only (a multi-lane branch would assume it can cut through a lane nobody checked).
2. **Survival alone made every lane tie.** It saturates at the horizon, so on an open road every escapable lane scored identically and the 0.35 stay-bonus decided — the same parking behaviour, one level up. Fix: room (immediate TTI) is the ranking signal and survival became the *veto* (`DEAD_END_WEIGHT` charges for a branch that runs out early). Getting these two the right way round is the single most important thing in the file.
3. **A guaranteed crash was priced below a probable one.** `BLOCKED_PENALTY` (10) was smaller than the worst dead-end cost (`horizon * DEAD_END_WEIGHT` = 13), so a trapped bot answered by steering straight through the car in the next lane. Fix: `BLOCKED_PENALTY` = 100, decisively above any dead-end score. **These two scales must never overlap.**
4. **The escape test was a cliff.** A lane looked perfectly safe until the frame its escape window shut, then lost a whole horizon of value at once — too late to act on. Fix: charge for thin slack (`MARGINAL_ESCAPE_WEIGHT`), turning the cliff into a slope the bot leaves down early.

Plus one self-inflicted one: the HARD profile's boost-farming weave (wagging the wheel to force the velocity reversal a drift needs) reversed on a fixed half-period, which at `STEER_RESPONSE` 9 builds up most of a lane width of swing — it was flinging itself into the next lane. It now reverses on **distance travelled**, and refuses to weave at all unless both shoulders are clear.

**Difficulty is foresight, not information.** All three profiles see the same board; they differ in how far ahead they plan (`horizon`, `lookahead`) and how late and sloppily they act (`decision_interval`, `reaction_time`, `aim_error`, `blunder_chance`), plus whether they use dash/boost/weaving at all. Measured medians over 16 four-player headless rounds each: EASY ~12s, NORMAL ~21s, HARD ~35s. A profile with a 6.5s horizon, depth 4 and zero reaction delay was also measured and scored the same as HARD — this sensing model is at its ceiling, so more lookahead is not where further work should go.

**Bound to the number row, not the function row.** The first pass used F1-F5, which is wrong on macOS — this project's own dev machine — where the function row is media keys unless `fn` is held, so F3 opened Mission Control and pulled focus off the game rather than toggling anything (the user hit this the moment they first tried it). Digits 1-5 collide with nothing in `PLAYER_CONFIGS`, and the digit matching the player number is a better mnemonic anyway. **Any future one-person-reaches-all-of-them binding should go on the number row for the same reason.**

The user played the HARD profile and confirmed it ("push it", then "hard is good"), and said they had not tried the other two and did not care about them — so HARD became the default. See §9 for what that does and does not settle.

### 2026-08-22, session I: the Taxi — first opponent skill

> **Its *behaviour* was substantially replaced in session L** (it roams the board instead of chasing the player, and picks lanes by gap rather than at random). The parts of this entry that still hold — and that must keep holding — are the **art lineage** and the **"it is an ordinary traffic vehicle, moved by the shared loop"** architecture, which session L built on rather than touched. Read the behavioural details below as history, not as the current design.

User asked for a skill that affects opponents: it "calls a taxi" for the other players. Stated behavior: the taxi appears from behind, goes left/right, switches lanes with no indicator, signals right then turns left, accelerates, decelerates — and should move "more like a player, more smooth, not like a normal lane switch by cars at the traffic." Summarized by the user as: it should terrorize the traffic. User supplied `taxi.png` from Documents and gave latitude to add anything else fitting the concept.

**The cross-board problem (new architecture, not just a feature).** This is the first skill that must affect a board other than the one that triggered it, and §11's note that "there's currently no cross-`PlayerBoard` communication path at all" was accurate. Solved with a new `opponent_skill_triggered(skill)` signal on `PlayerBoard`, connected in `Main._build_boards()` with `.bind(board)` so the relay knows the source, and fanned out in `Main._on_opponent_skill_triggered()` to every board *except* that source via a new `PlayerBoard.receive_opponent_skill()`. `OPPONENT_SKILLS` mirrors `SELF_SKILLS`' pool-of-strings shape, but is resolved on the *receiving* end rather than locally.

**Three rounds of correction, each a real redesign rather than a tuning pass — read in order:**

1. **First version (rejected — size + art).** Used the supplied `taxi.png` at its own aspect ratio (`height_frac` 2.08, taller than any sedan). User: too big, and it "looks like it's added afterwards, not a natural part of the traffic." Size was fixed by pinning `TAXI_KIND` to the sedan's own footprint.
2. **Second version (rejected — still reads as pasted on).** First hypothesis for "not part of the traffic" was *resolution*: the taxi art was ~600x990px while every fleet sprite is ~78-160px, so it retained fine detail (checker stripe, crisp linework) that the rest of the fleet doesn't have at its native pixel density. Downsampled it to 84x139 with opaque-only block averaging (so the near-white background couldn't fringe the edges). This helped but did not fix it. User then suggested the cause was "the model or color palette" — which was correct, and see §8 for why the resolution theory was only half the story.
3. **Third version (rejected — runs over cars).** User: "it still runs over car. why can't you add this to the normal traffic. like any other car." This was the important one — see below.

**Why it ran over cars, and the fix.** The taxi drove its own `position.y`, chasing `player_car.position.y + offset` every frame through an exponential approach. Anything between it and the player was simply never consulted, so it phased through traffic lengthwise. An earlier lateral clearance check (`_taxi_target_clear`) only ever guarded sideways moves, which is why adding checks never resolved it: **it was moving on a private code path, so it could not be fixed from within that path.**

The fix was the user's own suggestion, and it fit the existing model far better than expected: the taxi is now an ordinary traffic vehicle, moved by the *same line* as every other car in `_process`'s obstacle loop (`child.position.y += speed * speed_mult * delta`). Its AI no longer moves it at all — it only *sets* its own `speed_mult` and steers laterally, in `_update_taxis()`, called immediately **before** that shared loop. Because `speed_mult` is a closing *fraction* of road speed, a **negative** value means "driving faster than the player" — which is exactly how it overtakes and arrives from behind, with no need to go anywhere near the `speed_frac_max < 1.0` invariant in §7 (that invariant bounds the *slow* end; nothing ever needed the fast end bounded, since driving faster than the player is physically ordinary).

Everything erratic is therefore expressed *inside* the traffic rules rather than as an exception to them:

- **Accelerate/decelerate** is `speed_mult` easing toward a target re-rolled every `TAXI_DECISION_INTERVAL_MIN..MAX` (0.8-1.6s) by `_pick_taxi_speed_mult()`, which biases the roll by the taxi's current position relative to the player so it keeps hanging around them — always by choosing a *speed*, never by moving toward their position.
- **Can't run over cars**: `_taxi_follow_limit()` clamps that mult against any vehicle within `TAXI_FOLLOW_GAP` ahead in its own lane (`mult = max(mult, other_mult)` — matching the car in front means the gap stops shrinking), so overlap is geometrically impossible; it tailgates instead.
- **Lane changes** are gated on `_taxi_target_clear()` re-checked **every frame in `_update_taxi_steering()`**, not just at decision time — traffic keeps moving, so a gap that was open when it committed can shut before it arrives, in which case it abandons the merge and holds its x.
- It sets `lane` meta every frame (via `_nearest_lane()`) like every other obstacle-container child, so the rest of the traffic's own scans (`_lanes_used_near_top`, `_lane_clear_near`) see and avoid **it** too.

Its aggression survives entirely as *how tight it plays inside those rules*: `TAXI_SIDE_GAP` (18px) versus traffic's `LANE_CHANGE_SAFE_GAP` (200px), a `TAXI_SIGNAL_WARNING` of 0.35s versus traffic's 1.3s, and a 35/30/35 split in `_update_taxi_decision()` between an honest signal, no signal at all, and a fakeout that lights the *opposite* lamp before cutting across (the requested "signal right, turn left" — it works because the real target only lands in `tx_target_x` once the signal phase resolves, so the indicator is genuinely lit before the car commits). Lateral motion still uses the same exponential velocity-approach shape as the player's own steering rather than traffic's discrete eased slide, which is what keeps it reading as *driven* rather than as scenery.

**One non-obvious failure mode found by reasoning, not playtesting**: a taxi that catches up to slow traffic gets its mult clamped to that car's — but that car is itself drifting back past the player, so patient tailgating means being carried off the bottom of the board and culled by the shared despawn, quietly fizzling the skill a second or two after it was spent. Fixed by having `_taxi_follow_limit()` set a `tx_blocked` meta flag when it actually had to lift off, and `_update_taxi_ai()` collapsing the decision timer to ≤0.15s while blocked — so being stuck triggers an immediate hunt for a gap. Spawn y was also pulled in (`board_height + sz.y * 0.6 + 24.0`, still fully off-screen) so it doesn't start life already near that despawn threshold.

User confirmed "it is better now", then "push it". Pushed as commit `27825fe`.

### 2026-08-22, session H: shared vehicle-destruction explosion animation

User asked for a real animation whenever a car is destroyed — on the player's own crash and on a tank crush/cannon kill — instead of the near-nonexistent feedback that existed before (a crash just faded the player's car to 35% alpha; a tank kill only spawned small flying debris chips, no explosion). User also asked that once more skills add new ways to destroy a car, those get their own new animation too, rather than everything sharing one hardcoded effect. User supplied `patlama.png` from Documents (a 4x3 pixel-art explosion reference sheet: spark → growing flash → fireball → fireball-to-smoke → dissipating smoke) as a loose visual reference, explicitly noting it didn't need to use every frame/step in that sheet.

Same asset-processing gotcha as session G's tank art applied here: `patlama.png` had no real alpha channel (`PIL` reported plain `RGB`, near-black but not pure-black background at roughly `(18, 19, 26)`). Rather than a manual per-asset border flood-fill this time, used `scipy.ndimage.label` on a color-distance-from-background mask to find the single background-colored region connected to the image's own border, and zeroed alpha only there — this is the same "flood fill inward from the border" intent as session G's technique, just vectorized instead of hand-rolled, and worth reaching for again on any future multi-frame sheet since it handled the grid gaps between all 12 cells in one pass. The 4x3 grid's cell boundaries were located by scanning row/column brightness sums for the low-brightness gaps between cells (columns at x ≈ 0/314/627/940/1254, rows at y ≈ 0/418/836/1254), each cell then cropped to its own tight non-transparent bbox with a small padding margin.

Picked 6 of the 12 source frames (indices 1, 3, 4, 6, 8, 10 in reading order — spark, big flash, fireball, fireball, fire-to-smoke, settling smoke) as `sprites/cars/explosion_1.png`–`explosion_6.png`, skipping near-duplicate in-between frames and the last couple of frames (too faint to read at gameplay scale). Verified visually via a montage before committing to the selection.

Built as one shared function rather than one-off code at each call site:

- `PlayerBoard._play_destruction_effect(pos, vehicle_w, frames := EXPLOSION_FRAMES, source_peak_width := EXPLOSION_SOURCE_PEAK_WIDTH)` spawns a `Sprite2D` centered at `pos`, cycles through `frames` on a `Tween` (one `tween_callback`/`tween_interval` pair per frame, same sequencing shape as the tank's `_play_fire_animation`), then fades `modulate:a` to 0 and frees itself. `_show_destruction_frame(sprite, frame, world_scale)` is the bound per-frame callback (mirrors `_show_fire_effect_frame`'s pattern), with an `is_instance_valid` guard even though nothing currently kills this tween early.
- **Uniform scale derived from one reference width, not per-frame.** `EXPLOSION_SOURCE_PEAK_WIDTH` (313, the widest of the 6 chosen frames' own cropped bboxes) and `EXPLOSION_WORLD_SCALE` (1.5) together give one `world_scale = (vehicle_w * EXPLOSION_WORLD_SCALE) / source_peak_width` applied identically to every frame's texture — since each frame's own native pixel size already differs (small spark vs. full fireball vs. settling smoke), one shared scale factor preserves that authored relative sizing instead of forcing every frame to the same on-screen footprint (same reasoning as `TANK_EFFECT_SOURCE_TANK_WIDTH` in session G).
- **Parameterized specifically so future skills don't hardcode a second copy.** `frames`/`source_peak_width` default to the one standard explosion so every current destruction path (crash, tank crush, cannon) looks identical today, but a future skill that destroys a car through some new means can call `_play_destruction_effect()` with its own frame array and peak width to get a visually distinct effect without touching the tween-sequencing logic itself. This was an explicit, stated requirement, not a guess at future-proofing — see §6.
- Wired into both existing destruction paths: `_destroy_vehicle()` (tank crush + cannon kill, called alongside the pre-existing `_spawn_debris()` triangle chips rather than replacing them — the fireball flash and the flying debris read as complementary, not redundant) and `_on_player_area_entered()`'s crash branch (previously had zero destruction VFX, just the alpha fade — the fade is kept as the "wrecked car" resting state after the explosion plays out).

No explicit restart-time cleanup was added for the new effect sprite (unlike `fire_effect_sprite`, which needs it — see §7/§9's `Tween.kill()` gotcha). This is deliberately fine here: nothing external ever calls `.kill()` on this effect's tween (it's fire-and-forget, same category as the pre-existing debris burst, which also has no explicit restart cleanup), so it always reaches its own final callback and frees itself naturally well within its ~0.5s lifetime — a crash-triggered explosion in particular finishes long before the game-over screen's required Enter-press restart could ever interrupt it.

User confirmed in-editor ("great push it") without requesting changes; pushed as commit `3b71bda`.

   - **Rejected approach**: swapping the player's whole tank *body* texture through each animation-sheet frame in sequence. Measuring each frame's own content bbox showed the source sheet's tank render isn't pixel-aligned across its own cells (the flash/smoke cells' combined bbox centers land tens to hundreds of px away from the idle cell's own tank-only bbox center) — almost certainly an artifact of each cell being independently generated rather than a true engineered animation export. Chasing a symmetric-crop-around-a-shared-tank-center fix proved fragile and was abandoned.
   - **What shipped instead**: the tank's own body sprite stays static (`TANK_TEXTURE`) for the whole round; muzzle flash and smoke are extracted as *separate* overlay images with the tank hull pixels masked out entirely (cut at a fixed y-cutoff in the source cell, below which is tank hull and above which is pure effect), each cropped to its own tight bbox, and positioned every frame by `_show_fire_effect_frame()` via `Sprite2D.offset` so the frame's own bottom-center — not its geometric center — lands at `_muzzle_position()`. This sidesteps the sheet's internal misalignment completely, since nothing about the overlay's world position depends on where the effect happened to sit in its source cell. `_play_fire_animation()` sequences `TANK_FLASH_FRAMES` (2) then `TANK_SMOKE_FRAMES` (2) via a `Tween` of alternating `tween_callback`/`tween_interval` pairs, ending in `_fade_out_fire_effect()` (fades `modulate:a` to 0, then frees the sprite). `TANK_EFFECT_SOURCE_TANK_WIDTH` (188px, measured by inspection — same convention as `Road.SHOULDER_RATIO`) is the tank's own width inside the source sheet cell, used to derive a uniform scale so the overlay renders proportionate to whatever the in-game tank's actual current width is. The shell (`tank_shell.png`, cropped/rotated from `Projectile.png`) is a real `Sprite2D` tweened from the muzzle to the target's position (or off the top of the board on a miss), rotated to face its actual travel direction (`travel_dir.angle() + PI/2`, correcting for the art's native "points up" orientation), and only destroys the target on arrival (`_on_shell_arrived`) rather than instantly — `cannon_ready` (blocks re-firing) is restored there too, so the shell's own flight time doubles as the reload without a separate cooldown timer. Recoil: firing sets `recoil_offset = TANK_RECOIL_KICK`, decayed every frame via `move_toward` and added to the player's own y position, plus a `recoil_timer` window during which `current_speed()` is multiplied down (`TANK_RECOIL_SPEED_MULT`) — since this project's whole forward-motion illusion *is* `current_speed()` (no separate player-forward-velocity variable exists, see §7), this is also the only structurally correct way to make "the tank slows down" mean anything, and it's a deliberate, brief whole-board effect (traffic visibly slows too for that instant), not a bug.
3. **Bug found in the user's own playtest, not a design note**: after the transform ended, a smoke sprite from the fire animation was sometimes left behind on screen permanently — visible even across a crash and a full round restart. Root cause: `_deactivate_tank_mode()` and `start_round()` both call `fire_anim_tween.kill()` if the animation is still running when either fires (transform timing out mid-animation, or a restart cutting it off entirely) — but killing a `Tween` skips whatever `tween_callback`s hadn't fired yet, including the *final* one (`_fade_out_fire_effect`) that was responsible for ever freeing the sprite. With that callback skipped, `fire_effect_sprite` was simply an orphaned child node with nothing left to ever revisit it. Fixed by having both call sites explicitly `queue_free()` the sprite (if valid) and null the reference right alongside killing the tween, rather than relying on the tween's own completion to do it.

User confirmed the visuals/timing/animation looked good in-editor after each round of changes ("everything is great" after the tuning pass, then reported the leak, then "nice push it" after the fix) — playtested via a directly-launched game window (`godot --path . res://scenes/MainMenu.tscn`, run in the background) rather than the editor GUI, since the ask was just to see the game running, not to edit anything.

### 2026-08-21, session E: 4-player camera clipping + top/bottom render seam

User reported that in 4-player mode, the leftmost and rightmost boards only showed 3-4 of their 5 lanes — the rest didn't render — and separately asked for more road to be rendered ahead at the top, for the current zoom level to be kept as-is, and for the seam where rendering visibly starts/stops (top and, worse, bottom/"behind") to be masked better.

Root cause of the clipping: `Main._build_boards()` used a fixed `CAMERA_ZOOM` (1.15) regardless of player count. `boards_container`'s total width scales with player count (`count * board_width + (count-1) * BOARD_GAP`), but the camera's visible width at a fixed zoom does not — at 2-3 players the total width fits comfortably inside what `1.15` shows, but at 4 players (`1584` world units) it exceeds the visible width at that zoom (`viewport_width / 1.15 ≈ 1304`), so roughly 140px of each outer board fell outside the camera's view. That's almost exactly "2-3 lanes' worth" of a 5-lane, 360px-wide board — matching the reported symptom precisely.

Root cause of the render-seam complaint: fixing the above by zooming the camera *out* to fit 4 players' width also widens the vertical slice the camera sees (zoom is uniform on both axes), without `board_height` changing. That extra vertical slice fell outside `Road._draw()`/`LaneDivider._draw()`'s hardcoded `[0, height]` tiling loop, exposing bare background above and below the track — a visible hard edge where the road stopped being drawn. This letterboxing actually already existed at the *old* fixed zoom too (a smaller ~38px gap present in every player count, just apparently unnoticed until the 4-player fix made it bigger), which is why the fix below applies to 2-3 players as well, not just 4.

Fixed with three coordinated changes, all keyed off one computed `vertical_margin` (how far past `[0, board_height]` the camera can see, in board-local units):

1. **Dynamic camera zoom** (`Main._build_boards()`): `zoom = min(CAMERA_ZOOM, viewport_width / (total_width + margin))` — only ever zooms *out* from the preferred `1.15`, never in, and only as far as needed to keep every board's full width on screen. This is why 2-3 player framing is provably unchanged (`fit_zoom` exceeds `1.15` there, so `min()` still picks `1.15`) while 4-player no longer clips.
2. **Extended tile rendering** (`Road.render_margin`, `LaneDivider.render_margin`, both `@export var`, default `0.0`): the draw loop's bounds became `[-render_margin, height + render_margin]` instead of the fixed `[0, height]`, generalizing the original anchor-and-loop logic rather than replacing it (`render_margin = 0` reproduces the exact old behavior — verified by inspection, the top loop's extra `while y > top_edge: y -= tile_h` never executes when `top_edge = 0` since `scroll - tile_h` is already `<= 0`). `Main` sets this on every board (via `PlayerBoard.set_vertical_margin()`, which forwards to `road.render_margin`) and every divider directly (dividers have no wrapper node to go through).
3. **Extended obstacle spawn/despawn** (`PlayerBoard.vertical_margin`): spawn y and the despawn threshold both got `- vertical_margin` / `+ vertical_margin` added, so traffic still pops in/out beyond whatever the camera can actually see, at any zoom level.
4. **`ScreenMask.gd`** (new script + new `HUD/ScreenMask` node, first child of `HUD` so other HUD elements draw over it): a screen-space (not world-space, so unaffected by camera zoom) top/bottom vignette, fading to the viewport's own background color. Its fade height is `vertical_margin * zoom + SCREEN_MASK_BASE_PX` — converts the world-space margin back to screen pixels through the current zoom, plus a small always-on constant (24px) so there's a subtle fade even at 2-3 players where `vertical_margin` is 0. This is the actual "mask it better" ask — items 2-3 are structurally correct (nothing is missing/popping visibly) but the mask is what makes the top/bottom edge read as an intentional fade rather than a rendering boundary, however precisely items 2-3 are tuned.

User playtested in-editor and confirmed ("it looks great push it") without requesting further changes.

### 2026-08-20, session D: chaotic lane-changing traffic + turn signals

User asked for traffic to feel more chaotic — cars and trucks occasionally changing lanes — but explicitly wanted it kept fun/fair rather than cheap, and asked for a real-car-style yellow indicator light that blinks before the lane change starts, the way a real turn signal does.

Built as two pieces:

1. **Turn signal lamps (`Car.gd`)**: two small `Polygon2D` lamps built procedurally in `_ready()`/positioned in `_position_indicators()` (called from `_rebuild()`), so no scene or art changes were needed and it works identically on the placeholder shape and on real cropped-photo textures. `start_indicator(side)` (-1 left, 1 right) turns the correct lamp on immediately and arms a repeating blink via `_process`/`INDICATOR_BLINK_INTERVAL` (0.16s); `stop_indicator()` kills both. This node only owns the blink animation — it has no opinion about *when* to signal.
2. **Lane-change state machine (`PlayerBoard.gd`)**: `_maybe_flag_lane_change()` flags ~22% (`LANE_CHANGE_CHANCE`) of newly spawned obstacles with `lc_state = "pending"` and a random trigger y within the top half of the board (`LANE_CHANGE_TRIGGER_Y_MIN/MAX_FRAC`, 12%–50% down). `_update_obstacle_lane_change()`, called once per obstacle per frame from the same loop that already moves them, drives `pending -> warning -> moving -> settled -> idle`:
   - `pending`: waits until the obstacle reaches its trigger y, then calls `_pick_lane_change_direction()`, which only offers a direction whose target lane is clear of other traffic within `LANE_CHANGE_SAFE_GAP` (200px) of the same y (`_lane_clear_near()`). If neither adjacent lane is safe, it cancels back to `idle` rather than forcing a move.
   - `warning`: indicator blinks for `LANE_CHANGE_INDICATOR_WARNING` with the car still going perfectly straight — no motion at all yet.
   - `moving`: smoothstep-eased slide from the old lane center to the new one over `LANE_CHANGE_DURATION`.
   - `settled`: keeps blinking for `LANE_CHANGE_INDICATOR_TAIL` after arriving (a real signal doesn't cut off instantly either), then calls `stop_indicator()` and goes `idle` for good — each obstacle changes lanes at most once.

The obstacle's `lane` meta (already read by `_spawn_obstacle()`'s used-lane check) is updated the moment the direction is *decided*, not once the slide finishes — so a car mid-merge still correctly blocks a new spawn or another lane-change from targeting the lane it's moving into.

### 2026-08-20, session B: drift feel + continuous skid marks

User asked for two things: make the drift system feel less unintuitive (with a request to research how other games handle it), and fix the skid marks leaving discontinuous "part by part" marks instead of a continuous trail. This took four iterations because the first three each fixed a real bug but exposed the next one — **read this in order, it's the reasoning trail, not just a changelog**:

1. **Continuous trail (right the first time).** Old: `PlayerBoard._spawn_drift_mark()` stamped a `ColorRect` on a `DRIFT_MARK_INTERVAL` (0.045s) timer. At max steer speed (460px/s) the car moves ~20px between stamps while each stamp is only ~7px wide — guaranteed gaps. Per standard practice in every top-down drift tutorial researched (Godot forum "tire drift/skid marks with Line2D", multiple Line2D trail tutorials), replaced with two `Line2D` trails (one per rear wheel) that get a point appended every single `_process` frame while drifting — continuous regardless of speed. This part was correct from the start and never needed revisiting.

2. **Drift never resolved (attempt 1).** Original drift only ended `is_drifting` on full key release — so a caught slide stayed in reduced-grip mode for as long as any key was held, reading as a sticky mode rather than a slide you catch (unlike CarX/Inertial Drift-style resolution researched). First fix: auto-end the whole `is_drifting` session once `car_vx` converges to ~88% of `target_vx`. **This broke "keep drifting while switching direction"** (a pre-existing, deliberately-preserved feature) — ending the session also set `drift_cooldown_timer`, which then blocked an immediate re-drift on the next reversal.

3. **Split session from grip (attempt 2).** Fix: separated the *session* (`is_drifting` — trail generation + nose-lead rotation, persists across direction switches, only ends on release) from *grip* (new `drift_sliding` — resolves on convergence, but a fresh reversal re-arms it instantly via `_try_start_drift()`'s already-mid-session branch, no cooldown). This fixed holding-then-releasing, but the user reported switching direction **still** killed the drift.

4. **Release-both-keys gap (attempt 3).** Root cause: a real keyboard direction switch is never a single frame — there's a brief instant where both steer keys read released while a finger moves off the old key before it's on the new one. `is_drifting` was ending (session-level) the instant `target_vx` hit 0, which fires during that gap on every switch. Fix: `DRIFT_RELEASE_GRACE` (0.14s) — the session only actually ends once both keys have stayed released for the whole grace window, not on the first zero-input frame.

5. **Both-keys-held-simultaneously gap (attempt 4, the actual root cause).** User sent a screen recording (couldn't be read — see §8 for why) and re-reported the same symptom, which forced a re-check of `target_vx` itself rather than the drift state machine. Found it: `target_vx` was computed as `if left and not right: ... elif right and not left: ...`, meaning **both keys held simultaneously reads as neutral (target_vx = 0)**. Players commonly press the new direction key slightly *before* releasing the old one (especially on adjacent Left/Right arrow keys), so that overlap was decelerating the car to a dead stop mid-switch — independent of and underneath all the session/grip state machinery from attempts 2–3, which is why fixing the state machine alone never fully resolved it. Fix: added `steer_priority` (set to ±1 on every key-press event), and when both keys read held, `target_vx` now resolves to whichever direction was pressed most recently instead of zeroing out.

User confirmed after fix #5 that weaving (rapid direction changes without ever releasing) keeps the slide and trail unbroken ("its great, push it").

### 2026-08-20, session A: traffic speed/direction bug chain

Reported by the user as: *"trees and road moves at a different speed and cars look like it is going backward."* Three distinct, real bugs were found and fixed in sequence — **all three fixes are necessary; none of them individually resolved the full symptom**:

1. **`LaneDivider` never reset across rounds** (commit `b049efe`). `LaneDivider._process` accumulates its own `elapsed`/`distance` from the moment the node is created and never stops. `Main._start_round()` resets every `PlayerBoard`'s `elapsed`/`distance` to 0 on both the first round and every restart, but never touched the dividers. After any restart-after-crash, the road/traffic speed would snap back to `BASE_SPEED` while the tree median kept accelerating from wherever it had already climbed to — a growing speed mismatch between trees and road. Fix: added `LaneDivider.reset()`, called from `Main._start_round()` for every child of `dividers_container` alongside each board's `start_round()`.

2. **Road/median tiles scrolled in the opposite direction from traffic** (commit `5353b8a`). This was the primary cause of "cars look like they're going backward." `Road._draw()` and `LaneDivider._draw()` both anchored their tile loop at `y = -scroll`, and as `distance` (and therefore `scroll`) grew, that shifts the rendered pattern toward **negative y** (up, off the top of the screen). But obstacle traffic in `PlayerBoard._process` moves via `child.position.y += speed * speed_mult * delta` — **positive y** (down, toward the player), which is the geometrically correct direction for "you are driving forward." Background scrolling up while foreground traffic scrolls down is a direct visual contradiction — the road reads as sliding the wrong way under the cars. Fix: changed the anchor to `y = scroll - tile_h` in both `_draw()` methods, which makes the tiled pattern slide toward +y (down) as `distance` grows, matching the traffic direction. Coverage math (tile spacing, no gaps) is unaffected — only the anchor point's sign flipped.

3. **Some individual obstacles still looked like they were reversing, even after fix #2** (commit `d4b9532`). Root cause: `PlayerBoard._spawn_obstacle()` picked `speed_mult` uniformly from `randf_range(0.78, 1.28)` and used it as `child.position.y += speed * speed_mult * delta` directly. The road texture itself always scrolls at exactly `speed` (i.e., implicitly `speed_mult == 1.0`). Any obstacle with `speed_mult > 1.0` therefore closes toward the player **faster than the road surface's own scroll rate** — which is only physically possible if that car is driving in reverse relative to the road. Visually this reads as the car sliding backward across the lane stripes, even though its on-screen y is still increasing. Fix: reworked the whole speed model in terms of relative motion — an obstacle's screen speed represents `(road speed − the vehicle's own forward speed)`, which for any car that is actually driving forward is always strictly less than the road's own scroll rate. Implemented as per-`TRAFFIC_KINDS`-entry `speed_frac_min`/`speed_frac_max` fields (all kept below 1.0, capped at 0.95 max — see the invariant in §7), replacing the single flat 0.78–1.28 range. Trucks/buses get high fractions (0.75–0.95 → slow real-world speed → you close in on them fast); motorcycles get low fractions (0.35–0.65 → fast real-world speed → they roughly keep pace with you, hard to catch); sedans/SUVs/pickups/vans sit in between (0.55–0.9).

User confirmed the result looks correct after fix #3 ("its great").

## 6. Key technical decisions & why

- **Pile Up is turn-based because its scoring rule requires it, not to keep it simple.** "The one who drops a brick loses a life" only has an answer if exactly one player can be responsible for the tower's state at a time; with everyone dropping onto one shared stack simultaneously, a collapse has no author. Everything else about the mode follows from that — the turn timer exists so turns can't drag, and the settle wait exists so the author of a delayed collapse is still the right player. If simultaneous play is ever wanted, the fault rule has to be redesigned first, not the turn loop.
- **A second mode meant a second scene tree, not a generalised first one.** Don't Crash and Pile Up share `GameSettings`, the three menu screens and the key bindings. They share no geometry, camera model, update loop or physics approach — one moves `Area2D`s by hand down N independent scrolling boards, the other runs one world of real rigid bodies. Refactoring `Main`/`PlayerBoard` into something that could host both would have meant abstracting over two things with nothing in common, and would have put the project's only playtested mode at risk to add an unplayed one. The seam is `GameSettings.mode`, read in exactly three places (`MainMenu` sets it, `PlayerSelect` and `SkinSelect` branch on it).
- **Pile Up bricks have a terminal velocity, and it is a gameplay decision rather than a physics tweak.** Under plain gravity a brick arrives at the stack fast enough to demolish it, which made careful play measurably no better than terrible play (§5/§8 session S). Capping the fall is what makes the landing something a tower can absorb, so `MAX_FALL_SPEED` is the constant that decides whether skill pays off at all. It is deliberately *not* solved with damping or a lower gravity scale, both of which would also make the brick drift down sluggishly on its way; the cap only bites at the bottom of the fall.

- **The bot drives the game's own input entry points; it never synthesises `InputEvent`s or touches the `Input` singleton.** Faking a key press is global: every board bound to that key would see it, and it would fight a real player's fingers. Routing both the keyboard and the bot through `PlayerBoard._steer_held()` / `_press_steer()` / `_press_confirm()` instead means there is exactly one implementation of each action, a bot-driven board runs byte-identical physics to a human-driven one, and handing a board over mid-round costs nothing. See §5 session J and §7.
- **Bot difficulty is foresight, not information.** Every profile sees the same board; EASY differs from HARD in how far ahead it plans and how late and sloppily it acts. A bot that is handicapped by being fed worse data ends up erratic rather than beatable, and a bot with no handicap at all is not fun to race.
- **Skill choice never pauses the round and never expires.** Both were tried and explicitly rejected by the user in session F — see §5. The standing rule going forward: `choosing_skill` must never gate `PlayerBoard._process()`'s steering/traffic/distance logic, and must only be cleared by `_resolve_skill_choice()` (an actual pick), never by a timer. If a future skill needs a time-limited effect, that belongs in the *skill's own* implementation once skills exist, not in the choice-presentation system itself.
- **Skill-choice input uses dedicated keys, not the existing steer keys.** The first draft reused `key_left`/`key_right` to pick, which read naturally against the left/right icon layout but forced the player to stop steering to choose. `key_skill_opponent`/`key_skill_self` are separate bindings for exactly this reason — see §5 session F and §7.
- **`SkillPickup` reuses `PlayerBoard.obstacle_container`'s existing per-frame movement/despawn loop and lane-occupancy convention (`lane`/`speed_mult` meta) instead of a parallel container/loop of its own.** Since a pickup's motion (scroll at road speed) and despawn condition (past `board_height + margin`) are identical in shape to traffic's, giving it its own container would have meant duplicating that loop for no benefit — this is the same "don't duplicate a system you can parametrize" instinct as `Road`/`LaneDivider.render_margin` in §6/§7's existing entries.

- **Relative-speed model for traffic, not absolute multipliers.** An obstacle's screen-space closing speed must always be expressed as *(reference scroll rate − vehicle's own forward speed)*, never as an independent multiplier applied to the base speed. This is the single most important invariant introduced this session — see §7.
- **Per-vehicle-kind speed ranges instead of one global range.** Chosen over a single flat range because (a) it fixes the >1.0 bug structurally — every kind's range is authored below 1.0 — and (b) it adds gameplay texture "for free" (heavy vehicles feel slow/easy to catch, motorcycles feel nimble) without extra systems.
- **Dividers keep their own independent timer rather than reading a board's speed directly.** This predates session A's changes and was not restructured, only patched (see §7 for why this is a known fragility, not an endorsement).
- **Real cropped-texture tiling for road/median instead of procedural drawing.** Predates session A (commit `374f392`); kept as-is. Rationale (from the commit): both textures come from the same source art so grass/guardrail styling matches exactly, and it looks better than procedural shapes.
- **Drift session state and drift grip state are two separate booleans (`is_drifting` / `drift_sliding`), not one.** Session B tried a single flag first — it's simpler on paper, but conflates "should the trail/nose-lead be active" (a UI/feel question, answer: yes for as long as you're steering at all) with "should grip currently be reduced" (a physics question, answer: only while the slide hasn't caught up yet). They have different natural lifetimes and different end conditions; forcing them into one flag is what caused attempts 2's regression in §5.
- **`target_vx` tie-breaks toward the most-recently-pressed key on overlap, not neutral.** Treating "both steer keys held" as 0 (the original behavior) seems like the obviously-correct default, but it isn't what a fast key switch on a real keyboard produces — see attempt 5 in §5. Any future rework of the steering input must preserve `steer_priority` or reintroduce this exact bug.
- **Boost is hold-to-drain, not press-to-burn-all.** First implementation (session C, pass 1) spent the entire bar on a single keypress for a fixed-duration boost. User explicitly wanted partial spending, player-controlled amount, and unused charge preserved — a resource you dip into, not an ability you trigger. This is a real design requirement, not just a numbers tweak; don't revert to a fixed-consume-all model without re-confirming with the user.
- **Boost's speed tier is re-read from *current* charge every frame, not locked in at activation.** Considered locking the multiplier to whatever tier the bar was in when `confirm` was first pressed, but re-reading it live means a long burn from a full bar naturally tapers off in strength as it drains through the tiers — matching "a full bar should last longer" (more charge = more sustained time at *some* level of boost, front-loaded toward the strong end) without needing a separate duration-per-tier system.
- **Lane changes only commit when the target lane is verified clear, never on a fixed schedule.** Considered just picking a random direction at the trigger point, but that risks an obstacle sliding straight through another car — `_lane_clear_near()` gates the decision so a blocked lane silently cancels the change instead. This is what keeps "more chaotic" from becoming "unfair"; don't remove the safety check to simplify the state machine.
- **Camera zoom fits the widest player count instead of being tuned for one and left fixed.** A fixed zoom (the pre-session-E state) looks right for whichever player count it was tuned against and silently clips every other count that's wider — there's no visual warning, lanes just fall outside the viewport. Computing `zoom = min(CAMERA_ZOOM, viewport_width / total_width)` per build means the ceiling (`1.15`, the preferred feel) is preserved wherever it fits and only relaxed where it must be, rather than picking a single compromise value that's slightly wrong at every player count. See §5 session E.
- **`render_margin` / `vertical_margin` is plumbed through as an explicit value computed once in `Main`, not re-derived independently in `Road`, `LaneDivider`, and `PlayerBoard`.** Each of those needed to know the same "how far past the board's own bounds can the camera see" number for a different purpose (tile coverage, obstacle spawn/despawn), but only `Main` has both the viewport size and the final chosen zoom to compute it from. Passing the one computed value down (rather than, say, having each script independently query `get_viewport()` and guess the current zoom) keeps them from ever disagreeing — the exact class of duplication risk that `BASE_SPEED`/`SPEED_PER_SECOND` did fall into and that session K had to undo, deliberately avoided here from the start.
- **`body_color` on `PlayerBoard` is no longer just a placeholder-shape fallback.** It predates session C as an unused fallback color for `Car.gd`'s placeholder `Polygon2D` (real skins always use a texture, which hides the placeholder — see §12). Session C repurposed it as the actual per-player theme color for boost UI and exhaust flames by having `Main._build_boards()` populate it from the new `GameSettings.skin_colors` array. If skin selection is ever reworked, `skin_colors` must stay in lockstep with `skins` (same index, same length) or boost/exhaust colors will mismatch a player's actual car.
- **Tank Mode's muzzle flash/smoke are independent overlay sprites anchored at the muzzle every frame, not frames of a single swapped "tank body" animation.** The source sheet's tank render isn't pixel-aligned across its own cells (see §5 session G, §8) — an overlay that re-anchors itself at a known world point (`_muzzle_position()`) every step is correct regardless of where the effect happened to sit in its source cell, whereas a composite swap would have inherited any of the sheet's own misalignment as visible jitter. If a future skill needs a similar "swap the player's texture through a sequence" effect, check whether the source art is a true pixel-aligned animation export first — if it isn't, prefer this overlay-anchoring pattern over trusting the sheet's internal layout.
- **The tank's cannon shell is a real traveling sprite with `cannon_ready` restored on arrival, not an instant hit gated by a fixed cooldown.** Tying the "can I fire again" state to the shell's own tween completion means the fire rate is naturally paced by shot distance (a close target reloads faster than a miss that flies to the top of the board) without a separate timer to keep in sync with the animation.
- **The Taxi is a traffic vehicle whose AI only chooses `speed_mult` and lateral steering — it never moves its own `position.y`.** The first version did drive its own y (chasing the player's coordinate), which is precisely what made it phase through other cars, and it is not repairable by adding collision checks to that path — see §5 session I and §8. Forward motion must stay in `_process`'s shared obstacle loop, identically to every other vehicle. `_update_taxis()` is deliberately called *immediately before* that loop, so "decide, then be moved by the shared rule" stays the visible order of operations.
- **A negative `speed_mult` is legitimate and is how the taxi overtakes.** `speed_mult` is a closing fraction of road speed, so negative simply means the vehicle's own forward speed exceeds the player's — an ordinary overtake, and the only reason the taxi can arrive from behind at all. The §7 invariant bounding `speed_frac_max` below `1.0` constrains the *slow* end (a vehicle closing faster than a parked object would be driving backward); it says nothing about the fast end and must not be misread as forbidding negatives.
- **The Taxi's menace is expressed as tighter tolerances inside the traffic rules, never as exemptions from them.** `TAXI_SIDE_GAP` (28px vs traffic's 200px `LANE_CHANGE_SAFE_GAP`), `TAXI_SIGNAL_WARNING` (0.55s vs 1.3s), and the fakeout-signal roll are all "plays nastier", not "plays outside". Session N moved all three toward the lenient end without changing that shape, which is the point: "how aggressive is it" is a set of tolerance values you can turn, and it stays a tuning question exactly as long as nobody grants an exception. The only entity it is ever allowed to be unfair toward is the *player*; toward other traffic it obeys clearance and car-following limits strictly. If a future opponent skill needs to feel unfair, prefer this shape — tighten the tolerances — over granting an exception, since exceptions are what made it stop reading as part of the traffic.
- **The taxi's safety checks must veto a *frame of movement*, never cancel an *intention*.** Session L's `_taxi_lateral_blocked` refuses only the current frame's sideways step, and only when that step closes on a car alongside; `tx_target_x` is left alone. The version before it wrote the taxi's current x back into `tx_target_x` on any blocked frame, which abandoned the lane change until the next decision — and since traffic streams past a taxi doing -0.5 constantly, that meant almost every lane change died part-way and the taxi drifted around with no intent. Equally, the "only when it closes" half is not optional: a plain "is this x clear" test vetoes every direction for a taxi that is already boxed in, including its way out, welding it in place.
- **The taxi may not overtake within its lane, so its lane choice has to be gap-hunting, not random.** `_taxi_follow_limit` is what keeps it from driving through the car in front, and it spawns *behind* all the traffic — so a randomly chosen lane is usually just a different car to sit behind. `_taxi_lane_headroom` scores lanes by open road ahead. If this is ever reverted to a random pick, the taxi goes straight back to spending its life pinned at the bottom edge of the board.
- **Every vehicle-destruction path shares one `_play_destruction_effect()` function, parameterized on frame set + reference width, instead of each destruction method hardcoding its own animation.** User explicitly asked that future skills adding new ways to destroy a car get their own new animation, not a copy-pasted variant of this one — the parameterization (`frames`/`source_peak_width` default to the standard explosion) is what makes that a call-site choice later rather than a refactor. See §5 session H.
- **Tank Mode's forward-speed effects (the recoil dip) go through `current_speed()`, the same single value that drives both `distance` and every obstacle's on-screen speed.** This project has no separate "player's own forward velocity" — the whole forward-motion illusion is `current_speed()` shared by the board's scroll and its traffic (see the relative-speed model decision above). So briefly multiplying it down on a cannon shot necessarily reads as the *whole board* slowing for an instant, not just the player — that's an accepted, deliberate side effect (a little "impact" beat), not a scoping bug; don't try to give the player an independent speed variable just to avoid it.

## 7. Assumptions, constraints, conventions that must be preserved

- **Every read of a player's input must go through `PlayerBoard._steer_held()` / `_press_steer()` / `_press_confirm()` / `_release_confirm()`.** A new `Input.is_physical_key_pressed(key_...)` or a new key branch written straight into `_unhandled_input` is invisible to `BotDriver`, so a bot-driven board would silently stop being able to do whatever that input controls. `_unhandled_input` returns early for a bot-driven board on purpose (`if bot != null: return`) so the two can never both drive the same car.
- **In `BotDriver`'s lane scoring, `BLOCKED_PENALTY` must stay decisively larger than the worst dead-end score (`horizon * DEAD_END_WEIGHT`).** Steering through an occupied lane is a certain crash; sitting in a lane that runs out is only a probable one. When these two scales overlapped, a trapped bot answered by driving straight through the car next to it (§5 session J, fix 3).
- **`BotDriver` must keep room (immediate time-to-impact) as the headline term and survival as the veto, not the other way round.** Survival saturates at the horizon, so as a primary score it says the same thing about every escapable lane and lets the tie-breakers park the bot in a lane until it dies there (§5 session J, fixes 1-2).
- **`BotDriver.board` is deliberately untyped.** `PlayerBoard` names `BotDriver` as a field type; naming `PlayerBoard` back would be a cyclic class reference. Anything the bot needs from the board is reached dynamically, and the few physics values it shares (`car_size()`, `steer_bounds()`, `steer_top_speed()`, `steer_coast_time()`) are real methods on `PlayerBoard` used by `_process` too — never copies of its constants, which is the duplication trap `BASE_SPEED` fell into before session K centralized it in `SpeedRamp.gd`.
- **`choosing_skill` must never gate/pause `PlayerBoard._process()`, and must only be cleared by an actual pick (`_resolve_skill_choice()`), never by a timer.** Both a pause-while-choosing design and a timed auto-expiry were built, playtested, and explicitly rejected by the user in session F (see §5, §6). Don't reintroduce either without re-confirming — this is a real, twice-stated design requirement, not a numbers tweak.
- **`SkillPickup` nodes live in the same `obstacle_container` as traffic and must keep setting `lane`/`speed_mult` meta the same way traffic does.** `_lanes_used_near_top()` (shared by `_spawn_obstacle()` and `_spawn_skill_pickup()`), the per-frame movement/despawn loop, and `_lane_clear_near()` (used by lane-changing traffic to avoid merging into an occupied lane) all rely on every `obstacle_container` child exposing these two meta keys, regardless of whether it's a `Car` or a `SkillPickup`. If a new kind of obstacle-container child is ever added, it needs the same two meta keys or it will break these shared scans.

- **Every vehicle sprite faces up: the front of the vehicle sits at -y, the top of the image.** Traffic drives away from the player (who is at the bottom of the board), so a sprite drawn cab-down drives backwards through the entire field. Supplied sheets follow no convention — `kamyon.png` was drawn cab-at-the-bottom and shipped reversed (§5 session Q) — so check facing against an existing sprite when importing art, **by looking at it**. There is no reliable automated test; the plausible one was built, measured and rejected (§8).
- **New art for this project must be derived from, or matched to, the existing fleet's own rendering style — matching size and placement is not enough.** Two independently-sourced taxi sprites were rejected by the user as looking "added afterwards"; the cause was art lineage, measurable as mean value 0.73 vs the fleet's 0.42-0.59 and 13.5% dark pixels vs 20-37%, and visible as hard-outlined flat pixel art of a boxy vehicle against soft-shaded rounded renders with gray-blue tinted glass. `sprites/cars/taxi.png` is therefore a *derivative of `sedan_yellow.png`* (checker band + roof lamp painted on in the fleet palette), which makes belonging structural. Prefer this approach for any future vehicle art; if a genuinely new asset must be used, compare its value/saturation/dark-pixel statistics and its outline-and-shading technique against the fleet before assuming it will fit.
- **Don't Crash's life pips must stay behind everything the player's car emits, and that is a `z_index` rule, not a layout one.** They are `Sprite2D`s at `HEART_Z` (-2) rather than draw calls in `PlayerBoard._draw()` precisely because `_draw()` happens at the board's own z 0 — in front of the boost exhaust and Nitro's ground shadow, both z -1. Moving the row into `_draw()` "to keep the HUD in one place" would put a row of hearts over the flames coming out of the car's back end. Any future tail-pipe effect should sit at z -1 or above and will then be correct by construction.
- **`_layout_hearts()` must read `car_x`, never `player_car.position`.** That position carries Nitro's lift (105px up the board) and its per-frame shudder. Pips that follow it ride inside the comet for the whole flight and vibrate the rest of the time; anchored to the road, Nitro's lift is what opens the gap the effect plays out in. This is the whole answer to "put them behind the car but leave room for the nitro".
- **`CAR_BOTTOM_MARGIN` is the car's *rear bumper* line and both the car and the heart row hang off it.** `ground_y` subtracts half the car's own height on top of it, so the bumper lands on the same y whatever kind the player is currently driving (Tank Mode's taller footprint included) — which is what makes `_heart_row_y()` a constant rather than something that shifts under the player mid-round. It was two hardcoded `24.0`s before session W; don't add a third.
- **The heart pip is tinted per pixel, not with `modulate`.** Multiplying the whole sprite by a car colour turns the red body muddy and flattens the white highlight into the same hue as everything else, leaving only the black outline intact. `_tint_heart_texture()` re-hues only pixels at or above `HEART_BODY_SAT` and leaves the hue-less outline and highlight alone — that separation is what keeps a pip legible against grey asphalt, and it is why `extract_heart.py` normalises the body's peak value to 1.0 rather than the game side carrying a constant about the PNG.
- **A hit's three timers stay separate: pass-through (`INVULN_DURATION`), the slow-down (`INVULN_SLOW_DURATION`) and the blink's own fade-out.** The pass-through window has to outlast the traffic the player was already buried in or the next life goes to the car right behind the one that just hit them; the slow-down is deliberately much shorter, because being unable to move is a worse punishment than losing the life. Collapsing them onto one number is what makes a crash feel either free or fatal, with nothing in between.
- **The invulnerability slow-down is applied in `current_speed()`, never to `elapsed`** — the same rule boost, tank recoil and Nitro already follow, and for the same reason: a crash should cost the player distance, not rewind the shared difficulty ramp.
- **`Main` is the only relay for cross-board effects; `PlayerBoard`s never reference each other.** A board emits `opponent_skill_triggered` and `Main._on_opponent_skill_triggered()` fans it out to every board except the source (via `receive_opponent_skill()`). Keep future opponent skills on this path rather than introducing direct board-to-board references — the boards are built dynamically per player count and deliberately know nothing about their siblings.
- **Godot 2D coordinate convention: +y is down.** Any code that scrolls the road, median, or traffic must treat *increasing y* as "moving toward the player" (who sits near the bottom of each board). This is easy to get backward (as fix #2 shows) — always sanity-check the sign against `PlayerBoard._process`'s obstacle movement line (currently `child.position.y += speed * speed_mult * delta`), which is the canonical "forward" direction.
- **Invariant: every `TRAFFIC_KINDS` entry's `speed_frac_max` must stay below `1.0`.** This encodes "no traffic vehicle may close in on the player faster than the road itself scrolls." Violating it (as the pre-session code did with 1.28) reintroduces the "driving backward" visual bug. If you add a new vehicle kind, give it `speed_frac_min`/`speed_frac_max` in roughly the `[0.3, 0.95]` band and keep the max end away from `1.0` (a small safety margin, not just `< 1.0` exactly, keeps the effect visually convincing even at high round speeds).
- **`Road._draw()` and `LaneDivider._draw()` must use the same tile-anchoring convention.** They currently both use `y = scroll - tile_h`. If one is changed without the other, the road and median will visibly scroll at different apparent rates/directions again (this is exactly bug #2 in miniature). Treat these two functions as a matched pair.
- **`Main._build_boards()` is the single source of truth for `vertical_margin`/`render_margin` (see §5 session E, §6).** `Road`, `LaneDivider`, and `PlayerBoard` all just store and use whatever value they're given — none of them compute it independently. If camera framing logic is ever touched, keep this one-way flow (`Main` computes → pushes down) rather than letting a script derive its own guess from `get_viewport()`, or the top/bottom render coverage can silently fall out of sync with the actual camera zoom.
- **Camera zoom (`Main._build_boards()`) must never exceed `CAMERA_ZOOM` (1.15), only go below it.** `zoom = min(CAMERA_ZOOM, fit_zoom)` — this is intentional: `CAMERA_ZOOM` is the tuned "good" feel confirmed by the user, and `fit_zoom` only kicks in to prevent boards from being clipped at wider player counts. If a future change needs a different zoom ceiling, update `CAMERA_ZOOM` itself rather than the `min()` — flipping it to `max()` or dropping the cap would let the game zoom in tighter than intended at narrow player counts, which was never asked for.
- **Scrolling scenery must derive its distance from a board's odometer, never integrate its own.** This is the session-O invariant and it replaces the old "remember to reset every timer" rule, which was the weaker version of the same idea. A parallel timer running the same ramp is *not* in sync with the road: `PlayerBoard.current_speed()` applies boost and tank-recoil multipliers on top of the ramp, and freezes outright when the player crashes, so any element integrating `SpeedRamp` independently drifts permanently on the first boost and unboundedly on the first crash. `LaneDivider` shipped exactly that bug for four sessions. If a new decorative element scrolls, give it a board to follow (integrating the *delta*, so switching sources never teleports it) and set `process_priority` above the boards' so it samples a fresh odometer.
- **`Main._start_round()` must still reset every board AND every divider**, and a follower's `reset()` must re-prime its source odometer rather than nulling it — a null source takes its baseline from an already-advanced odometer and permanently drops a frame of distance (see §5 session O).
- **The difficulty ramp lives in `SpeedRamp.gd` and must not be re-derived anywhere else.** `BASE_SPEED`/`SPEED_PER_SECOND` used to be copy-pasted into both `PlayerBoard.gd` and `LaneDivider.gd`, kept numerically identical by hand; session K removed the duplication. Tune the curve in `SpeedRamp.gd`; do not add a local speed constant to a caller. What *does* legitimately live in `PlayerBoard` is its own temporary multipliers (boost, tank recoil), because they are per-board state — and neither touches `elapsed`, so the permanent ramp stays independent of them. **But note what centralising the ramp did and did not buy**: it stopped the road and the median disagreeing about the *curve*, and session K's write-up treated that as the end of the desync. It wasn't, because the multipliers above sit outside the ramp entirely — see §5 session O. `PlayerBoard` is now the ramp's only caller.
- **A nitro frame group's crop size is load-bearing, not tidiness.** Every frame in a group was cropped to one common size, and every comet frame to one common head slot. Re-cropping them to their own bounding boxes would destroy the size progression that *is* the animation (stage 1 grows from sparks to a full ring; if every frame is cropped tight and scaled to fill, they all render the same size), and a head position that moved between frames would make the whole effect jitter against the car as they advance. It is also why one `aura_scale`/`beam_scale` covers a whole sheet.
- **Nitro must keep applying its multiplier to `current_speed()` and never to `elapsed`** — the same rule boost and tank recoil already follow, and now the third multiplier sitting outside the ramp. It is also the reason `LaneDivider`'s session-O odometer-following design was necessary rather than merely tidy: a 2.85x surge is a bigger divergence than boost ever produced, and any scenery integrating `SpeedRamp` on its own would jump permanently out of phase the first time someone used the skill.
- **A skill's glyph must come from the roll, not from the pool's first member.** `_roll_pending_skills()` decides both sides when the choice *appears* and `_resolve_skill_choice()` only applies what was already rolled. The old code rolled at pick time and drew hardcoded tank/taxi art, which was invisible-as-a-bug only because both pools held exactly one entry. Any new skill needs a `SKILL_GLYPHS` entry or its icon draws bare.
- **A held Pile Up brick must stay out of the collision world, not merely frozen, and every move it makes must be shape-queried first.** `TowerPiece.set_held(true)` sets `collision_layer`/`collision_mask` to 0 as well as `freeze`. A frozen body is still solid, and steering writes the brick's transform every frame, so a merely-frozen brick would bulldoze the top of the tower it is about to land on. Because it is outside the world it also generates no contacts, which is why `TowerMode._blocked()` exists and why *all three* axes go through it — sideways, rotational and downward. Dropping the check on any one of them puts a brick inside the tower. The counterpart invariant is `SPAWN_CLEARANCE`, which must stay above the largest half-extent any brick can have (2 cells, a vertical I piece) or a brick could appear already overlapping the stack, silently.
- **In Pile Up, being counted as fallen and being freed are separate events and must stay separate.** A brick is scored the moment it passes `LOST_Y` (just under the slab, where nothing can rejoin the tower) and freed at `DESPAWN_Y`, far off screen. Merging them — culling only at the far plane — makes every turn wait for debris to fall up to 900px before the world counts as at rest, which fired the settle timeout on 6.5% of turns until it was split (§5 session S). Doomed bricks must also stay excluded from `_everything_at_rest()` and `_recompute_stack_top()`.
- **`TowerMode` must treat a brick that descends past `LOST_Y` as landed.** The aim bound deliberately allows a brick to be walked entirely off the slab, and under the self-descending model such a brick has nothing to land on — without this it descends forever and the turn never ends.
- **`TowerMode` resolves a turn on the whole world coming to rest, never on the dropped brick landing.** The interesting case in the mode is a brick that settles innocently and shoves the tower over seconds later; resolving on contact would score that against whoever drops next. If settling ever feels slow, the knob is `SETTLE_LINEAR`/`SETTLE_ANGULAR`/`SETTLE_HOLD`, **not** `TowerPiece`'s damping, which exists to take the ring out of a landing and not to end turns.
- **`TowerMode`'s kill planes must stay fixed world values, never camera-relative.** The camera pans up with the tower, so a kill plane defined against the camera would eventually rise above the platform itself and cull the bricks the tower is standing on. `KILL_Y` sits below the platform in world space and stays there.
- **`TowerPiece` collision is merged rectangles, not one box per cell.** Four unit boxes in a row present internal edges that a neighbouring brick's corner can catch on, which reads to a player as the tower snagging on nothing. Every tetromino decomposes into one or two rectangles (`GameSettings.TETROMINOES[i]["boxes"]`), so the merged form costs nothing.
- **`TowerGround` and `TowerBackground` must keep agreeing about `GROUND_LINE_PX`, and only `TowerGround` may track the camera exactly.** They are two cuts of one image: the backdrop anchors itself so that row lands where the near-ground band is drawn, which is the only place the two are required to line up, and it is why the seam is invisible at the start of a match. Giving the near ground any parallax would slide the outcrop out of the ground it grows from; giving the backdrop none would leave a flat picture that says nothing about climbing.
- **`TowerGround` must stay after `PiecesContainer` in the scene tree.** It is a foreground layer — bricks falling off the tower are meant to disappear *behind* the grass, which is also what hides their despawn. Moved earlier it becomes just another piece of background and bricks pop out of existence in mid-air.
- **In Pile Up, touching the tower is not the same as being inside it, and `QUERY_SKIN` must stay half `TowerPiece.FOOT_INSET`.** Every command lands on an exact half-cell lattice, so a brick's faces line up precisely with the stack's — and Godot counts an exactly-touching pair of rectangles as a collision. `_blocked()` therefore trims its query boxes by `QUERY_SKIN`, *across the direction of travel only*, so a grazing contact cannot refuse a move while a landing is still detected at the exact pixel of contact. The feet in `_supported()` are inset by half of `FOOT_INSET` per side, and the equality between the two is load-bearing: it is what guarantees that anything deep enough to refuse a descent is also deep enough for the feet to find, leaving no band of geometry in which a brick can be blocked and unsupported at once. Move one number without the other and bricks start hanging in mid-air again (§5 session T).
- **In Pile Up, "can the brick move down" and "is the brick supported" must stay two separate questions.** `_blocked()` decides whether a move is legal; `_supported()` decides whether the turn is over. Collapsing them back into one ends a brick's turn the moment it brushes the flank of a taller stack, leaving it limp in mid-air (§5 session S). `LandingProbe` fails on exactly this.
- **`_supported()`'s foot probes must be built against the world axes, never baked into the brick's local frame.** "Underneath" is a property of the world; a foot offset stored in the brick's own frame rotates with it, so a half-turned brick probes upward and never finds the floor it is standing on. This shipped once and silently disabled support detection on every brick that was not upright.
- **A Pile Up turn ends when something is *underneath* the brick, and at no other time.** Not when it can no longer move down, not on a timer. `WEDGE_GRACE` exists only so a turn cannot hang forever and must stay long enough never to fire in ordinary play. `LandingProbe` asserts this directly, and distinguishes the three legitimate endings (supported, backstop, steered off the platform) from the one that is a defect (ended on a flank with the backstop unexpired).
- **A probe that models a passive player is not exercising the input paths.** `LandingProbe` set its aim once per brick and reported clean results for two passes while never once pressing a brick against a flank — the exact case it existed to check. Half its turns now lean hard on a direction for the whole descent. Any future Pile Up harness needs the same: a player who *does nothing* reaches almost none of this mode's interesting states.
- **Any Pile Up probe must seed the *global* RNG, not just its own `RandomNumberGenerator`.** `TowerMode._begin_turn()` picks bricks with `randi()`, so a probe that seeds only its own generator reproduces the aim and nothing else — two runs of the same "seed" disagreed by an order of magnitude before this was fixed, which makes every result unfalsifiable.
- **Pile Up's dash must stay observably different from two ordinary taps, not merely different in intent.** It covers `DASH_CELLS` at `DASH_FOLLOW_SPEED` with an afterimage; two taps cover the same ground at `FOLLOW_SPEED` with none. The distance is deliberately the same, so *speed and trail are the entire difference* — remove either and the mechanic silently stops existing while every line of it still runs correctly (§5/§8 session S). **This has to hold on every press, not on average**: session U found the fast follow being cancelled by a hold-repeat tick landing mid-dash, so one press in six ran the whole cell at `FOLLOW_SPEED` while the code around it stayed correct. `DashProbe` fails if the dash's *intent* stops differing; `DashFeelProbe` fails if the brick's *measured movement* does, in any phase of the repeat tick — and only the second of those could see that bug.

- **A shared node between the two modes must hold no game state and must not own a clock.** `Countdown` is the only one, and it stays shareable because it does neither: freezing is the caller's, and `advance(delta)` is called from Main's `_process` and TowerMode's `_physics_process` because those are the loops those two modes' own state lives in. Ticking it from its own `_process` measurably moved Pile Up's first brick off the physics frame (§5 session U). Anything else that ends up shared has to clear the same bar, or it belongs in each mode separately.

- **Pile Up's dash chord must be worth the same in both orders.** Holding a direction and pressing dash, and holding dash and pressing a direction, are the same gesture; which one a player reaches for depends on where the brick is and which way their hand was already going, and they should never have to plan it. `_press_dash()` and `_press_direction()` are the two entry points and both must end in `_dash()` with the same direction and the same distance. `DashFeelProbe` compares them directly and fails if they come apart.
- **Anything Pile Up draws over its backdrop must be dark, not light.** The mode's first version drew white-alpha guide lines and white-alpha HUD plates against the project's dark clear colour; once `TowerBackground` put a bright pixel-art sky behind them they vanished. A HUD that only exists on a dark background stops existing the moment the background changes.
- **`sprites/blocks/*.png` must be regenerated with `scripts/dev/extract_blocks.py`, not re-cropped by hand.** The exported cells are square by construction and `TowerPiece` relies on that: it scales a brick by the single factor `cell / 100` and places cell-unit collision rectangles against it. A hand crop would reintroduce the source sheet's own 4-14% per-piece aspect inconsistency, and the collision would silently stop lining up with the art.
- **No automated test suite exists.** `godot --headless --quit` only catches GDScript compile/parse errors — it does not verify gameplay behavior, timing, or visual correctness. Every bug in §5 was diagnosed by reading the physics/input logic, not by running a test. **The user's explicit workflow preference: always let them playtest a change in the editor before committing** — do not commit right after an edit just because headless validation passed. Wait for explicit confirmation (e.g. "it's great", "push it") before running `git commit`.
- Commits in this repo explain *why*, with the physical/visual/input reasoning spelled out (see commit history). Keep that convention — this codebase has a history of subtle sign/reference-frame/input-timing bugs where the reasoning is what prevents regressions.
- **`DRIFT_CONVERGE_FRAC` (0.88), `DRIFT_RELEASE_GRACE` (0.14s), and `REVERSAL_THRESHOLD` (140) are feel-tuned constants, not derived values.** If drift feels too sticky, lower `DRIFT_CONVERGE_FRAC`; if switching direction still occasionally drops the session, raise `DRIFT_RELEASE_GRACE` slightly — but note session B's actual bug (steer_priority / both-keys-held) was independent of this constant, so don't assume a "still drops sometimes" report is this timer before checking `target_vx` computation first.
- **Any code path that can `Tween.kill()` a tank-mode animation tween (`fire_anim_tween`) must also explicitly free `fire_effect_sprite` itself, not just rely on the tween's own final callback.** Killing a `Tween` skips every `tween_callback` that hadn't fired yet, including the one responsible for freeing the overlay sprite — see the session G leak in §5/§9. Both current call sites (`_deactivate_tank_mode()`, `start_round()`) do this; if a third path is ever added that can end the animation early, it needs the same explicit cleanup.
- **Every place that positions/sizes the player's own car must read through `PlayerBoard._current_kind()`, not hardcode `PLAYER_KIND`.** Since Tank Mode temporarily changes the player's own footprint (`TANK_KIND`, a different aspect ratio than `PLAYER_KIND`), anything that assumed a fixed player size (dash's shoulder clamp, drift trail width/offset, the skill-choice icon's offset from the car) would silently use stale (normal-car) dimensions while transformed if it read `PLAYER_KIND` directly. `start_round()`/`_deactivate_tank_mode()` are the two deliberate exceptions (they explicitly want `PLAYER_KIND` — resetting *to* the normal car regardless of whatever `tank_mode_active` still says at that instant).
- **Raw PNGs supplied for this project cannot be assumed to have a real alpha channel just because they visually look like they have a transparent background.** Both `tank.png` and `tank_animasyon.png` had a checkerboard pattern *baked into their opaque RGB pixels* (common output of tools that render a transparency preview and then flatten it) rather than an actual alpha channel — `sips`/PIL both reported plain `RGB`. Always check `Image.open(path).mode` (or `sips -g hasAlpha`, though it has known reporting quirks) before trusting a source asset's background is really transparent, and if it isn't, flood-fill the background color inward from the image's own border (not a flat global color-key) so pixels that merely *resemble* the background color from deep inside the subject's own silhouette are left alone.

## 8. Approaches that were tried and did NOT work (don't repeat these)

- **Cutting Pile Up's spawn height to make turns faster (session T).** The descent was measurably where a turn's time went, so both of the numbers that produce it were cut at once — `DESCEND_SPEED` 58 → 105 and `SPAWN_CLEARANCE` 7 → 5.5 cells. The speed was right; the height was not, and it was reported from play within one round as bricks starting too low. **Height and speed produce the same seconds and do not do the same job**: the distance above the stack is how much of the fall the player can see coming and plan against, so shortening it does not read as a quicker turn, it reads as a brick that appears already half way down. Restoring it cost 0.5s of the saving and kept all of the rest — which is the check worth applying next time two constants look like one knob: change them one at a time and see which one the improvement actually came from.
- **Assuming a Pile Up brick that has left the tower falls away from it (session T).** The turn waits for the world to stop, and most of that wait is one dislodged brick tumbling the full height of the tower to reach `LOST_Y` — 3.74s against 1.25s on turns where nothing fell. The obvious saving is to score such a brick the moment it is clear of the platform's footprint, since it plainly cannot land there any more. Measured, **579 of 689 bricks that went clear touched the tower again afterwards**, and the change would have bought 0.72s. Debris does not leave, it slides down the outside of the tower hitting it on the way, and resolving the turn early would have billed those hits to the next player. The general form is the one this mode keeps producing: *"it is obviously gone" is a claim about a trajectory, and trajectories have to be measured, not pictured.*
- **Aiming a probe with `randf()` at a game that moves on a lattice (session T).** `TowerProbe` and `LandingProbe` steer bricks to random real positions, which sounds strictly more thorough than testing a handful of fixed ones. It is the opposite where the geometry is discrete: every command in Pile Up is a multiple of half a cell from x=0, so a player lines a brick's faces up *exactly* with the stack's faces on almost every turn, and a continuous random aim essentially never does. Godot's `intersect_shape` calls two exactly-touching rectangles a hit, so bricks were being refused their next step down by contacts of literally zero depth — constantly in play, never once in 500+ probed turns. **A probe must move the way the input moves.** Where the input quantises, randomising past the quantum tests a game nobody is playing.
- **Testing for a tunnelled brick by asking where it *is* rather than where it *went* (session S).** "Is the brick below the platform while still horizontally inside the platform's footprint" sounds like a definition of passing through it, and it reported 1 tunnelled brick in 189 turns. It was a false positive: a brick that legitimately fell off the edge can be knocked back inward by the next brick on its way down and end up in exactly that state. The sound test is the *trajectory* — the slab is solid edge to edge, so a brick can only reach the void beneath it by taking its centre past the edge first, and one that is now below the slab having never reached the edge did not go round it. With that test tunnelling measures zero everywhere. Generalises: a "was it ever in this state" test and a "how did it get into this state" test are not interchangeable, and the cheap one manufactures bugs that then get "fixed".
- **Putting a timer on the wedge state (session S).** The flank fix kept the player's control while a brick was pressed against a taller stack — but only for 1.5s, after which it was taken anyway. Short enough to fire during ordinary placement, so it reproduced the original complaint in a subtler form: control still vanished mid-placement, just later. A backstop that fires during normal play is not a backstop, it is a rule; either make it long enough to be unreachable or do not have it.
- **Deciding a Pile Up brick had landed because it could not move down (session S).** The two really do coincide most of the time, which is what makes it convincing: a brick that cannot descend has usually arrived. But it is also true of a brick pressed against the *side* of a taller stack, and there the turn ended with the brick hanging in mid-air over a visible void. Reported as "player looses control of the brick before it touches other bricks", which is precisely what it was.
- **Measuring a Pile Up landing after `release()` (session S).** By then physics has moved the brick *and* put it back in the collision world, so re-running the landing query reports the brick intersecting itself. It produced a confident 42px mean gap that was pure artifact and pointed the investigation at the tower instead of at the probe. **A measurement taken after the state you are measuring has already changed is not a measurement of it.**
- **Measuring that gap under the brick's lowest point (session S).** The obvious definition, and wrong: J, T, S and Z each decompose into two boxes a cell apart in depth, so a brick resting on its shallower box legitimately has a cell of air under the deeper one. The metric reported a 38px failure for an ordinary correct landing. The right question is the gap under the *nearest-supported part*, per box.
- **Letting a shared UI node tick itself in `_process` (session U).** `Countdown` self-driving looked obviously right — it is a HUD element, HUD elements run on idle frames. But Pile Up's model lives in `_physics_process`, so the signal that starts the first turn arrived from an idle frame and the first brick was created off the physics step. Every assertion still passed; the probes' *numbers* moved and stayed moved. **A node that decides when something happens owns a clock, and a clock is not a shareable thing between two modes that run on different ones.** Passing `delta` in from the owner costs one line and one call site each.

- **Cancelling an in-flight dash to stop a hold-repeat inheriting its speed (session S, found session U).** `_update_hold_repeat()` cleared `dash_active` on every tick, which is the obvious way to keep a held direction from turning into a permanent fast mode. It also runs before the follow in the same frame, so a tick landing during the two frames a dash takes stripped the dash of the speed that *is* the mechanic — measured at one press in six with no fast frame at all. **A flag shared by two systems that run in the same frame belongs to whichever one runs first, whatever the code reads like.** The fix was to give the dash its own destination (`dash_target_x`) so the two systems stop sharing a flag at all, rather than to reorder them or to make the cancel conditional.

- **Inferring the dash's direction at all (session S, removed session U).** The dash key is one key and a dash needs a side, so the direction was taken from the last steer press — within 0.45s at first, which made the button do *nothing at all* (no movement, no trail, no feedback) a moment later; then for the whole turn, which made it dash somewhere the player had stopped thinking about. Both are answers to a question that should not have been asked. **When an input genuinely has no good answer, look for a way to stop asking rather than for the least-bad answer.** The dash is a chord now — hold either the dash key or a direction key and press the other — so the direction is always stated and the dash key alone is simply an unfinished gesture rather than a dead input.

- **Defining Pile Up's dash as "the total ends up one cell from where the gesture started" (session S).** Precise, defensible, and it made the dash add the second half of a cell to the half the first tap had already moved — at the same speed. Double-tap: 1.00 cells. Two slow taps: 1.00 cells. The mechanic ran perfectly and could not be perceived, and was reported as simply not working. **Do not judge an added mechanic by whether its own code is correct; judge it by whether its output differs from what the player could already do.** The distance was fine and was kept; what had to change was the speed and the trail.
- **Culling a fallen Pile Up brick only at the point where it is safely gone (session S).** One kill plane, well below the platform, doing both jobs: deciding the brick is lost *and* freeing it. Correct-looking, and it worked fine while towers were short. Once landings got gentle and towers reached twenty cells, a brick knocked off the top had to fall ~900px — about six seconds — before that plane counted it, and since a turn ends when everything is at rest, every collapse burned the full settle timeout with the player watching "settling...". **When something became true and when you may stop tracking it are different questions**; answering the first with the second makes the game wait on something nobody is watching. Split into `LOST_Y` (scored, immediately) and `DESPAWN_Y` (freed, off screen) and the timeout stopped firing entirely.
- **Letting Pile Up bricks fall under plain gravity (session S).** Not a bug, and it looked perfectly reasonable — bricks fell, landed, stacked. What it actually did was make the mode unwinnable-by-skill: a brick released a fixed height above the stack arrives at ~670px/s, and at that speed it demolishes rather than stacks. The tell was a comparison, not an observation: `TowerProbe` measured careful centre-of-platform drops losing bricks at the same rate as deliberately terrible ones (14.7/match vs 13.1), with no tower ever passing 10 bricks. **A difficulty knob that hurts good and bad play equally is not a difficulty knob**, and the only way to see that was to measure two different qualities of play against each other rather than looking at either alone.

- **Trying to rescue front-elevation vehicle art for a top-down game with a rotation or a flip (session Q).** `motorlu.png`'s bikes face the camera; the game needs them facing away. 180° rotation puts the rider upside down, and a vertical flip does the same thing — because a front view and a rear view differ in *content* (visor and headlight against the rider's back and a tail lamp), not in orientation. No rigid transform converts one into the other. Distinguish this from the semis' problem in the same session: those were correctly projected and merely pointed the wrong way, which a rotation does fix. **Wrong facing is cheap to fix; wrong view is not fixable at all** — check the projection before extracting a sheet.
- **Detecting a vehicle sprite's facing from where its red tail lamps sit (session Q).** True of the art, useless as a test: red/orange/yellow bodywork drowns out its own lamps, and a pickup towing a light-coloured trailer scores as maximally backwards while being perfectly correct. **21 false positives out of 59 sprites.** Facing has to be checked by rendering new art next to a known-good sprite — there is no cheap statistic for it, which is why `FleetProbe` checks size, art, meta and speed but says nothing about orientation.
- **Making the semi's trailer bigger by scaling the finished sprite, or by stretching the box (session Q).** The finished sprite is already downsampled ~2x from source, so scaling it up resamples twice and goes soft. And a *stretch* is wrong even at source resolution: the trailer is ribbed, so stretching coarsens the rib pitch and the whole vehicle reads as a zoomed sprite rather than a longer truck. Repeat whole rib periods out of the uniform middle instead — the pitch, the front face and the rear doors all stay exactly as drawn.

- **Removing the multi-step sheet's little violet arrows by colour or by brightness (session P).** Both fail for the same reason: the art's own lightning is violet too, and some arrows are as bright as a bolt, so any rule loose enough to catch every arrow also catches lightning. The loosened attempt punched visible rectangular holes straight through the beam in two frames. An isolation test (is the blob sitting alone in a dark gap?) correctly rejected the lightning but still missed most arrows, because an arrow touching a ring's spike merges into one blob and fails the wedge-shape test. What worked was **position**: render the sheet with a labelled coordinate grid, read off all 17 arrow x-values by eye, and refine each to its local violet cluster before clearing. Slower to set up and the only approach that is actually correct.
- **Making the energy "bigger" by scaling one sheet up (session P).** It reads as blurry, not as massive — the frame gets larger but no denser, so it loses presence at exactly the moment it is supposed to gain it. Two additive layers of the *same* storyboard at different sizes is what produces a footprint neither sheet carries alone. The rule generalises: for a glow effect, reach comes from a second dimmer layer, not from a bigger first one.
- **Cropping animation frames to their own bounding boxes (session P).** Tempting, and it silently destroys any effect whose animation *is* a change in size — every frame ends up the same size on screen, so stage 1's growth from sparks to a full ring flattens into a static ring. Frames in a group must share one crop window, with the content sitting wherever it sits inside it.

- **Assuming the restart-desync fix (bug #1 / `LaneDivider.reset()`) would resolve the "cars going backward" complaint.** It didn't — the user reported it was still happening after that fix shipped. That fix was still correct and necessary (it's a real, separate bug), but it was not the primary cause of the reported symptom. Lesson: when a background-vs-foreground motion complaint persists after a timing/sync fix, check the *direction* of motion next, not just the *rate*.
- **Assuming the direction fix (bug #2) alone would resolve it.** After shipping the `y = -scroll` → `y = scroll - tile_h` change, the user reported *some* cars still looked backward — not all of them. This pointed away from a global/systemic direction bug (already fixed) and toward a per-obstacle issue, which was bug #3 (the `speed_mult` range exceeding 1.0). Lesson: "some cars" vs. "everything" is a meaningful diagnostic signal — a global draw-direction bug affects everything uniformly; a per-obstacle backward artifact points at per-obstacle speed logic.
- **The original `speed_mult` range of `0.78–1.28`** (introduced in commit `374f392`, before session A) was an attempt to add speed variety ("cars drift ahead of or fall behind each other") but was implemented as a naive multiplier on the base speed without grounding it in the relative-speed model. Do not reintroduce a flat range that crosses `1.0` — see the invariant in §7.
- **Session B, ending the whole drift session on grip convergence** (attempt 1 in §5). Looked correct in isolation (fixed the "sticky forever" complaint) but broke direction-switch continuity because it also armed a cooldown. Lesson: when a state has two different "done" conditions (grip resolved vs. player let go), collapsing them into one flag will eventually satisfy one caller and break another — split them instead of picking whichever one the current bug report is about.
- **Session B, assuming the state-machine fixes (attempts 2–3) would resolve "stops when changing direction."** They didn't, fully — the user reported the same symptom again after both landed. The actual bug (attempt 5, `target_vx` treating simultaneous both-keys-held as neutral) lived one layer below the drift state machine entirely, in plain steering input. Lesson: if a complaint survives a fix that was clearly a real, necessary bug, check the layer *underneath* the one you just fixed, not just harder within the same layer — here that meant looking at raw `Input.is_physical_key_pressed` handling instead of tuning `is_drifting`/`drift_sliding` further.
- **Untyped `for x in [const_a, const_b]:` loop feeding a `:=` inferred var (session C).** `for frac in [BOOST_TIER_LOW_MAX, BOOST_TIER_MID_MAX]: var divider_x := bar_x + bar_w * frac` is a **parse error** in this project's GDScript (4.7, presumably with static typing warnings/errors enabled) — `frac`'s type can't be inferred from an untyped array literal, so nothing derived from it can use `:=` either. This isn't a runtime bug that only shows up when the code path executes — it's a load-time parse failure, so it broke the *entire* script (`PlayerBoard.gd`) the moment anything tried to load it, which cascaded into `Main.gd` silently failing to build any player boards. Fix: type the loop variable explicitly (`for frac: float in [...]`) or explicitly type the derived var (`var divider_x: float = ...`). **Lesson: any `for x in <array literal or untyped Array>:` loop in this codebase should type the loop variable if anything inside the loop body uses `:=` on a value derived from it** — don't assume GDScript's local type inference reaches through loop-variable iteration.
- **Trusting a no-argument `godot --headless --quit` to validate scripts not reachable from the configured main scene (session C).** This project's own `CLAUDE.md` documents this exact command as the standard validation step, and it *did* run clean after the parse-error bug above was introduced — because the project's main scene is `MainMenu.tscn`, and nothing in the menu screen's own script chain preloads `PlayerBoard.gd`. The bug was only reachable by actually progressing through the menu flow to `Main.tscn`, which the bare command never does. **Lesson: when validating a change to a script that isn't loaded from the project's initial scene (anything under `PlayerBoard`, `Road`, `LaneDivider`, or scenes instantiated dynamically via `preload()`+`instantiate()` rather than being in the boot scene tree), run `godot --headless --quit res://scenes/<TheActualScene>.tscn` (or each scene in the flow) instead of the bare no-argument form** — the bare form only proves the boot scene's own reachable scripts parse, not the whole project.
- **Reading a user-provided `.mov` screen recording via `cp`/`ffmpeg`/Read on its original path.** macOS puts screen recordings in a `NSIRD_screencaptureui_*` temp folder under `TemporaryItems` that the agent's shell has no permission for (`Operation not permitted`, confirmed with `file`, `cp`, and `ffmpeg` alike) — even though other files under `~/Desktop` were readable fine. Similarly-timed recordings that had already landed on the Desktop were checked as a fallback but didn't show the relevant part of the window (player car area was cropped out of frame). If video evidence is needed again, ask the user to move/save the file to an accessible path (Desktop, project folder) rather than trying to read the screencapture temp path directly.
- **Session K, assuming that centralising the speed ramp had fixed the road/median desync.** It removed the copy-pasted `BASE_SPEED`/`SPEED_PER_SECOND` from `LaneDivider.gd` so the two could not disagree about the curve, which was correct and worth doing — but it was recorded as closing the desync, and it didn't. `PlayerBoard` multiplies the ramp by boost and tank recoil *after* asking for it, and stops asking entirely when the player crashes, so the divider running the identical curve still drifted permanently on the first boost and unboundedly on the first crash. **De-duplicating an input does not synchronise an output**; the only thing that does is having one number and making everything else downstream of it (session O). The tell was available the whole time: `current_speed()` and `SpeedRamp.speed_at()` were never the same function.
- **Session I, giving the Taxi its own movement path (driving its own `position.y` toward the player's).** This is the single most instructive failure of the session. It looked correct — a smooth exponential chase toward `player_car.position.y + offset`, using the same formula shape as the player's own steering — and it produced exactly the "actively driven at you" feel that was wanted. But nothing on that path consulted the vehicles in between, so the taxi phased straight through traffic lengthwise. Two rounds of adding clearance checks failed to fix it because those checks only ever guarded *lateral* moves; **the defect was the existence of the private movement path, not a missing check within it.** The fix was to delete the path entirely and let the shared obstacle loop move it, with the AI reduced to choosing `speed_mult`. Lesson: when an entity is supposed to belong to an existing system, make it move through that system's own code and express its personality as *parameters* to that code — an entity with its own update path will keep diverging from the system's guarantees no matter how many of them you re-implement inside it.
- **Session I, assuming the taxi read as "not part of the traffic" because of sprite resolution.** The gap was real and worth fixing (~600px source art against a fleet of ~78-160px sprites, so it kept detail nothing else had), and downsampling it to the fleet's pixel density did help — but the user still rejected it, and correctly identified the cause as "the model or color palette". The deeper mismatch was rendering *technique*: hard black outlines and flat unshaded fill on a boxy silhouette, versus the fleet's soft-shaded rounded bodies with gray-blue reflective glass, plus a much brighter value (0.73 vs 0.42-0.59). Lesson: "this asset doesn't belong" is usually about drawing technique and tonal range, not dimensions — measure value/saturation/dark-pixel share against the existing set and render a side-by-side on the actual background before theorizing.
- **Session G, swapping the player's whole tank-body texture through each frame of the firing-animation sheet.** Seemed like the obvious approach (it's literally an animation sheet) and was tried first, but measuring each frame's own content bbox showed the source art's tank render isn't pixel-aligned across its own cells — the combined flash/smoke bbox for later frames centers tens to hundreds of px away from the idle frame's own tank-only bbox center. Attempting to fix this by cropping every frame symmetrically around a shared "tank center" reference was fragile and still didn't visually hold up. Lesson: before treating a multi-cell sprite sheet as a true animation export (frames differing only in *content*, not in the subject's own position), verify each cell's subject position independently — AI-generated sheets in particular don't guarantee this the way a hand-authored/engineered export would. When it doesn't hold, decompose the effect into pieces you can anchor yourself (see the overlay approach in §5 session G, §6) instead of fighting the sheet's own layout.

## 9. Known bugs, limitations, unresolved problems

### Pile Up (all of it unplayed)

- **It has now been played, but barely.** Session T is the first report from real play (a brick stopping in mid-air — fixed, see §5), so the mode is no longer entirely theoretical. Nothing below has been retested by hand since. Everything else claimed about the mode still comes from headless measurement (`TowerProbe`: 12 matches per configuration, all terminating, zero tunnelling, settle timeout firing on ~0.4% of turns) and from arithmetic on the camera/HUD layout. None of that can say whether a collapse *reads* on screen, whether 14s is the right turn length, whether the drop guide is enough to aim with, or whether the mode is fun. This is the first thing to do — see §11.
- **The balance numbers are a floor, not a prediction.** `TowerProbe` steers bricks to random positions at random rotations without ever looking at the shape of the tower, so its ~80% per-turn fall rate is what *blind* play produces. A human picks a rotation that fits a gap. Careful play does now measurably outbuild sloppy play (21.2 turns per match at spread 0.3 against 16.7 at 1.0, with tall seeds reaching 12-23 bricks against 5), which is the thing that was broken before the fall cap — but real matches should run much longer than either, and nothing measures that yet. If matches turn out too long, `START_LIVES` (3) is the first knob; if too short, `AIM_BOUND_CELLS` (2.5, widened from 2.0 in session T's fourth pass) and `PLATFORM_CELLS` (5.0) are the difficulty ones. `AIM_BOUND_CELLS` must stay a multiple of 0.5 or the aim clamp falls off the half-cell lattice.
- **`TowerProbe` does not exercise the controls.** It sets the commanded x and rotation directly, so it covers the collision-checked follow and the descent but says nothing about the half-cell step, the hold-repeat or the soft drop. `DashProbe` covers the dash's intent, `DashFeelProbe` (session U) covers what the dash and the hold-repeat actually do under real key events, and `StallProbe` (session T) is the one probe that steers through `_press_steer()` on the real lattice — which is exactly the bug class the others structurally cannot see (§8). **The soft drop is still unexercised by anything except reading the code.**
- **`WEDGE_GRACE` (6s) is a backstop nobody should ever meet.** It bounds how long a brick can sit pressed against a flank refusing to land. At 1.5s it fired during ordinary play and took bricks away mid-placement; six seconds should mean only a deliberate hold reaches it. It was being met — `StallProbe` measured bricks riding it out for the full six seconds over five cells of clear air — but that was the zero-depth contact bug in §5 session T, and with `QUERY_SKIN` in place a refused descent implies real support, so there should be no geometry left for the wedge state to occupy. That is reasoning plus a probe that no longer reaches the path, not a human holding a brick against a wall on purpose.
- **The countdown's length is a guess, and session V spends more of it.** 0.68s a digit and 0.62s for GO!, ~2.7s in all, picked to feel like a countdown and confirmed by nobody. The burst now takes the first 0.2s of every step out of that budget rather than adding to it, so a digit is legible for ~0.48s where it used to be ~0.68s — the same guess with less margin. `BURST_FPS` shortens the burst without touching the length of the count. It plays before *every* round including replays, so it is paid again on each Enter, and a party game that gets replayed a lot may find it long. `STEP_TIME` and `GO_TIME` are the knobs; there is deliberately no skip key.
- **The countdown has no sound, because this project has no audio at all.** A visual-only countdown is doing half the job — the whole point of one is that you can prepare without watching it. Worth knowing if audio ever lands.
- **The probes' absolute numbers moved in session U and the old ones in this document are not comparable.** `TowerProbe` reads 22.9 turns per match at spread 0.3 (was 20.8) and `PaceProbe` 5.53s per turn (was 4.97). That is which towers get built, not how long anything takes — measured spreads across seed bases are 20.3-22.9 and 4.95-5.53 respectively, and both figures sit inside both. **Treat these means as ±10% at best**; the assertions (all matches terminate, zero tunnelling, zero settle timeouts) are the parts that carry real signal.
- **The dash is a chord and nobody has played it.** Session U made it "hold either the dash key or a direction key, press the other", which removed the direction-guessing this mechanic used to do (§8). Both orders are measured equal and both halves pressed alone are measured inert, but that is a probe, not a hand. The specific thing to watch is whether the dash key held down as a *modifier* is comfortable: it is `confirm` (W / Up / T / I), which sits above the steering keys rather than beside them, and a player holding it may find their hand covering the rotate keys. If it is awkward, the binding is the knob, not the gesture — and note `confirm` is the only key per player that Pile Up had spare (§5 session S fifth pass), so a different one means taking it from Don't Crash's table.
- **The dash key pressed alone is deliberately silent, and silence is what this mechanic has twice been reported for** (§8). It is defensible now — it is an unfinished chord, not a refused input — but a player who does not know the chord will press it, see nothing, and conclude the same thing they concluded in session S. If that happens, the answer is feedback (a hint on the brick while the key is held, say), not going back to guessing a direction.
- **`DESCEND_SPEED` (105px/s) sets the whole pace of a turn** — about 2.4 seconds from spawn to the top of the stack — and with the turn timer gone it is the only thing bounding how long a player can take. It was 58px/s and turns did drag, exactly as this bullet predicted; §5 session T has the measurements. **`SPAWN_CLEARANCE` is not a second copy of this knob** and must not be trimmed for pace again: it was cut to 5.5 cells in the same pass and the user reported bricks starting too low immediately. It is back at 7 and is a readability constant — see the comment on it. If the descent ever feels rushed, `DESCEND_SPEED` is the knob and `SOFT_DROP_SPEED` (430) is still there for players who have decided early.
- **The settle wait is dominated by one dislodged brick falling, and that is not fixable by tuning.** 3.07s on turns where a brick fell against 0.87s where none did. The brick has to reach `LOST_Y` before it is scored, and it cannot be scored earlier because it spends the fall hitting the tower on the way down (§8). Anything that shortens this materially has to change either `MAX_FALL_SPEED` (a collapse-feel constant, §7) or the fault rule itself.
- **A life is lost per *turn* in which something fell, not per brick.** So a drop that collapses six bricks costs the same one life as a drop that nudges one off the edge. This was chosen deliberately — a single catastrophe knocking a player from 3 lives to 0 is a bad party-game moment — but it is a real divergence from Tricky Towers, where each falling brick costs a life. The message does report the count ("P2 DROPPED 4 BRICKS"), so switching to per-brick is a one-line change in `_resolve_turn()` if the user wants the harsher rule.
- **There is no Pile Up AI.** `BotDriver` plays a `PlayerBoard` — it senses traffic in an `obstacle_container` and steers between lane centres, none of which exists here — so the bot hotkeys and the "1 PLAYER vs BOT" option are hidden in this mode rather than doing nothing. That also means Pile Up has none of the hand-it-to-a-bot testing loop that makes Don't Crash cheap to iterate on, which is a real workflow gap, not just a missing feature.
- **The platform goes off the bottom of the screen at about eleven bricks.** The camera rests with the outcrop low in frame until the tower reaches about five bricks, then switches to holding the stack top at 48% of screen height, so ~11 cells of tower stay visible below it and the base eventually scrolls away. The platform's footprint is drawn as two vertical guide lines running up the whole screen, and the shaded play column marks the legal area, so this is believed fine — but it has not been seen in motion, and if the base disappearing feels disorienting, `CAM_STACK_TOP_FRAC` is the knob.
- **The outcrop's stone is one 260x62 window of the backdrop, tiled.** `ROCK_SRC` is a hand-picked crop of the art's earth band; it repeats every 62px down the outcrop, which at 160px tall is two and a half repeats. Nobody has looked at whether that repetition is visible in motion. If the backdrop art is ever replaced, `ROCK_SRC`, `TowerGround.GROUND_LINE_PX`, `TowerBackground.SKY_COLOR` and `GROUND_COLOR` are all measured against *this* image and all go stale silently — the mode would still run and would simply be made of the wrong pixels.
- **The near ground is decorative, with no collision.** A brick that falls off passes through the grass rather than landing on it; it is hidden behind the band and then freed at `DESPAWN_Y`. Debris never piles up at the foot of the tower, which is a missed bit of drama rather than a bug, but it does mean the ground is a curtain and not a floor.
- **The backdrop's parallax has an end.** `BACKDROP_PARALLAX` (0.28) is set so a roughly twenty-cell tower scrolls the art almost exactly to its top; past that the sky continues in a flat sampled colour and the sense of climbing quietly stops. Fine for the tower heights measured so far, unverified beyond them.
- **The heart pips were confirmed on one pass and every number in them is still a first guess.** `PIP_H` (20px), `PIP_GAP` (24px), `PIP_ROW_UP` (22px) and `PIP_EMPTY_ALPHA` (0.22) were picked against a rendered screenshot and then played once, at the player count that session happened to use. The two most likely to be wrong: the ghost's alpha, which has to read as *spent* and not as a dim life still in hand — the failure mode is a player miscounting their own lives, which on this mode is miscounting the score; and the pip size on a 4-player screen, where four cards of three hearts is the most this column ever carries. The pop also swells over its neighbour for a moment (`HeartPips.LOSS_POP`, shared with Don't Crash), which is fine behind a car and has not been watched on a card.
- **Bricks are colour-coded by shape, not by player.** Every brick already on the pile looks the same whoever placed it; only the brick currently in the air carries its owner's colour (a tinted outline that fades on landing). That is deliberate — it matches Tricky Towers and keeps the tower readable as one object — but it does mean you cannot look at a finished tower and see who built which part.
- **`RESOLVE_PAUSE_QUIET`/`RESOLVE_PAUSE_EVENT`, `ROTATE_LERP` and `MAX_FALL_SPEED` are all unvalidated feel constants**, in the same category as the drift constants in §7 — picked to be reasonable, confirmed by nobody.
- **Not stress-tested for the pathological cases**: a tower tall enough for the camera to have panned a long way, a match where two players are eliminated in consecutive turns, or a brick that comes to rest balanced exactly on the kill plane's boundary.

### Don't Crash

- **The three-lives system was confirmed on one pass, and every number in it is still a first guess.** `INVULN_DURATION` (2.2s), `INVULN_SLOW_DURATION` (0.95s), `INVULN_SLOW_MULT` (0.32), `INVULN_BLINK_INTERVAL` (0.09s) and `HEART_HEIGHT` (17px) were all picked to be reasonable and have survived exactly one session. The two most likely to move: the pass-through window, which is either too short (you die twice to one wall of traffic) or long enough to be used as a free run through the traffic on purpose; and the crawl, which at 0.32x may simply feel like the game froze.
- **Three lives makes a round roughly three times as long, and nothing else was retuned for that.** `SpeedRamp`'s curve completes at 100s and then creeps at +1.2/s so a round always ends; that was sized against players who crashed once. Watch whether the last survivor is now driving a road nobody can read, and whether the distance scores still separate players meaningfully when everyone gets three attempts at the same traffic.
- **A player who has lost a life is faster to spot than one who hasn't**, because the pips are the only per-board state visible at a glance and there is no scoreboard for them. Nothing shows a rival's remaining lives from across the screen at 3-4 players; if that turns out to matter, `Main`'s status strip is where it would go.
- **The pips sit 4px above the bottom edge of the board and are inside `ScreenMask`'s vignette.** They come out ~15% darkened at 2 players and less at 3-4 (the fade is deeper but the board bottom sits further from the viewport edge). If that reads as dirty rather than as depth, `HEART_TRAIL_GAP` moves the row up, at the cost of the gap to the bumper.
- **The bot does not know it is invulnerable.** `BotDriver` keeps dodging exactly as hard during the pass-through window, so bot boards will never use the free seconds a human would. Harmless — but it means bot rounds under-report how exploitable the window is, which is the one thing the playtest most needs to answer.
- **Coaches are 14% longer than they have ever rendered, and that has not been played yet.** Session R split `coach` out of `bus` so `bus_coach.png` stops being squashed (§5 session R), which takes it from 78px to 89px of road. It is 2% of traffic and still shorter than a trailer (124px) or a semi (148px), so this should be unremarkable — but it is an unplayed change to a lane-blocking footprint, same class as the pickup/SUV note below. The knob is `coach`'s own `weight`, which is now independent of the transit bus's.
- **The motorcycles are still the three original top-down sprites, and the ten-bike sheet is unused.** `motorlu.png` was imported in session Q and reverted the same session once it was played: it is drawn as a **front elevation** — the rider's face, arms out to the bars, headlight and front wheel at the bottom of the frame — so its bikes ride straight *at* the player while every other vehicle drives away. `moto_*` is therefore three plainer, lower-detail sprites against a fleet that got much richer around them, which is a real cosmetic gap. **Closing it needs top-down bike art**; it cannot be closed with a different transform of the sheet already here (§5 session Q, §8).
- **A semi is now 179px of a 620px board — 29% of the visible road — and has not been played.** Session Q lengthened the trailer 40% at the user's request (`height_frac` 4.18 → 5.07, on-road 148px → 179px). At 7% of traffic that is a real difficulty change on a 5-lane board, especially stacked with the longer pickups/SUVs below and with `trailer` (124px) already in the table. If lanes feel unfairly walled off, the knobs in order are `truck`'s **weight** (7), then `EXTRA_RIB_PERIODS` in the extraction (re-derive `height_frac` if that changes) — **not** `width_frac`, which is what keeps a semi inside its lane.
- **Pickups and SUVs are meaningfully bigger than they were.** Pickup 50px → 74px of road, SUV 59px → 72px, both because `height_frac` now matches the art's real aspect (2.23 and 1.98 against the old 1.52 and 1.79). Combined they are 28% of traffic, so lanes are genuinely more blocked than before session Q. This is correct rather than a regression — a crew-cab pickup *is* longer than a sedan — but it is an unplayed difficulty change, and if rounds feel tighter than expected this is the first place to look, ahead of `SpeedRamp`.

- **Nitro's halo layer holds one frame per stage while the core plays 23.** The halo is a soft, dim, deliberately out-of-focus bloom, so a slower cadence there reads as lag rather than as staleness — but it is a real asymmetry, and if the effect ever reads as half-animated this is why. The first sheet only has six frames; fixing it properly means either finding a multi-step version of it or driving both layers from the same sheet, which would cost the reach the halo exists to provide (see §5 session P).
- **A drift trail started before a nitro launch keeps its already-laid marks on screen while the car is airborne.** `_update_drift_trails()` is skipped while off the road, so no *new* rubber is laid and the marks stop where the wheels left the asphalt — which is correct — but the existing `Line2D` keeps scrolling and fading beneath a car that is now 105px above it. Cosmetic, brief, and cheaper to live with than coupling the drift system to the skill.
- **A car flying at 1.24x scale can overhang the painted shoulder.** `steer_bounds()` clamps against `car_size()`, which does not know about the temporary draw scale, so the visual silhouette can sit ~4px past the clamp at full lift. Arguably correct (the car is airborne) and only visible in an edge lane.
- **Nitro's three arrow-free crops rely on 17 hardcoded x-positions.** If the source sheet is ever re-exported at a different layout, the arrow-removal positions in the extraction go stale silently — the frames would simply come out with small violet chevrons in them. Colour and brightness were both tried and neither can separate an arrow from the art's own lightning (§5 session P).

- **Almost every number in the six modular skills is still a first guess.** Durations (5/7/5/5s), Compact's 0.66 and 1.08, Oil Slick's 0.34 grip and 140px/s² fishtail, Make Way's 0.7 hurry, Detour's line count and spacing — all reasoned, none felt. The only verification is `SkillProbe`, which proves they end cleanly and bite while live, and sees no pixels. **Smoke Screen's numbers have now been moved twice against play** — density to 0.80/0.32/0.38, floor variation 0.20, 34 puffs, the band from above the visible road down to 0.66 of it, and the HUD veil at 0.52 — each time in the direction the user asked for and each time deliberately past the caution the file itself had written down. Make Way's 720px reach has been moved once. These are the most likely things in the skill set to need another pass, and the direction to move them is *back*, not further; `BASE_ALPHA` is the lever for the smoke, because it sets what the thinnest spot costs.
- **Make Way's police skin has never been seen next to Tank Mode or Compact.** The precedence is written and the probe proves the skin is put back three ways, but a tank ending mid-siren (restores the cruiser), Compact shrinking the cruiser to 66% width, and a crash's fade/explosion over it are all unplayed. Compact is the interesting one: the cruiser is already narrower than a stock sedan, so it will look very thin.
- **Smoke Screen's bottom edge is 26px from a Nitro-lifted car roof, and that is the tightest clearance in the skill set.** `BAND_BOTTOM_FRAC * 620 = 409`; Nitro lifts the car to a roof at ~435. Anything that raises the lift, lowers the car, or increases `BAND_BOTTOM_FRAC` puts a boosting victim inside their own smoke, which reads as a rendering bug rather than as weather. It is checked by nothing — the probe is headless and Nitro-under-Smoke has never been played.
- **The smoke's HUD veil is the one place traffic is still readable inside the band.** It has to be: the overlay draws above the boost bar and the timer bars, and a player who cannot see their own charge thinks the game broke. It is held to the middle half of the board (the bars' own width) and to ~0.42 alpha, so what it costs is a short stretch of the centre lanes. If it ever needs to cost less, the honest fix is not a thicker veil — it is moving the HUD's drawing above `SkillOverlay.OVERLAY_Z` so the smoke can cover the strip outright, which is a `PlayerBoard` change and would also stop the boost bar being drawn behind passing traffic (§5 session Y notes it has always been).
- **Every skill icon and Detour's barrier are still code-drawn placeholders.** They read at 28px as silhouettes, and that is all they do. (Oil Slick's in-round puddles are real art as of session Z; its *icon* is not.) `docs/SKILL_ART_BRIEF.md` is the replacement brief; the same filename under `sprites/skills/` drops in with no code change.
- **The bot is immune to Smoke Screen and only half-aware of Oil Slick.** It senses the obstacle container, not the screen, so smoke costs it nothing; it reads `steer_top_speed()` (which Slick leaves alone) but not grip, so it plans as if it could still place the car. Both recorded in the skill files rather than "fixed" by handicapping the bot artificially. It *does* see Detour's barriers (they are `Car`s with `lane` metas) and benefits from Compact (it reads `car_size()`).
- **Skill interactions are untested, all of them.** Compact under Nitro (the shrunken car lifts; `_box()` follows `player_car.position.y` so the readout should ride up with it), Slick during a drift (0.48 × 0.34 — deliberately awful, and deliberately allowed), Smoke Screen over a Nitro comet (z 6 over z 3, so the smoke covers the energy), Detour into a Taxi wave (a barrier line and a taxi are both just container children; the taxi's follow limits should stop it in front of a barrier, unverified), and Make Way against a car mid-taxi-merge. Two rivals sending the same opponent skill in one moment refresh rather than stack on the victim's board (same-id rule), but two *different* ones compound by multiplication.
- **Detour's barriers are `Car`s, so the tank crushes them and the cannon shoots them.** Almost certainly right (a tank through a barricade is the fantasy), noted so nobody reads it as a bug. They also carry `speed_mult` 1.0 exactly, which `FleetProbe`'s "< 1.0" invariant would flag if it ever inspected them — it only inspects `_spawn_obstacle()`'s output, so it does not.
- **Make Way's corridor uses `player_car.position.y`, which Nitro lifts by up to 105px.** That only shortens the reach while airborne, and traffic under an airborne car is being flown over anyway; left as-is.
- **Multiple taxis on one board are now exercised but only in headless measurement, not in real play.** Session L measured 3-taxi waves on a 4-player board (all three delivered, all roaming, all leaving) after fixing a spawn stagger that culled the second taxi of a wave instantly. Taxis avoid each other — `_taxi_lateral_blocked`/`_taxi_follow_limit` treat any `Car` as an obstacle, including another taxi — but nobody has watched a 3-4 player pile-up with human hands on the boards.
- **The taxi can still graze another vehicle, by a few px.** Not the session-I phasing bug (that path is gone). Worst-case overlap depth by version: session I 33.1px → session L 15.7px → session M 4.3px — but **that 4.3px is wrong, and the error is instructive**: it was measured over 5 seeds. Session N re-ran 20 seeds per version and both the session-M code and its own reach **20-25px** (old code seeds 11/13: 21.7px, 24.0px). Most seeds are still completely clean; the deep episodes are rare and every one of them classifies as `traffic-merging-in`, i.e. the cause immediately below, not the taxi driving into anyone. **Five seeds is not enough to bound a rare event** — the harness's own header warns that unseeded runs prove anything you like, and a five-seed *worst case* has the same problem. **Do not "fix" this by raising `TAXI_FOLLOW_GAP`** — that buys clearance by making the taxi timid, which is the opposite of what it is for, and session M's diagnosis showed the follow gap was never the cause anyway.
- **One residual overlap cause is known and deliberately not fixed: traffic never re-checks a merge it has committed to.** `_update_obstacle_lane_change` tests `_lane_clear_near` once, at `pending`, then runs 1.3s of indicator warning plus a 0.5s slide with no further checks. Ordinary traffic closes slowly enough that the 200px `LANE_CHANGE_SAFE_GAP` survives that window; a taxi closing at ~1.6x road speed covers ~500px in it and can arrive inside the target lane after the merge was cleared. The fix would be a second `_lane_clear_near` at the `warning` → `moving` transition ("signal, then look again before actually moving", which is also what a real driver does) — but that changes core traffic behaviour the user signed off in session D, to address roughly one episode across five measured seeds. Not worth the risk unbidden; get sign-off first.
- **A taxi can still be culled early in heavy traffic.** The blocked-→-re-decide fix (§5 session I) and session L's gap-hunting both make this much less likely, but if it is genuinely walled in while the car it's stuck behind drifts back past the player, it will cross the shared bottom despawn threshold before its chaos window is up. Reads as the skill fizzling; the fix would be a larger despawn allowance for taxis (`OBSTACLE_DESPAWN_MARGIN` is now a named constant, so a taxi-specific one has somewhere to sit) rather than loosening the follow limit.
- **The taxi does not interact with `SkillPickup`s.** It drives over them without collecting or disturbing them (they aren't `Car`s, so both its clearance scans skip them). Fine today, but worth knowing if pickups ever become collectible by non-player entities.
- **Skill-choice keyboard bindings are placeholder and untuned.** Chosen only as a keyboard mnemonic (flanking each player's `confirm` key); since the project targets PS5 (per the user, session F), don't invest in optimizing these specific keys further — the real design work is the eventual gamepad mapping.
- **Not stress-tested with multiple pickups/choices in flight across 3-4 players simultaneously**, nor with a player repeatedly re-triggering the choice by driving over several pickups in a row before ever picking one.
- **Tank Mode has not been stress-tested with 3–4 players simultaneously**, nor with two players both transformed at once, nor with a player re-picking "self" (refreshing the timer, see `_activate_tank_mode`) while already mid-fire-animation. Each `PlayerBoard` owns its own tank/fire/recoil state independently, so this should be fine structurally, but hasn't actually been tried.
- **Tank Mode's cannon target search (`_find_cannon_target`) doesn't account for `SkillPickup`s or the player's own dash/drift lateral motion between the frame it fires and the frame the shell lands** — it picks a target once, at the moment of firing, and the shell always flies to wherever that target *was* at that instant (a snapshot `Vector2`, not a live per-frame chase), so a fast-moving/lane-changing target could visually have moved somewhat by the time the shell arrives. Not reported as a problem in playtesting, but worth knowing if a "shell missed a lane-changing car" report ever comes in.
- **`TANK_EFFECT_SOURCE_TANK_WIDTH` (188) is a measured-by-inspection constant tied to the current `tank_animasyon.png` asset.** If that source sheet is ever re-exported at a different resolution/crop, this must be re-measured (same category of fragility as `Road.SHOULDER_RATIO`) or the flash/smoke overlay will render at the wrong scale relative to the tank body.

- **The session-K ramp curve is feel-tuned against one playtest, not balanced.** `RAMP_CURVE` (1.45), `RAMP_DURATION` (100s), `TOP_SPEED` (560), `SPAWN_RAMP_DURATION` (70s) and `OVERTIME_SPEED_PER_SECOND` (1.2) were picked to answer a specific complaint ("gets too fast too soon") and confirmed in a single pass. The open question is the opposite failure: whether the first ~30 seconds is now too *placid*, since it is much flatter than the old line (230px/s at t=30 where the old ramp was at 340). `RAMP_CURVE` and `RAMP_DURATION` are the two knobs for that. Long rounds (past the 100s ramp completion, where only the slow overtime creep is left) have also not been played out.
- **A divider cannot match both of the boards it sits between.** Resolved in session O as far as it can be: `LaneDivider` now follows `neighbors[0]` (its left board) exactly, falling back to the right board when the left stops scrolling. When the two flanking boards legitimately differ — one player boosting, the other not — the median matches the left one and not the right. This is inherent to one strip shared by two independently-paced boards, not a bug to be fixed; the only complete fix tears the trees down the middle. **Do not "fix" it by reverting to an independent timer**, which matches *neither* board and was the original complaint.
- **This entry used to say the opposite, and the way it was wrong is the point.** It read: the divider "stays in lockstep with the boards ... this is coincidental synchronization via duplicated logic", with the residual risk framed as a divider "reset or created at a different moment" than its board. Every word of that is about *start time*, and start time was never the problem — boards and dividers are reset in the same call. The actual causes (boost multipliers, and a crashed board freezing) were sitting in plain sight in `current_speed()` and in `_process`'s early return. A known-limitation entry that names the wrong mechanism is worse than no entry, because it directs the next session's attention away from the cause: this one survived sessions L, M and N unexamined.
- **Only the HARD profile has been played. The user confirmed it ("hard is good") and said explicitly that they had not tried EASY or NORMAL and did not care about them.** So HARD's numbers are settled — including its lane-commitment feel and its boost-farming weave, both of which were on screen and drew no complaint, as were the "BOT · LEVEL" tag and the caption-less skill-choice icons — and it is now the default (`GameSettings.bot_difficulty`). EASY and NORMAL are *unvalidated*: their survival medians (~12s and ~21s against HARD's ~35s, measured headless over 16 four-player rounds each) say they form a ladder, but nothing says they *feel* like plausible weaker drivers rather than a good driver acting broken. **Don't spend time tuning them unprompted** — the user has already said where that sits for them. If either ever does matter, the levers are `horizon`/`lookahead` (foresight) and `decision_interval`/`reaction_time`/`aim_error`/`blunder_chance` (latency and sloppiness) in `BotDriver.PROFILES`.
- **The bot's sensing model is at its ceiling at roughly 35s of survival (HARD).** A profile with a 6.5s horizon, depth-4 lookahead and zero reaction delay was measured and scored no better. Further gains would need a different model, not more lookahead — e.g. evaluating positions between lane centres (it only ever considers the five lane centres, so it cannot thread a gap straddling two lanes), or accounting for traffic that has not spawned yet.
- **The bot ignores `SkillPickup`s except as a mild lane bonus, and only when a lane is already clear for the full horizon.** It will not detour for one. It also has no model of its opponents at all — it plays its own board and picks "self" vs "opponent" skills off its own local pressure and a coin flip, never off who is actually winning.
- **Bot difficulty is global, not per-player** (`GameSettings.bot_difficulty`), so a HARD bot and an EASY bot cannot share a round. The 5 key changes all of them at once. `BotDriver.set_difficulty()` is per-instance, so this is a UI limitation rather than a structural one.
- **Two game modes exist** ("Don't Crash", "Pile Up"). The rest of the README's roadmap (further modes, gamepad support, web/desktop export) is unstarted — no code toward any of it exists yet.
- **No CI, no automated tests, no export presets configured.** Validation is headless-compile-check plus manual playtesting only.
- Multi-round replay under 3–4 players and extended play sessions (many minutes, high speed ramp) have not been specifically stress-tested this session beyond the user's own playtest confirmation — worth another pass if traffic issues resurface at very high speeds.

## 12. Non-obvious implementation details

- **A GDScript `static var` makes a headless run report leaked ObjectDB instances at exit, even holding `null`.** Session Z put a `static var _puff_tex: GradientTexture2D = null` on `SmokeScreenSkill.gd` — a shared cache for a texture that depends on nothing — and `godot --headless --quit res://scenes/Main.tscn` started printing "9 ObjectDB instances were leaked at exit" plus two resource-in-use errors, on a run that never draws anything and therefore never assigned it. Removing the two `static` keywords and nothing else exits clean; measured both ways on 4.7.1. The storage for a script's statics evidently outlives the leak check. This matters more than the waste it was avoiding: the clean headless run is this project's only automated validation, and a permanent false positive in it would hide the next real leak. Prefer a per-instance field on a `RefCounted` skill effect.

- **`Car._rebuild()` scales a texture to `width x height` on each axis independently, so a car sprite's aspect ratio is not a suggestion.** A texture whose aspect differs from the `kind_cfg` it is drawn under (`PLAYER_KIND` is width_frac 0.62 / height_frac 1.69, i.e. 78x132) is squashed or stretched on screen, silently. The two ways out are to author the art onto that canvas (what `extract_police.py` does — the cruiser is fitted to the sedans' 121px length and centred, ending up narrower rather than distorted) or to claim `car_kind()` as well (what Tank Mode does, `TANK_KIND` being "the cropped sprite's own aspect ratio"). The second changes the hitbox, so it is a gameplay decision, not an art one.

- **Anything that re-skins or re-sizes the player's car must go through `refresh_car_texture()` / `refresh_car_size()`, never set it directly.** Two systems can now claim the car (Tank Mode inline, and any `SkillEffect` via `car_kind()`/`car_texture()`), and a direct `player_car.set_texture(player_texture)` at the end of one of them is wrong whenever the other is still live — `_deactivate_tank_mode` had exactly that bug waiting, and would have dropped a player out of the police car they were still driving. The shared functions resolve the precedence in one place. The `SkillEffect` lifecycle is what makes them usable from the hooks: the effect is in `active_effects` during `activate()` and out of it during `deactivate()`, so the same call means "take my claim" at one end and "give it up" at the other.

- **`draw_set_transform()` is canvas state, and a `SkillEffect`'s `draw_board()` runs partway through `PlayerBoard._draw()`.** `draw_texture_rect` cannot rotate or mirror, so a skill wanting either has to set a transform — and everything `PlayerBoard._draw()` draws *after* the skill hooks (the boost bar, the life pips, the bot tag) inherits it. `SlickSkill._draw_spills()` resets to identity after its loop unconditionally for that reason. The same applies to `draw_overlay()` and `SkillOverlay._draw()`, where the victim would be the *next* effect in `active_effects`.

- **Two Claude sessions editing this working tree at once silently lost an edit, and the loss was invisible in both git status and the compile check.** During session Q a background task ran session R's `bus`/`coach` split in the *same* checkout (`git worktree list` showed one tree, not two). Read-modify-write from two processes meant one write clobbered the other: `scripts/GameSettings.gd` came out with 9 kinds and `bus` back at weight 5, while `README.md` and this document — written by the other session moments earlier — described 10 kinds and a `coach` entry. Nothing flagged it. `godot --headless --quit` was clean, because a table with 9 valid kinds is perfectly valid code; only `FleetProbe` printing `bus … 14.5% stretch` again after the split had supposedly fixed it gave it away. **If a background task is touching the same files, re-read them before writing and diff the code against what the docs claim** — the docs are the half most likely to be describing work the code no longer contains.

- **A newly added `class_name` script is invisible to headless runs until the project is reimported.** Godot resolves global class names through `.godot/global_script_class_cache.cfg`, which the *editor* rebuilds on import — a bare `godot --headless --quit <scene>` does not. Adding `scripts/SpeedRamp.gd` in session K therefore produced `Identifier "SpeedRamp" not declared in the current scope` and a cascading `Failed to load script "res://scripts/PlayerBoard.gd"`, which looks exactly like a real parse error in code that is in fact fine. Run `godot --headless --import` after adding any `class_name` script, before trusting the validation output. (`.godot/` is gitignored, so a fresh clone regenerates it on first editor open.)
- **Godot 2D: +y is down, +x is right.** Repeatedly relevant this session — see §7.
- **`GameSettings` is an autoload singleton**, not a resource you instantiate — it's globally accessible as `GameSettings.foo` from any script without a reference, and its `const` tables (`PLAYER_SKINS`, `TRAFFIC_KINDS`, `PLAYER_CONFIGS`) `preload()` every texture at parse time, so adding vehicle kinds means editing this one file's array literals, not spawning new resources.
- **`Car.gd`'s placeholder `Polygon2D` shapes auto-hide** the moment `set_texture()` is called (`body.visible = false; windshield.visible = false` in `_rebuild()`) — you never need to manually hide them when assigning real art to a new `Car` instance.
- **`speed_mult` (the per-obstacle meta key) is a closing-speed *fraction* of the current road speed, not a real-world speed.** Read `PlayerBoard._process`'s obstacle-movement block (`child.position.y += speed * speed_mult * delta`) together with `GameSettings.TRAFFIC_KINDS`' `speed_frac_min`/`speed_frac_max` comment block to understand it — the comment there explains the physical reasoning in full and should be kept in sync with any future changes to this system.
- **Tile-anchoring formula `y = scroll - tile_h`** (in both `Road._draw()` and `LaneDivider._draw()`): `scroll` is `fmod(distance, tile_h)`, always in `[0, tile_h)`. This anchors the first (partially off-screen) tile at `y ∈ [-tile_h, 0)` and lets it (and all tiles after it) drift toward `y = 0` and beyond as `distance` grows, which is what makes the whole pattern appear to slide downward. If you ever need to reverse the visual scroll direction intentionally (e.g. a "reverse" game mode), flip this to `y = -scroll` deliberately — but remember that then also requires making obstacle motion negative to match (see the §7 invariant about keeping `Road`/`LaneDivider`/traffic direction consistent).
- **Dash and drift are purely lateral (x-axis) mechanics** — they do not interact with the forward-scroll speed system described above at all. `car_vx`/`car_x` in `PlayerBoard.gd` are entirely separate from `distance`/`current_speed()`. Don't conflate the two systems when debugging either one.
- **Drift trail scrolling is done by mutating every existing `Line2D` point every frame** (`for i in line.get_point_count(): line.set_point_position(i, ...)` in `_process`), not by moving the node. This mirrors how the old `ColorRect` marks scrolled (`mark.position.y += speed * delta`) but is O(points) per trail per frame instead of O(1) — fine at party-game scale (a few players, short-lived trails capped by fade duration) but would need rethinking if trails were made much longer-lived.
- **`_try_start_drift()` is one function serving two different callers with different needs**: a fresh entry from normal driving (gated by `REVERSAL_THRESHOLD` + `drift_cooldown_timer`) and a re-catch mid-session (gated by nothing — `is_drifting` being true is itself the permission). Read the early-return chain top to bottom; the order encodes the priority (dashing blocks everything, then already-drifting short-circuits the cooldown check entirely).
- **Boost's `confirm` key release is handled *before* (and unconditionally of) the `active`/`alive`/`is_dashing` gate at the top of `_unhandled_input`**, unlike every other input in that function. If it were gated the normal way, releasing the key while `is_dashing` happened to be true would get swallowed, leaving `boost_active` stuck on — draining charge with no way to stop it until some later input event fired. Press-side activation (`_try_activate_boost`) is still gated normally. If you add more boost-adjacent inputs, keep "can this leave a persistent flag stuck on" in mind for what needs to bypass the gate.
- **`GameSettings.PLAYER_SKINS[i]["color"]` is a hand-picked flat approximation of each texture's dominant hue, not sampled from the actual sprite.** It exists purely for UI/effects that need a plain `Color` (boost bar fill, exhaust flame tint) rather than a tintable shape — the real car art is a texture. If a skin's art is ever re-colored/replaced, its `color` entry won't update itself and should be revisited by eye.
- **A new global `class_name`-declaring script (e.g. `SkillPickup.gd`) isn't visible as a type to other scripts until Godot rebuilds `.godot/global_script_class_cache.cfg`.** Session F hit this directly: `godot --headless --quit res://scenes/Main.tscn` reported `Could not find type "SkillPickup" in the current scope"` immediately after the script was created, even though the script itself was syntactically fine — the class just wasn't registered yet. Fix/workflow: run `godot --headless --editor --quit` once (a full editor boot that scans the project and rebuilds the class cache) after adding or renaming a `class_name`, *before* trusting a headless compile check's result. A `--headless --quit` alone does not trigger this rescan.
- **GDScript loop-variable typing gotcha**: `for x in <untyped array>:` gives `x` an unresolvable type for the purposes of `:=` type inference on anything derived from it — this is a **parse-time** error, not a runtime one, so it breaks the whole script immediately on load rather than only when that code path runs. See §8 for the specific incident and why the standard `godot --headless --quit` validation command didn't catch it (it never loaded the broken script at all, since the main scene doesn't reach it).
- **`Sprite2D.offset` is applied in the sprite's own local, pre-scale pixel space, then carried through the node's scale/rotation like the rest of its transform.** Tank Mode's fire-effect overlay (`_show_fire_effect_frame`) uses this to anchor a frame's own bottom-center — not its geometric center, which is where a centered `Sprite2D` draws by default — at the node's position: `offset = Vector2(0, -tex_size.y * 0.5)` shifts the drawn rect so its bottom edge sits exactly at local y=0 regardless of the node's current scale, since offset scales proportionally along with everything else in that local space. Useful anytime a sprite needs to be anchored by an edge/corner instead of its center without hand-rolling the position math every frame.
- **A script constant *does* resolve through an untyped instance** — `board.MAX_LIVES`, `board.HEART_Z` from a skill file where `board` must stay untyped. `GDScriptInstance::get()` falls through member variables to the script's constant map, and `PitStopSkill` relies on it (verified by `SkillProbe`'s refund case on 4.7). `SkillProbe` and `SmokeScreenSkill` read the same constants via `board.get_script().get_script_constant_map()` instead, out of caution written before that was known. Both work; the direct form is the readable one. (`Object.get("CONST")` goes through the same path, so it works too — the probe's earlier worry was unfounded.)
- **A freed node read through an *untyped* reference cannot be assigned to a typed local — it errors before `is_instance_valid()` can run.** `PlayerBoard.heart_sprites` keeps a dangling entry for every spent pip on purpose (fixed slots, see `_layout_hearts`). Inside `PlayerBoard`, `var heart: Sprite2D = heart_sprites[i]` is fine: the analyzer knows the element type and emits a plain assign. From a skill file, where `board` must stay untyped (the cyclic-reference rule), the same line comes back as a Variant and the typed assign validates it at runtime — "Trying to assign invalid previously freed instance", every time the slot is stale, which is the normal case. Read it untyped (`var stale = board.heart_sprites[slot]`), then guard. Session Y: `PitStopSkill._restore_pip` and `SkillProbe` both hit it on the first real refund, and neither the compile check nor the pinned-invulnerability lifecycle cases could have — only a case that actually spends a pip first.
- **Killing a `Tween` (`Tween.kill()`) does not run any of its remaining `tween_callback`s, including the last one.** If a tween's final step is "clean up/free something," anything that can kill that tween early must do that cleanup itself — see the session G leak in §5/§8/§9 (`fire_anim_tween` being killed skipped `_fade_out_fire_effect`, orphaning a sprite). This is a general Tween gotcha, not specific to this one feature — worth checking any future code that both builds a tween ending in a cleanup callback *and* has another path that can kill that same tween early.
- **A `Callable.bind()`'d extra argument (as used for every step of `_play_fire_animation`'s tween, and `_spawn_shell`'s arrival callback) captures the value at bind time, not a live reference re-read later.** `_on_shell_arrived.bind(shell, target)` freezes which `Car` node `target` refers to at the moment the shot was fired — this is intentional (see the "shell flies to a snapshot position" limitation in §9), but it's a general pattern worth remembering: `.bind()` is a snapshot, not a closure over a variable that keeps updating.
