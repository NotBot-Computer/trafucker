# Traffic Tower — Project State

Last updated: 2026-08-21, at commit `b3d789f` on `main` (working tree clean apart from this doc's own commit, which lands immediately after — pushed to `origin/main` — `github.com/NotBot-Computer/trafucker`).

## 1. What this project is

**Traffic Tower** is a local split-screen party game built in **Godot 4.7** (GL Compatibility renderer). Each player gets their own vertically-scrolling lane board side by side on one screen; you steer left/right to dodge oncoming traffic, and the road speeds up over time. Whoever survives longest (covers the most distance) wins the round. Structurally it's meant to grow into a "many small competitive modes" party game (inspired by *Tricky Towers*) — currently only one mode, **Don't Crash**, exists.

Full player-facing description, controls, and art notes are in [README.md](../README.md) — that file is accurate and up to date; don't duplicate it here, read it for the "how to play" side.

## 2. Architecture / structure

Scene tree flow: `MainMenu.tscn` → `PlayerSelect.tscn` (pick 2–4 players) → `SkinSelect.tscn` (each player cycles/locks a car color) → `Main.tscn` (the actual round).

`Main.tscn` instantiates one `PlayerBoard.tscn` per player side by side inside `BoardsContainer`, and one `LaneDivider.tscn` between each adjacent pair inside `DividersContainer`. Each `PlayerBoard` owns its own `Road` (background), `PlayerCar`, and `ObstacleContainer` (spawned traffic). `LaneDivider` is a separate, independently-timed decorative strip — it is **not** a child of `PlayerBoard` and does not share state with it directly (see §7, this is a deliberate but fragile design).

Global/shared state lives in the `GameSettings` autoload (`scripts/GameSettings.gd`, registered in `project.godot` under `[autoload]`): player count, chosen skins, the `PLAYER_SKINS` and `TRAFFIC_KINDS` tables (textures + spawn weights + per-kind speed ranges), and the 4-way keyboard binding table (`PLAYER_CONFIGS`).

## 4. What's already implemented

- Full menu flow: main menu → 2/3/4 player select → per-player skin select (duplicate-skin avoidance, ready-up gating) → round start.
- Momentum-based steering (not lane-snapping) with configurable top speed and grip response.
- **Dash**: double-tap a direction within a short window → fast eased snap exactly one lane over, with a fading afterimage trail, on a per-player cooldown.
- **Drift**: triggered by a genuine velocity reversal (pressing the opposite direction while still carrying real speed the other way) — not a separate button/gesture. Nose points where you steer, actual momentum lags behind at reduced grip, leaves a twin continuous skid-mark trail (`Line2D`, not stamped marks). The drift *session* (trail + nose lead, `is_drifting`) persists across direction switches and only ends after a short release-grace window with both keys up; *grip* (`drift_sliding`) is a separate sub-state that resolves once momentum catches up to the held direction, and instantly re-engages on a fresh reversal. See §5/§6/§8 for why this is split this way — it was not obvious up front.
- Traffic: 7 vehicle kinds (sedan, SUV, pickup, van, truck, bus, motorcycle) with weighted random spawn selection, real cropped sprite art, per-kind size ratios matched to each sprite's real aspect ratio.
- **Chaotic lane-changing traffic**: a random slice of spawned obstacles blink a turn signal, then smoothly merge one lane over mid-transit, instead of every vehicle holding a perfectly straight line for its whole lifetime. See §5 session D for the fairness constraints that keep this from feeling cheap.
- Speed ramp: `current_speed() = BASE_SPEED + elapsed * SPEED_PER_SECOND` (160 base, +6/s), same formula shared conceptually across `PlayerBoard` and `LaneDivider`.
- Round scoring by distance traveled; game-over overlay declares the winner; Enter restarts, Esc returns to menu.
- Road and median rendered as tiled real-texture scrolling strips (not procedurally drawn shapes) — both cropped from the same source art so grass/guardrail styling matches exactly (`Road.SHOULDER_RATIO` is tuned to the texture's actual asphalt width).
- **Player-count-aware camera framing**: camera zoom adapts to fit every board's full width on screen at any player count (2-4), only ever zooming out from the preferred `1.15`, never in — see §5 session E. Road/median tile rendering and obstacle spawn/despawn extend to match whatever extra vertical area that zoom-out reveals, and a screen-space vignette (`ScreenMask.gd`) masks the top/bottom edge.
- **Skill pickup + choice system (plumbing only, no actual skills yet)**: a rare glowing collectible (`SkillPickup.gd/.tscn`) spawns in a free lane every 9-15s, scrolling at the road's own rate (not a vehicle's own pace). Driving over one doesn't crash the player — it shows two glowing choice icons flanking the car (left = a skill that affects opponents, right = a skill that benefits the player) that the player picks with two new dedicated per-player keys, independent of steering, so the round never pauses and the choice never expires (it only ever changes if the player drives over another pickup before picking). `PlayerBoard._resolve_skill_choice()` is a deliberate stub — no skill effects exist yet. See §5 session F for the full design history (two real corrections from the initial pass) and §11 for next steps.
- **Boost**: a per-player charge bar (drawn above the car via `PlayerBoard._draw()`) fills while `is_drifting` is true. Spent by holding the player's `confirm` key (bound per-player in `PLAYER_CONFIGS`, previously unused during a round) — a hold-to-drain resource, not an instant full-bar burn, so a player can spend part of the bar and bank the rest. Speed multiplier is re-read from the *current* charge every frame across three tiers (1.3x/1.5x/1.8x), so a long burn from a full bar visibly weakens as it drains through them. Multiplies `current_speed()` only (not `elapsed`), so it doesn't touch the permanent difficulty ramp. Exhaust is small procedural flame polygons (same technique as the dash-ghost trail, no particle system/new art) tinted from the player's own car color, which required adding a real `Color` per skin (`GameSettings.PLAYER_SKINS[i]["color"]`) since skins were texture-only before — threaded through `SkinSelect` lock-in → `Main._build_boards()` → `PlayerBoard.body_color`. See §5 session C and §12 for details.

## 5. Session history

### 2026-08-21, session F: skill pickup + choice system (plumbing only)

User asked for a skill system to be added, explicitly scoped to *just the system* — no actual skills, those come later. Requirements given: something glowy appears on the road; running it over with your car gives the player 2 choices; one choice affects opponents, the other benefits the player themself; visually inspired by (but only loosely, "just a suggestion") Tricky Towers' skill-choice popup, where two icons appear near the player's piece. User also suggested, as one possible layout, self-benefiting skills on the right of the car and opponent-affecting skills on the left.

Built as three pieces:

1. **`SkillPickup.gd`/`.tscn`**: a new `Area2D`-based collectible, structurally parallel to `Car.gd` (procedural, no texture/art asset) — concentric pulsing-alpha circles for a glow, plus a slowly-rotating 4-point sparkle polygon (rotation done via the node's own `rotation` property, not by hand-transforming points). `PlayerBoard._spawn_skill_pickup()` spawns one every `randf_range(SKILL_PICKUP_INTERVAL_MIN, SKILL_PICKUP_INTERVAL_MAX)` (9-15s) into the same `obstacle_container` traffic already lives in, tagged with the same `lane`/`speed_mult` meta convention (`speed_mult = 1.0`, since a pickup is a fixed road marking, not a vehicle with its own forward speed — see the `TRAFFIC_KINDS` speed-fraction reasoning in `GameSettings.gd` for why 1.0 would be wrong for an actual vehicle but is exactly right here). This let it ride the *existing* per-frame obstacle movement/despawn loop and lane-change-state-machine no-op path with zero special-casing. The lane-availability scan that both traffic and pickups need (don't spawn in a lane something else already occupies near the top of the board) was factored out of `_spawn_obstacle()` into a shared `_lanes_used_near_top()`.
2. **Collision routing**: `PlayerBoard._on_player_area_entered()` now checks `area is SkillPickup` first and branches to `_collect_skill_pickup()` instead of the crash path — this is the only change to crash detection itself.
3. **The choice UI + resolution flow** — this is where the design changed twice from the first shipped version, based on direct user feedback:
   - **First version (rejected)**: collecting a pickup froze that player's whole board (`choosing_skill` gated the top of `_process()`, mirroring how a crash already freezes one board via `alive`/`active`) and the two choice icons were picked with the player's *existing* `key_left`/`key_right` — spatially matching the left/right icon layout. User's correction: **the game should never pause**, and picking should use **a different button**, not the steer keys (which are needed to keep dodging while the choice is up).
   - **Second version**: removed the freeze entirely — `choosing_skill` no longer gates `_process()`; steering/traffic/spawn/distance all keep running unchanged while it's true. Added two new dedicated per-player key bindings, `key_skill_opponent`/`key_skill_self` (wired through `GameSettings.PLAYER_CONFIGS` → `Main._build_boards()` → `PlayerBoard`, same threading pattern as `key_left`/`key_right`/`key_confirm`), independent of steering. This version also added a 4-second expiry with a last-second fade-out, on the assumption an ignored choice shouldn't linger forever.
   - User's second correction: the choice should **not** disappear/expire — it should only ever change if the player drives over *another* pickup before picking. Removed `SKILL_CHOICE_WINDOW`/`SKILL_CHOICE_FADE_START` and the countdown entirely; `choosing_skill` now only clears in `_resolve_skill_choice()`, i.e. only when the player actually presses one of the two keys. Colliding with a second pickup while a choice is already up just re-triggers it (resets the glow-pulse animation) rather than stacking or being ignored.

   Final input handling: `key_skill_opponent`/`key_skill_self` presses are checked in `_unhandled_input()` right after the `active`/`alive` gate but *before* the `is_dashing` gate — a dash in progress has no reason to block a skill pick, unlike steering input.

   The keyboard bindings chosen for the four players' two new keys (P1: Q/E, P2: `,`/`.`, P3: R/Y, P4: U/O — each flanking that player's existing `confirm` key as a mnemonic only) are arbitrary placeholders. **User stated this project targets PS5**, where steering will map to a stick and these two actions become a pair of shoulder/face buttons — so the specific keyboard keys chosen now don't need to be especially ergonomic and shouldn't be over-optimized for keyboard play.

`PlayerBoard._resolve_skill_choice(category: String)` is a deliberate stub: it just `print()`s which category ("opponent" or "self") was picked and clears `choosing_skill`. This is the explicit hook point for real skill selection/effects once actual skills are designed — see §11.

User confirmed the pickup/glow/icon visuals and the final (no-pause, no-expiry, dedicated-button) behavior looked good and asked to push; not separately re-tested in-editor after the "don't expire" tweak beyond the user's own read of the diff description, since that change is a pure subtraction (removing the timer/fade code) with no new logic to verify.

### 2026-08-21, session E: 4-player camera clipping + top/bottom render seam

User reported that in 4-player mode, the leftmost and rightmost boards only showed 3-4 of their 5 lanes — the rest didn't render — and separately asked for more road to be rendered ahead at the top, for the current zoom level to be kept as-is, and for the seam where rendering visibly starts/stops (top and, worse, bottom/"behind") to be masked better.

Root cause of the clipping: `Main._build_boards()` used a fixed `CAMERA_ZOOM` (1.15) regardless of player count. `boards_container`'s total width scales with player count (`count * board_width + (count-1) * BOARD_GAP`), but the camera's visible width at a fixed zoom does not — at 2-3 players the total width fits comfortably inside what `1.15` shows, but at 4 players (`1584` world units) it exceeds the visible width at that zoom (`viewport_width / 1.15 ≈ 1304`), so roughly 140px of each outer board fell outside the camera's view. That's almost exactly "2-3 lanes' worth" of a 5-lane, 360px-wide board — matching the reported symptom precisely.

Root cause of the render-seam complaint: fixing the above by zooming the camera *out* to fit 4 players' width also widens the vertical slice the camera sees (zoom is uniform on both axes), without `board_height` changing. That extra vertical slice fell outside `Road._draw()`/`LaneDivider._draw()`'s hardcoded `[0, height]` tiling loop, exposing bare background above and below the track — a visible hard edge where the road stopped being drawn. This letterboxing actually already existed at the *old* fixed zoom too (a smaller ~38px gap present in every player count, just apparently unnoticed until the 4-player fix made it bigger), which is why the fix below applies to 2-3 players as well, not just 4.

Fixed with three coordinated changes, all keyed off one computed `vertical_margin` (how far past `[0, board_height]` the camera can see, in board-local units):

1. **Dynamic camera zoom** (`Main._build_boards()`): `zoom = min(CAMERA_ZOOM, viewport_width / (total_width + margin))` — only ever zooms *out* from the preferred `1.15`, never in, and only as far as needed to keep every board's full width on screen. This is why 2-3 player framing is provably unchanged (`fit_zoom` exceeds `1.15` there, so `min()` still picks `1.15`) while 4-player no longer clips.
2. **Extended tile rendering** (`Road.render_margin`, `LaneDivider.render_margin`, both `@export var`, default `0.0`): the draw loop's bounds became `[-render_margin, height + render_margin]` instead of the fixed `[0, height]`, generalizing the original anchor-and-loop logic rather than replacing it (`render_margin = 0` reproduces the exact old behavior — verified by inspection, the top loop's extra `while y > top_edge: y -= tile_h` never executes when `top_edge = 0` since `scroll - tile_h` is already `<= 0`). `Main` sets this on every board (via `PlayerBoard.set_vertical_margin()`, which forwards to `road.render_margin`) and every divider directly (dividers have no wrapper node to go through).
3. **Extended obstacle spawn/despawn** (`PlayerBoard.vertical_margin`): spawn y and the despawn threshold both got `- vertical_margin` / `+ vertical_margin` added, so traffic still pops in/out beyond whatever the camera can actually see, at any zoom level.
4. **`ScreenMask.gd`** (new script + new `HUD/ScreenMask` node, first child of `HUD` so other HUD elements draw over it): a screen-space (not world-space, so unaffected by camera zoom) top/bottom vignette, fading to the viewport's own background color. Its fade height is `vertical_margin * zoom + SCREEN_MASK_BASE_PX` — converts the world-space margin back to screen pixels through the current zoom, plus a small always-on constant (24px) so there's a subtle fade even at 2-3 players where `vertical_margin` is 0. This is the actual "mask it better" ask — items 2-3 are structurally correct (nothing is missing/popping visibly) but the mask is what makes the top/bottom edge read as an intentional fade rather than a rendering boundary, however precisely items 2-3 are tuned.

User playtested in-editor and confirmed ("it looks great push it") without requesting further changes.

### 2026-08-20, session D: chaotic lane-changing traffic + turn signals

User asked for traffic to feel more chaotic — cars and trucks occasionally changing lanes — but explicitly wanted it kept fun/fair rather than cheap, and asked for a real-car-style yellow indicator light that blinks before the lane change starts, the way a real turn signal does.

Built as two pieces:

1. **Turn signal lamps (`Car.gd`)**: two small `Polygon2D` lamps built procedurally in `_ready()`/positioned in `_position_indicators()` (called from `_rebuild()`), so no scene or art changes were needed and it works identically on the placeholder shape and on real cropped-photo textures. `start_indicator(side)` (-1 left, 1 right) turns the correct lamp on immediately and arms a repeating blink via `_process`/`INDICATOR_BLINK_INTERVAL` (0.16s); `stop_indicator()` kills both. This node only owns the blink animation — it has no opinion about *when* to signal.
2. **Lane-change state machine (`PlayerBoard.gd`)**: `_maybe_flag_lane_change()` flags ~22% (`LANE_CHANGE_CHANCE`) of newly spawned obstacles with `lc_state = "pending"` and a random trigger y within the top half of the board (`LANE_CHANGE_TRIGGER_Y_MIN/MAX_FRAC`, 12%–50% down). `_update_obstacle_lane_change()`, called once per obstacle per frame from the same loop that already moves them, drives `pending -> warning -> moving -> settled -> idle`:
   - `pending`: waits until the obstacle reaches its trigger y, then calls `_pick_lane_change_direction()`, which only offers a direction whose target lane is clear of other traffic within `LANE_CHANGE_SAFE_GAP` (200px) of the same y (`_lane_clear_near()`). If neither adjacent lane is safe, it cancels back to `idle` rather than forcing a move.
   - `warning`: indicator blinks for `LANE_CHANGE_INDICATOR_WARNING` with the car still going perfectly straight — no motion at all yet.
   - `moving`: smoothstep-eased slide from the old lane center to the new one over `LANE_CHANGE_DURATION`.
   - `settled`: keeps blinking for `LANE_CHANGE_INDICATOR_TAIL` after arriving (a real signal doesn't cut off instantly either), then calls `stop_indicator()` and goes `idle` for good — each obstacle changes lanes at most once.

The obstacle's `lane` meta (already read by `_spawn_obstacle()`'s used-lane check) is updated the moment the direction is *decided*, not once the slide finishes — so a car mid-merge still correctly blocks a new spawn or another lane-change from targeting the lane it's moving into.

User playtested and asked for the indicator to "turn a lit bit earlier" — `LANE_CHANGE_INDICATOR_WARNING` was bumped `0.7s -> 1.3s` so the blink-before-move gap reads clearly. Confirmed after that change ("good push it").

### 2026-08-20, session C: drift-charged boost system

User asked for a boost tied to drifting: a bar that fills while drifting, and when activated gives a speed boost with a fiery exhaust colored to match the player's own car. Built in two passes based on follow-up feedback:

1. **First pass**: bar fills while `is_drifting`, single press of the (previously unused in-round) `confirm` key burns the *entire* bar at once for a fixed 1.7x/1.0s boost. Flame exhaust added as procedural `Polygon2D` triangles (same style as the existing dash-ghost trail), tinted from `body_color` — which required adding a `color` field per skin in `GameSettings.PLAYER_SKINS` (skins were texture-only before this) and threading it through `SkinSelect`/`Main` into `PlayerBoard.body_color`.
2. **Follow-up rework**: user wanted (a) partial-charge usage, (b) player control over how much charge to spend, (c) unused charge preserved rather than lost, and (d) the bar split into sections where a fuller bar gives more speed, with a slower fill but longer total boost time. Reworked from "press to burn all" into **hold-to-drain**: holding `confirm` drains `boost_charge` at `BOOST_DRAIN_PER_SECOND` for as long as it's held and charge remains; releasing early stops the drain and banks whatever's left. The speed multiplier is re-evaluated every frame from the *current* charge via `_boost_speed_mult()` across three tiers (low/mid/high, thresholds at 1/3 and 2/3), so a long burn starting from a full bar audibly/visually weakens as it drains down through the tiers rather than staying at one fixed strength for a flat duration. Fill rate dropped from full-in-2s to full-in-~4.5s (`BOOST_FILL_PER_SECOND` 0.5 → 0.22); a full bar now sustains ~2.9s of continuous boost if held straight through (`BOOST_DRAIN_PER_SECOND` 0.35), versus the old fixed 1.0s burst — satisfying "full bar should last longer."

**Real bug hit mid-session, not just a design iteration**: the first attempt at drawing tier-divider lines on the bar used `for frac in [BOOST_TIER_LOW_MAX, BOOST_TIER_MID_MAX]: var divider_x := bar_x + bar_w * frac` — GDScript's static analyzer can't infer a type for `divider_x` from an untyped array-literal loop variable, which is a **parse error**, not a runtime error. This broke `PlayerBoard.gd` entirely, which cascaded into `Main.gd` failing to instantiate any `PlayerBoard` (logged as "Trying to assign value of type 'Node2D' to a variable of type 'PlayerBoard.gd'") — from the user's side this read as "the game just didn't start after locking in skins," with no visible error. **`godot --headless --quit` (the standard validation command in this project) did not catch it**, because with no scene argument it only boots the configured main scene (`MainMenu.tscn`) and quits — it never loads `Main.tscn`/`PlayerBoard.gd`, since those are only reached by preload chains triggered later in the menu flow. Fixed by explicitly typing the loop variable (`for frac: float in [...]`) and the derived var. See §8 and §12 for the standing lesson from this.

After the sectioned rework, user also asked for the tiers to be visually obvious rather than just two thin divider lines — added a third pass rendering each third of the bar as its own block (progressively brighter shades of the player's car color) while charging, switching to a single glowing flame-color fill only while actively draining (blending three block colors mid-burn read as muddy, kept simple instead). User confirmed all of the above in-editor ("great push it") after each round of changes; both the mechanic rework and the section-rendering pass are pushed.

### 2026-08-20, session B: drift feel + continuous skid marks

User asked for two things: make the drift system feel less unintuitive (with a request to research how other games handle it), and fix the skid marks leaving discontinuous "part by part" marks instead of a continuous trail. This took four iterations because the first three each fixed a real bug but exposed the next one — **read this in order, it's the reasoning trail, not just a changelog**:

1. **Continuous trail (right the first time).** Old: `PlayerBoard._spawn_drift_mark()` stamped a `ColorRect` on a `DRIFT_MARK_INTERVAL` (0.045s) timer. At max steer speed (460px/s) the car moves ~20px between stamps while each stamp is only ~7px wide — guaranteed gaps. Per standard practice in every top-down drift tutorial researched (Godot forum "tire drift/skid marks with Line2D", multiple Line2D trail tutorials), replaced with two `Line2D` trails (one per rear wheel) that get a point appended every single `_process` frame while drifting — continuous regardless of speed. This part was correct from the start and never needed revisiting.

2. **Drift never resolved (attempt 1).** Original drift only ended `is_drifting` on full key release — so a caught slide stayed in reduced-grip mode for as long as any key was held, reading as a sticky mode rather than a slide you catch (unlike CarX/Inertial Drift-style resolution researched). First fix: auto-end the whole `is_drifting` session once `car_vx` converges to ~88% of `target_vx`. **This broke "keep drifting while switching direction"** (a pre-existing, deliberately-preserved feature) — ending the session also set `drift_cooldown_timer`, which then blocked an immediate re-drift on the next reversal.

3. **Split session from grip (attempt 2).** Fix: separated the *session* (`is_drifting` — trail generation + nose-lead rotation, persists across direction switches, only ends on release) from *grip* (new `drift_sliding` — resolves on convergence, but a fresh reversal re-arms it instantly via `_try_start_drift()`'s already-mid-session branch, no cooldown). This fixed holding-then-releasing, but the user reported switching direction **still** killed the drift.

4. **Release-both-keys gap (attempt 3).** Root cause: a real keyboard direction switch is never a single frame — there's a brief instant where both steer keys read released while a finger moves off the old key before it's on the new one. `is_drifting` was ending (session-level) the instant `target_vx` hit 0, which fires during that gap on every switch. Fix: `DRIFT_RELEASE_GRACE` (0.14s) — the session only actually ends once both keys have stayed released for the whole grace window, not on the first zero-input frame.

5. **Both-keys-held-simultaneously gap (attempt 4, the actual root cause).** User sent a screen recording (couldn't be read — see §8 for why) and re-reported the same symptom, which forced a re-check of `target_vx` itself rather than the drift state machine. Found it: `target_vx` was computed as `if left and not right: ... elif right and not left: ...`, meaning **both keys held simultaneously reads as neutral (target_vx = 0)**. Players commonly press the new direction key slightly *before* releasing the old one (especially on adjacent Left/Right arrow keys), so that overlap was decelerating the car to a dead stop mid-switch — independent of and underneath all the session/grip state machinery from attempts 2–3, which is why fixing the state machine alone never fully resolved it. Fix: added `steer_priority` (set to ±1 on every key-press event), and when both keys read held, `target_vx` now resolves to whichever direction was pressed most recently instead of zeroing out.

User confirmed after fix #5 that weaving (rapid direction changes without ever releasing) keeps the slide and trail unbroken ("its great, push it").

### 2026-08-20, session A: traffic speed/direction bug chain

Reported by the user as: *"trees and road moves at a different speed and cars look like it is going backward."* Three distinct, real bugs were found and fixed in sequence — **all three fixes are necessary; none of them individually resolved the full symptom**:

1. **`LaneDivider` never reset across rounds** (commit `b049efe`). `LaneDivider._process` accumulates its own `elapsed`/`distance` from the moment the node is created and never stops. `Main._start_round()` resets every `PlayerBoard`'s `elapsed`/`distance` to 0 on both the first round and every restart, but never touched the dividers. After any restart-after-crash, the road/traffic speed would snap back to `BASE_SPEED` while the tree median kept accelerating from wherever it had already climbed to — a growing speed mismatch between trees and road. Fix: added `LaneDivider.reset()`, called from `Main._start_round()` for every child of `dividers_container` alongside each board's `start_round()`.

2. **Road/median tiles scrolled in the opposite direction from traffic** (commit `5353b8a`). This was the primary cause of "cars look like they're going backward." `Road._draw()` and `LaneDivider._draw()` both anchored their tile loop at `y = -scroll`, and as `distance` (and therefore `scroll`) grew, that shifts the rendered pattern toward **negative y** (up, off the top of the screen). But obstacle traffic in `PlayerBoard._process` moves via `child.position.y += speed * speed_mult * delta` — **positive y** (down, toward the player), which is the geometrically correct direction for "you are driving forward." Background scrolling up while foreground traffic scrolls down is a direct visual contradiction — the road reads as sliding the wrong way under the cars. Fix: changed the anchor to `y = scroll - tile_h` in both `_draw()` methods, which makes the tiled pattern slide toward +y (down) as `distance` grows, matching the traffic direction. Coverage math (tile spacing, no gaps) is unaffected — only the anchor point's sign flipped.

3. **Some individual obstacles still looked like they were reversing, even after fix #2** (commit `d4b9532`). Root cause: `PlayerBoard._spawn_obstacle()` picked `speed_mult` uniformly from `randf_range(0.78, 1.28)` and used it as `child.position.y += speed * speed_mult * delta` directly. The road texture itself always scrolls at exactly `speed` (i.e., implicitly `speed_mult == 1.0`). Any obstacle with `speed_mult > 1.0` therefore closes toward the player **faster than the road surface's own scroll rate** — which is only physically possible if that car is driving in reverse relative to the road. Visually this reads as the car sliding backward across the lane stripes, even though its on-screen y is still increasing. Fix: reworked the whole speed model in terms of relative motion — an obstacle's screen speed represents `(road speed − the vehicle's own forward speed)`, which for any car that is actually driving forward is always strictly less than the road's own scroll rate. Implemented as per-`TRAFFIC_KINDS`-entry `speed_frac_min`/`speed_frac_max` fields (all kept below 1.0, capped at 0.95 max — see the invariant in §7), replacing the single flat 0.78–1.28 range. Trucks/buses get high fractions (0.75–0.95 → slow real-world speed → you close in on them fast); motorcycles get low fractions (0.35–0.65 → fast real-world speed → they roughly keep pace with you, hard to catch); sedans/SUVs/pickups/vans sit in between (0.55–0.9).

User confirmed the result looks correct after fix #3 ("its great").

## 6. Key technical decisions & why

- **Skill choice never pauses the round and never expires.** Both were tried and explicitly rejected by the user in session F — see §5. The standing rule going forward: `choosing_skill` must never gate `PlayerBoard._process()`'s steering/traffic/distance logic, and must only be cleared by `_resolve_skill_choice()` (an actual pick), never by a timer. If a future skill needs a time-limited effect, that belongs in the *skill's own* implementation once skills exist, not in the choice-presentation system itself.
- **Skill-choice input uses dedicated keys, not the existing steer keys.** The first draft reused `key_left`/`key_right` to pick, which read naturally against the left/right icon layout but forced the player to stop steering to choose. `key_skill_opponent`/`key_skill_self` are separate bindings for exactly this reason — see §5 session F and §7.
- **`SkillPickup` reuses `PlayerBoard.obstacle_container`'s existing per-frame movement/despawn loop and lane-occupancy convention (`lane`/`speed_mult` meta) instead of a parallel container/loop of its own.** Since a pickup's motion (scroll at road speed) and despawn condition (past `board_height + margin`) are identical in shape to traffic's, giving it its own container would have meant duplicating that loop for no benefit — this is the same "don't duplicate a system you can parametrize" instinct as `Road`/`LaneDivider.render_margin` in §6/§7's existing entries.

- **Relative-speed model for traffic, not absolute multipliers.** An obstacle's screen-space closing speed must always be expressed as *(reference scroll rate − vehicle's own forward speed)*, never as an independent multiplier applied to the base speed. This is the single most important invariant introduced this session — see §7.
- **Per-vehicle-kind speed ranges instead of one global range.** Chosen over a single flat range because (a) it fixes the >1.0 bug structurally — every kind's range is authored below 1.0 — and (b) it adds gameplay texture "for free" (heavy vehicles feel slow/easy to catch, motorcycles feel nimble) without extra systems.
- **Dividers keep their own independent timer rather than reading a board's speed directly.** This predates session A's changes and was not restructured, only patched (see §7 for why this is a known fragility, not an endorsement).
- **Real cropped-texture tiling for road/median instead of procedural drawing.** Predates session A (commit `374f392`); kept as-is. Rationale (from the commit): both textures come from the same source art so grass/guardrail styling matches exactly, and it looks better than procedural shapes.
- **Drift session state and drift grip state are two separate booleans (`is_drifting` / `drift_sliding`), not one.** Session B tried a single flag first — it's simpler on paper, but conflates "should the trail/nose-lead be active" (a UI/feel question, answer: yes for as long as you're steering at all) with "should grip currently be reduced" (a physics question, answer: only while the slide hasn't caught up yet). They have different natural lifetimes and different end conditions; forcing them into one flag is what caused attempts 2's regression in §5.
- **`target_vx` tie-breaks toward the most-recently-pressed key on overlap, not neutral.** Treating "both steer keys held" as 0 (the original behavior) seems like the obviously-correct default, but it isn't what a fast key switch on a real keyboard produces — see attempt 5 in §5. Any future rework of the steering input must preserve `steer_priority` or reintroduce this exact bug.
- **Boost is hold-to-drain, not press-to-burn-all.** First implementation (session C, pass 1) spent the entire bar on a single keypress for a fixed-duration boost. User explicitly wanted partial spending, player-controlled amount, and unused charge preserved — a resource you dip into, not an ability you trigger. This is a real design requirement, not just a numbers tweak; don't revert to a fixed-consume-all model without re-confirming with the user.
- **Boost's speed tier is re-read from *current* charge every frame, not locked in at activation.** Considered locking the multiplier to whatever tier the bar was in when `confirm` was first pressed, but re-reading it live means a long burn from a full bar naturally tapers off in strength as it drains through the tiers — matching "a full bar should last longer" (more charge = more sustained time at *some* level of boost, front-loaded toward the strong end) without needing a separate duration-per-tier system.
- **Lane changes only commit when the target lane is verified clear, never on a fixed schedule.** Considered just picking a random direction at the trigger point, but that risks an obstacle sliding straight through another car — `_lane_clear_near()` gates the decision so a blocked lane silently cancels the change instead. This is what keeps "more chaotic" from becoming "unfair"; don't remove the safety check to simplify the state machine.
- **Camera zoom fits the widest player count instead of being tuned for one and left fixed.** A fixed zoom (the pre-session-E state) looks right for whichever player count it was tuned against and silently clips every other count that's wider — there's no visual warning, lanes just fall outside the viewport. Computing `zoom = min(CAMERA_ZOOM, viewport_width / total_width)` per build means the ceiling (`1.15`, the preferred feel) is preserved wherever it fits and only relaxed where it must be, rather than picking a single compromise value that's slightly wrong at every player count. See §5 session E.
- **`render_margin` / `vertical_margin` is plumbed through as an explicit value computed once in `Main`, not re-derived independently in `Road`, `LaneDivider`, and `PlayerBoard`.** Each of those needed to know the same "how far past the board's own bounds can the camera see" number for a different purpose (tile coverage, obstacle spawn/despawn), but only `Main` has both the viewport size and the final chosen zoom to compute it from. Passing the one computed value down (rather than, say, having each script independently query `get_viewport()` and guess the current zoom) keeps them from ever disagreeing — the exact class of duplication risk already flagged for `BASE_SPEED`/`SPEED_PER_SECOND` in §7/§9, deliberately avoided here.
- **`body_color` on `PlayerBoard` is no longer just a placeholder-shape fallback.** It predates session C as an unused fallback color for `Car.gd`'s placeholder `Polygon2D` (real skins always use a texture, which hides the placeholder — see §12). Session C repurposed it as the actual per-player theme color for boost UI and exhaust flames by having `Main._build_boards()` populate it from the new `GameSettings.skin_colors` array. If skin selection is ever reworked, `skin_colors` must stay in lockstep with `skins` (same index, same length) or boost/exhaust colors will mismatch a player's actual car.

## 7. Assumptions, constraints, conventions that must be preserved

- **`choosing_skill` must never gate/pause `PlayerBoard._process()`, and must only be cleared by an actual pick (`_resolve_skill_choice()`), never by a timer.** Both a pause-while-choosing design and a timed auto-expiry were built, playtested, and explicitly rejected by the user in session F (see §5, §6). Don't reintroduce either without re-confirming — this is a real, twice-stated design requirement, not a numbers tweak.
- **`SkillPickup` nodes live in the same `obstacle_container` as traffic and must keep setting `lane`/`speed_mult` meta the same way traffic does.** `_lanes_used_near_top()` (shared by `_spawn_obstacle()` and `_spawn_skill_pickup()`), the per-frame movement/despawn loop, and `_lane_clear_near()` (used by lane-changing traffic to avoid merging into an occupied lane) all rely on every `obstacle_container` child exposing these two meta keys, regardless of whether it's a `Car` or a `SkillPickup`. If a new kind of obstacle-container child is ever added, it needs the same two meta keys or it will break these shared scans.

- **Godot 2D coordinate convention: +y is down.** Any code that scrolls the road, median, or traffic must treat *increasing y* as "moving toward the player" (who sits near the bottom of each board). This is easy to get backward (as fix #2 shows) — always sanity-check the sign against `PlayerBoard._process`'s obstacle movement line (currently `child.position.y += speed * speed_mult * delta`), which is the canonical "forward" direction.
- **Invariant: every `TRAFFIC_KINDS` entry's `speed_frac_max` must stay below `1.0`.** This encodes "no traffic vehicle may close in on the player faster than the road itself scrolls." Violating it (as the pre-session code did with 1.28) reintroduces the "driving backward" visual bug. If you add a new vehicle kind, give it `speed_frac_min`/`speed_frac_max` in roughly the `[0.3, 0.95]` band and keep the max end away from `1.0` (a small safety margin, not just `< 1.0` exactly, keeps the effect visually convincing even at high round speeds).
- **`Road._draw()` and `LaneDivider._draw()` must use the same tile-anchoring convention.** They currently both use `y = scroll - tile_h`. If one is changed without the other, the road and median will visibly scroll at different apparent rates/directions again (this is exactly bug #2 in miniature). Treat these two functions as a matched pair.
- **`Main._build_boards()` is the single source of truth for `vertical_margin`/`render_margin` (see §5 session E, §6).** `Road`, `LaneDivider`, and `PlayerBoard` all just store and use whatever value they're given — none of them compute it independently. If camera framing logic is ever touched, keep this one-way flow (`Main` computes → pushes down) rather than letting a script derive its own guess from `get_viewport()`, or the top/bottom render coverage can silently fall out of sync with the actual camera zoom.
- **Camera zoom (`Main._build_boards()`) must never exceed `CAMERA_ZOOM` (1.15), only go below it.** `zoom = min(CAMERA_ZOOM, fit_zoom)` — this is intentional: `CAMERA_ZOOM` is the tuned "good" feel confirmed by the user, and `fit_zoom` only kicks in to prevent boards from being clipped at wider player counts. If a future change needs a different zoom ceiling, update `CAMERA_ZOOM` itself rather than the `min()` — flipping it to `max()` or dropping the cap would let the game zoom in tighter than intended at narrow player counts, which was never asked for.
- **`Main._start_round()` must reset every board AND every divider.** If a new decorative or moving element is added to `Main.tscn` with its own internal timer, it must also be reset here, or it will desync after the first restart the same way `LaneDivider` did (bug #1).
- **`BASE_SPEED` / `SPEED_PER_SECOND` are currently duplicated** as separate constants in `PlayerBoard.gd` (160 / 6) and `LaneDivider.gd` (160 / 6, same values, copy-pasted). They must be kept numerically identical or the road and median will scroll at different rates. See §9 for the recommended fix (centralize this).
- **No automated test suite exists.** `godot --headless --quit` only catches GDScript compile/parse errors — it does not verify gameplay behavior, timing, or visual correctness. Every bug in §5 was diagnosed by reading the physics/input logic, not by running a test. **The user's explicit workflow preference: always let them playtest a change in the editor before committing** — do not commit right after an edit just because headless validation passed. Wait for explicit confirmation (e.g. "it's great", "push it") before running `git commit`.
- Commits in this repo explain *why*, with the physical/visual/input reasoning spelled out (see commit history). Keep that convention — this codebase has a history of subtle sign/reference-frame/input-timing bugs where the reasoning is what prevents regressions.
- **`DRIFT_CONVERGE_FRAC` (0.88), `DRIFT_RELEASE_GRACE` (0.14s), and `REVERSAL_THRESHOLD` (140) are feel-tuned constants, not derived values.** If drift feels too sticky, lower `DRIFT_CONVERGE_FRAC`; if switching direction still occasionally drops the session, raise `DRIFT_RELEASE_GRACE` slightly — but note session B's actual bug (steer_priority / both-keys-held) was independent of this constant, so don't assume a "still drops sometimes" report is this timer before checking `target_vx` computation first.

## 8. Approaches that were tried and did NOT work (don't repeat these)

- **Assuming the restart-desync fix (bug #1 / `LaneDivider.reset()`) would resolve the "cars going backward" complaint.** It didn't — the user reported it was still happening after that fix shipped. That fix was still correct and necessary (it's a real, separate bug), but it was not the primary cause of the reported symptom. Lesson: when a background-vs-foreground motion complaint persists after a timing/sync fix, check the *direction* of motion next, not just the *rate*.
- **Assuming the direction fix (bug #2) alone would resolve it.** After shipping the `y = -scroll` → `y = scroll - tile_h` change, the user reported *some* cars still looked backward — not all of them. This pointed away from a global/systemic direction bug (already fixed) and toward a per-obstacle issue, which was bug #3 (the `speed_mult` range exceeding 1.0). Lesson: "some cars" vs. "everything" is a meaningful diagnostic signal — a global draw-direction bug affects everything uniformly; a per-obstacle backward artifact points at per-obstacle speed logic.
- **The original `speed_mult` range of `0.78–1.28`** (introduced in commit `374f392`, before session A) was an attempt to add speed variety ("cars drift ahead of or fall behind each other") but was implemented as a naive multiplier on the base speed without grounding it in the relative-speed model. Do not reintroduce a flat range that crosses `1.0` — see the invariant in §7.
- **Session B, ending the whole drift session on grip convergence** (attempt 1 in §5). Looked correct in isolation (fixed the "sticky forever" complaint) but broke direction-switch continuity because it also armed a cooldown. Lesson: when a state has two different "done" conditions (grip resolved vs. player let go), collapsing them into one flag will eventually satisfy one caller and break another — split them instead of picking whichever one the current bug report is about.
- **Session B, assuming the state-machine fixes (attempts 2–3) would resolve "stops when changing direction."** They didn't, fully — the user reported the same symptom again after both landed. The actual bug (attempt 5, `target_vx` treating simultaneous both-keys-held as neutral) lived one layer below the drift state machine entirely, in plain steering input. Lesson: if a complaint survives a fix that was clearly a real, necessary bug, check the layer *underneath* the one you just fixed, not just harder within the same layer — here that meant looking at raw `Input.is_physical_key_pressed` handling instead of tuning `is_drifting`/`drift_sliding` further.
- **Untyped `for x in [const_a, const_b]:` loop feeding a `:=` inferred var (session C).** `for frac in [BOOST_TIER_LOW_MAX, BOOST_TIER_MID_MAX]: var divider_x := bar_x + bar_w * frac` is a **parse error** in this project's GDScript (4.7, presumably with static typing warnings/errors enabled) — `frac`'s type can't be inferred from an untyped array literal, so nothing derived from it can use `:=` either. This isn't a runtime bug that only shows up when the code path executes — it's a load-time parse failure, so it broke the *entire* script (`PlayerBoard.gd`) the moment anything tried to load it, which cascaded into `Main.gd` silently failing to build any player boards. Fix: type the loop variable explicitly (`for frac: float in [...]`) or explicitly type the derived var (`var divider_x: float = ...`). **Lesson: any `for x in <array literal or untyped Array>:` loop in this codebase should type the loop variable if anything inside the loop body uses `:=` on a value derived from it** — don't assume GDScript's local type inference reaches through loop-variable iteration.
- **Trusting a no-argument `godot --headless --quit` to validate scripts not reachable from the configured main scene (session C).** This project's own `CLAUDE.md` documents this exact command as the standard validation step, and it *did* run clean after the parse-error bug above was introduced — because the project's main scene is `MainMenu.tscn`, and nothing in the menu screen's own script chain preloads `PlayerBoard.gd`. The bug was only reachable by actually progressing through the menu flow to `Main.tscn`, which the bare command never does. **Lesson: when validating a change to a script that isn't loaded from the project's initial scene (anything under `PlayerBoard`, `Road`, `LaneDivider`, or scenes instantiated dynamically via `preload()`+`instantiate()` rather than being in the boot scene tree), run `godot --headless --quit res://scenes/<TheActualScene>.tscn` (or each scene in the flow) instead of the bare no-argument form** — the bare form only proves the boot scene's own reachable scripts parse, not the whole project.
- **Reading a user-provided `.mov` screen recording via `cp`/`ffmpeg`/Read on its original path.** macOS puts screen recordings in a `NSIRD_screencaptureui_*` temp folder under `TemporaryItems` that the agent's shell has no permission for (`Operation not permitted`, confirmed with `file`, `cp`, and `ffmpeg` alike) — even though other files under `~/Desktop` were readable fine. Similarly-timed recordings that had already landed on the Desktop were checked as a fallback but didn't show the relevant part of the window (player car area was cropped out of frame). If video evidence is needed again, ask the user to move/save the file to an accessible path (Desktop, project folder) rather than trying to read the screencapture temp path directly.

## 12. Non-obvious implementation details

- **Godot 2D: +y is down, +x is right.** Repeatedly relevant this session — see §7.
- **`GameSettings` is an autoload singleton**, not a resource you instantiate — it's globally accessible as `GameSettings.foo` from any script without a reference, and its `const` tables (`PLAYER_SKINS`, `TRAFFIC_KINDS`, `PLAYER_CONFIGS`) `preload()` every texture at parse time, so adding vehicle kinds means editing this one file's array literals, not spawning new resources.
- **`Car.gd`'s placeholder `Polygon2D` shapes auto-hide** the moment `set_texture()` is called (`body.visible = false; windshield.visible = false` in `_rebuild()`) — you never need to manually hide them when assigning real art to a new `Car` instance.
- **`speed_mult` (the per-obstacle meta key) is a closing-speed *fraction* of the current road speed, not a real-world speed.** Read `PlayerBoard._process`'s obstacle-movement block (`child.position.y += speed * speed_mult * delta`) together with `GameSettings.TRAFFIC_KINDS`' `speed_frac_min`/`speed_frac_max` comment block to understand it — the comment there explains the physical reasoning in full and should be kept in sync with any future changes to this system.
- **Tile-anchoring formula `y = scroll - tile_h`** (in both `Road._draw()` and `LaneDivider._draw()`): `scroll` is `fmod(distance, tile_h)`, always in `[0, tile_h)`. This anchors the first (partially off-screen) tile at `y ∈ [-tile_h, 0)` and lets it (and all tiles after it) drift toward `y = 0` and beyond as `distance` grows, which is what makes the whole pattern appear to slide downward. If you ever need to reverse the visual scroll direction intentionally (e.g. a "reverse" game mode), flip this to `y = -scroll` deliberately — but remember that then also requires making obstacle motion negative to match (see the §7 invariant about keeping `Road`/`LaneDivider`/traffic direction consistent).
- **Dash and drift are purely lateral (x-axis) mechanics** — they do not interact with the forward-scroll speed system described above at all. `car_vx`/`car_x` in `PlayerBoard.gd` are entirely separate from `distance`/`current_speed()`. Don't conflate the two systems when debugging either one.
- **Drift trail scrolling is done by mutating every existing `Line2D` point every frame** (`for i in line.get_point_count(): line.set_point_position(i, ...)` in `_process`), not by moving the node. This mirrors how the old `ColorRect` marks scrolled (`mark.position.y += speed * delta`) but is O(points) per trail per frame instead of O(1) — fine at party-game scale (a few players, short-lived trails capped by fade duration) but would need rethinking if trails were made much longer-lived.
- **`_try_start_drift()` is one function serving two different callers with different needs**: a fresh entry from normal driving (gated by `REVERSAL_THRESHOLD` + `drift_cooldown_timer`) and a re-catch mid-session (gated by nothing — `is_drifting` being true is itself the permission). Read the early-return chain top to bottom; the order encodes the priority (dashing blocks everything, then already-drifting short-circuits the cooldown check entirely).
- **Boost's `confirm` key release is handled *before* (and unconditionally of) the `active`/`alive`/`is_dashing` gate at the top of `_unhandled_input`**, unlike every other input in that function. If it were gated the normal way, releasing the key while `is_dashing` happened to be true would get swallowed, leaving `boost_active` stuck on — draining charge with no way to stop it until some later input event fired. Press-side activation (`_try_activate_boost`) is still gated normally. If you add more boost-adjacent inputs, keep "can this leave a persistent flag stuck on" in mind for what needs to bypass the gate.
- **`GameSettings.PLAYER_SKINS[i]["color"]` is a hand-picked flat approximation of each texture's dominant hue, not sampled from the actual sprite.** It exists purely for UI/effects that need a plain `Color` (boost bar fill, exhaust flame tint) rather than a tintable shape — the real car art is a texture. If a skin's art is ever re-colored/replaced, its `color` entry won't update itself and should be revisited by eye.
- **A new global `class_name`-declaring script (e.g. `SkillPickup.gd`) isn't visible as a type to other scripts until Godot rebuilds `.godot/global_script_class_cache.cfg`.** Session F hit this directly: `godot --headless --quit res://scenes/Main.tscn` reported `Could not find type "SkillPickup" in the current scope"` immediately after the script was created, even though the script itself was syntactically fine — the class just wasn't registered yet. Fix/workflow: run `godot --headless --editor --quit` once (a full editor boot that scans the project and rebuilds the class cache) after adding or renaming a `class_name`, *before* trusting a headless compile check's result. A `--headless --quit` alone does not trigger this rescan.
- **GDScript loop-variable typing gotcha**: `for x in <untyped array>:` gives `x` an unresolvable type for the purposes of `:=` type inference on anything derived from it — this is a **parse-time** error, not a runtime one, so it breaks the whole script immediately on load rather than only when that code path runs. See §8 for the specific incident and why the standard `godot --headless --quit` validation command didn't catch it (it never loaded the broken script at all, since the main scene doesn't reach it).
